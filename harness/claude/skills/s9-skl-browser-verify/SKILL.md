# Browser Verification (하네스 필수)

화면/UI 요구사항의 검증은 **코드 리뷰만으로 끝내지 않는다**. 코드가 맞아 보여도 실제
렌더 결과는 다르다(레이아웃 붕괴, 잘림, 겹침, 폰트/색, 느린 로딩, 죽은 버튼). 반드시
**실제 브라우저를 띄워 사람이 하듯 조작**한 근거를 산출물에 포함한다.

## 필수 동작 (가능한 도구로 실제 수행)

1. **띄우고 본다**: 대상 URL(예: `s9 serve` → http://127.0.0.1:9909)을 실제 브라우저로
   열고 초기 렌더를 스크린샷으로 남긴다.
2. **기다린다**: 비동기 로딩·폴링·애니메이션이 있으면 안정될 때까지 대기한 뒤 다시 확인.
   (live 스트림, 그래프 물리 정착, digest 반영 등)
3. **조작한다**: 클릭/탭(버튼·탭 전환·카드), 입력(검색·폼), 드래그(칸반·그래프 노드),
   **스크롤**(긴 목록·터미널 뷰의 하단 도달, 가로 스크롤 컨테이너)을 실제로 수행하고
   각 상태를 스크린샷으로 비교.
4. **반응형**: 좁은 폭/넓은 폭에서 헤더 wrap, 사이드바, 컬럼이 의도대로인지 확인.
5. **콘솔/네트워크**: JS 에러와 실패한 요청(4xx/5xx)이 없는지 본다.

## 검증 수단 (있는 것을 쓴다 — 순서대로 시도)

- 브라우저 자동화 MCP(Playwright/Chrome 계열)나 그에 준하는 도구가 붙어 있으면 그것으로
  navigate/click/scroll/screenshot을 실제 실행한다.
- **Chrome이 설치된 환경**: Chrome 확장(Claude용 브라우저 확장/DevTools MCP 등)을 통해서도
  동일 절차로 확인이 가능해야 한다. 확장 경로가 있으면 그 경로로도 검증한다.
- built-in `run` 스킬이 앱 구동/스크린샷 경로를 제공하면 활용한다.

## ⚠ WSL 환경 (중요 — 리눅스에 브라우저가 없다고 포기하지 마라)

이 하네스는 WSL(Windows 안의 리눅스)에서 자주 실행된다. `which google-chrome`가
비어도 **Windows 쪽에 브라우저가 있다**. 리눅스에 브라우저가 없다는 이유로
"미검증"으로 넘기지 말고 아래를 시도하라:

- **Windows 브라우저로 URL 열기**: 서버는 리눅스에서 `s9 serve` 로 띄우고
  (127.0.0.1은 WSL↔Windows 간 공유됨), Windows 기본 브라우저로 그 주소를 연다 —
  `cmd.exe /c start http://127.0.0.1:9909` 또는 `wslview <url>`(wslu 설치 시)
  또는 `powershell.exe -c "Start-Process <url>"`. 그다음 사용자에게 화면 확인을 요청하거나
  스크린샷을 받는다.
- **Windows의 Chrome을 headless로 구동**: `"/mnt/c/Program Files/Google/Chrome/Application/chrome.exe"`
  (또는 Program Files (x86))를 `--headless --screenshot=<경로> --window-size=1440,900 <url>`
  로 호출해 렌더 결과를 PNG로 얻는다. 경로에 공백이 있으니 따옴표 필수.
- **Windows의 Playwright/Chrome MCP**: Windows 측에 설치돼 있으면 그 MCP로 조작한다.
- **간편 헬퍼**: `~/section9/bin/s9 shot <url> [--out PNG] [--size 1440,900]` 가
  WSL이면 Windows Chrome/Edge를 headless로 구동해 스크린샷 PNG 경로를 출력한다.
  이 PNG를 Read 도구로 열어 실제 렌더를 눈으로 확인하라. (브라우저 없으면 비-0 종료 +
  수동 확인 명령 안내 — 그때만 미검증 처리.)
- 위 경로들을 실제로 시도해 본 뒤에도 불가능할 때만 "실브라우저 미검증"을 명시한다 —
  단, WSL에서 Windows 브라우저 경로를 **시도조차 안 하고** 미검증 처리하는 것은 금지.

## 엔진은 둘이다 — Chrome 만으로 검증을 끝내지 않는다 (Safari/WebKit, REQ-20260906-093)

주인 지시(2026-09-06): **UX 는 반드시 Safari 에서도 확인한다. Mac 에서도 확인한다.**
대시보드는 iPad·Mac 의 Safari 에서 쓰이고, WebKit 은 Blink 와 다르게 그린다 —
`:has()`·`clamp()` 지원 시점, `pointer:coarse` 판정, sticky 안의 의사요소, `min-height`
가 있는 flex 항목의 높이, 100vh 와 주소창, 폭 0 인 오버레이 스크롤바. Chrome 캡처
한 벌은 검증의 절반이다. 경로는 순서대로 시도한다:

1. **실제 Safari** — Mac 또는 iPad 가 닿으면 그 Safari 로 같은 URL 을 열어 캡처한다.
   사람이 열어야 하면 행동 요청 가이드(PROTOCOL 14조)로 절차를 준다.
2. **Playwright WebKit** — Safari 가 없으면 WebKit 엔진으로 찍는다. 이 WSL 에서는
   **Windows 쪽**에 둔다 — 리눅스 WebKit 은 root 권한의 시스템 라이브러리가 필요하고
   원격 테스트 머신도 같았다(2026-09-06 실측, REQ-20260906-093). Windows 는 관리자
   권한 없이 된다. 자리는 `C:\Temp\s9-webkit`. 찍기:
   ```
   s9 shot "http://127.0.0.1:9909/#board" --engine webkit --size 768x1024 --out /tmp/wk-board-768.png
   ```
   → 찍힌 PNG 경로를 Read 로 본다. **엔진이 없으면 `s9 shot --engine webkit` 이 설치
   안내(node zip 풀기 → run-npx.cmd → `install webkit`)를 stderr 로 내고 비-0 으로 끝난다** —
   안내 원문은 `bin/s9.py` 의 `_shot_webkit_install_guide()` 한 곳에만 있다(REQ-20260906-098).
   WebKit 에서 갈리는 것을 계산값으로 확인해야 하면
   같은 폴더의 `probe.js`(playwright API, `page.evaluate`)를 본보기로 쓴다.
3. 둘 다 불가능하면 산출물에 **「Safari(WebKit) 미검증」** 을 명시하고, review 가 아니라
   blocked 로 올린다 — 여는 조건은 「사람이 Safari 에서 확인」이다.

태블릿 폭(768x1024·1024x768)은 WebKit 으로도 찍는다 — 그 태블릿이 곧 iPad 다.

## 손이 얹힌 얼굴까지 찍는다 (REQ-20260830-043 2차 반려의 교훈)

`s9 shot` 은 정적이라 **:hover·:focus-visible·:active 가 캡처에 안 나온다** — 쉼
얼굴만 찍고 통과시킨 산출물이 hover 에서 글자를 파고들어 반려됐다. 인터랙션
피드백(반전·칠·링·확대)이 있는 컨트롤은:

- **실포인터로 얹어라**: Windows Chrome 을 `--remote-debugging-port` 로 띄우고
  CDP `Input.dispatchMouseEvent` 로 포인터를 대상 좌표에 올린 뒤 찍는다
  (stdlib 만으로 WebSocket 클라이언트를 짜서 가능 — 선례가 REQ-20260830-043 노트에
  있다). **CSS 를 복제해 hover 를 흉내 내지 마라** — 흉내 낸 규칙이 실제 캐스케이드와
  다르면 검증이 거짓이 된다. 키보드 얼굴은 CDP `Input.dispatchKeyEvent`(Tab)로.
- **픽셀은 2배로 재라**: `--force-device-scale-factor=2` 캡처에서 잰 값 ÷2 가
  css px 다. 1배 그림으로는 몇 px 어긋났는지 판정이 안 된다.
- **색을 가정하지 말고 차이로 찾아라**: hover 전/후 두 캡처의 화소 차이로 피드백의
  경계를 찾으면 스킨·톤과 무관하게 같은 자로 잴 수 있다.
- 잰 값은 잉크 기준으로 보고한다(상자 여백이 아니라 보이는 틈 — s9-design 2절).

## 배율은 정수만이 아니다 — 비정수 배율에서도 찍어라 (REQ-20260831-019/020)

CSS px 수치가 대칭이어도 사용자 화면은 다르게 그려질 수 있다: 실화면은 Windows
표시 배율(125/150%)로 렌더되고, 홀수 치수·소수 테두리(7px 상자·1.5px 선)는
비정수 배율에서 화소 반올림이 위/아래·왼/오 서로 다르게 갈린다. DPR 1(또는
정수 2배)만 잰 "대칭 3.0px 균등"이 사용자 눈의 비대칭으로 반려된 실제 사고.

- 정밀 기하(대칭·중심·정렬)를 판정할 때는 `--force-device-scale-factor` 또는
  CDP `Emulation.setDeviceMetricsOverride` 로 **1 · 1.25 · 1.5 세 배율**에서 찍어라.
- **수치는 눈의 보조지 대체가 아니다**: 잰 값과 별도로, 캡처를 확대해 실제 렌더
  화소를 **직접 눈으로 보고** 판정하고, 판정 근거 캡처를 문서에 남겨라.
- 비정수 배율에서 갈리면 잣대를 늘리지 말고 **기하를 고쳐라** — 배율 불변 설계는
  s9-design 「배율 불변」 절이 기준이다.

## 보고

수행한 조작 목록, 각 단계 스크린샷(또는 관찰), 발견한 시각/동작 결함, 사용한 검증 수단,
미검증으로 남긴 부분을 명시한다. "코드상 문제없음"만으로 UI 완료를 선언하지 않는다.

### 캡처는 경로가 아니라 그림으로 남긴다 (REQ-20260827-028)

노트에 `\\wsl.localhost\...\shots\` 같은 **경로를 문자열로 적지 마라.** 판정을 청하면서
증거는 상대가 직접 열게 만드는 짓이고, 실제로 그렇게 올라간 판정 요청이 방치됐다.

    ~/section9/bin/s9 note <REQ> --label response '확인 포인트…' \
        --attach <캡처.png> [--attach <또 하나.png>]

첨부는 문서 옆 `assets/<문서ID>/` 로 옮겨지고, 문서 화면이 그 자리에 **그림으로 그린다**
(문서 가시성을 그대로 물려받는다 — 문서를 못 여는 사람은 그림도 못 본다). 이미지가
아닌 파일은 📎 칩으로 붙고 본문이 검색에 걸린다.

`s9 status <REQ> review --note '...'` 의 노트에는 **확인 포인트만** 쓴다 — 그림은 위
`s9 note` 로 이미 문서에 붙어 있다.

### 확인 포인트는 300자 · 갈래 3개까지 (REQ-20260829-009)

넘으면 전이가 거부된다(예외는 `--force`). 화면 작업의 확인 포인트가 특히 길어진다 —
현상·원인·비유·고친 것 넷·확인 절차 여섯·색 판단·캡처 목록·곁가지까지 한 문단에 들어가
카드에서 잘렸고, 사용자는 판정을 하러 왔다가 본문으로 들어가 읽었다.

**네 문장이면 된다**: 무엇이 달라졌나 / 무엇에 빗댈 수 있나(생략 가능) / 어디서 무엇을
눌러 보나(F5·서버 재시작 같은 선행 조작 포함) / 무엇이 보이면 승인이고 무엇이 보이면
반려인가. **스킨·톤·밀도 전수 확인, 캡처 파일 이름, 곁가지 수정, 실패한 무관 테스트는
확인 포인트가 아니다** — 그건 위의 `--label response` 노트가 맡는다. 눌러서 판정할 수 없고
기계로 확인되는 것(키보드 도달·대비·테스트)은 애초에 사람에게 올리지 말고 직접 닫아라.

    # 982자 5갈래로 잘리던 것을 232자로 (REQ-20260828-041 실사례)
    멈춰 있던 카드에 `깨우기` 단추가 생겼습니다. 먼저 `bin/s9 serve --restart` 로 서버를
    다시 띄우고, Board 탭 IN-PROGRESS 열에서 `멈춤 …` 줄이 붙은 카드의 `깨우기` 를 눌러
    보세요. 깨워지면 점이 주황으로 바뀌고 멈춤 줄이 사라집니다. 못 깨운 이유(이미 붙어
    있음·한도 소진·아직 안 멈춤)가 붉은색 오류 창으로 뜨면 반려해 주세요 — 고장이 아니라
    보통 창이어야 합니다.
