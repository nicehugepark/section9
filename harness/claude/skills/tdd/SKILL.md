# TDD (개발 직군 필수)

개발/구현 작업은 **테스트를 먼저** 쓴다. Red → Green → Refactor. 예외 없다.

## 착수 전: TDD 시나리오를 REQ 문서에 작성 (필수)

구현/개발 요청을 받으면 코드를 건드리기 전에, 그 요청의 **완료를 정의하는 테스트
시나리오**를 요청 문서(REQ)에 기록한다. 이것이 사람이 "요청이 어디까지 구현됐는지"
커버리지를 확인하는 근거가 된다.

```
s9 note <REQ-id> --label tdd "
## TDD 시나리오
- [ ] S1. <정상 케이스>: 주어진 <입력> → 기대 <출력/상태>
- [ ] S2. <경계>: 빈/0/최대/유니코드 …
- [ ] S3. <실패 경로>: 잘못된 <입력>이 <올바른 방식으로 거부>
- [ ] S4. <회귀>: <고친 버그>가 재발하지 않음
"
```

- 각 시나리오는 **검증 가능한 문장**으로. "잘 동작한다"는 시나리오가 아니다.
- 요청의 모든 AC(완료 조건)가 최소 하나의 시나리오로 커버되는지 확인한다.
- 구현이 진행되며 통과한 시나리오는 `- [x]` 로 갱신(`s9 note` 로 상태 추가 기록) →
  문서만 봐도 커버리지가 보인다.

## 사이클

1. **Red**: 시나리오 하나를 실패하는 테스트로 작성하고, 실제로 실패함을 확인(실행 출력 첨부).
2. **Green**: 그 테스트만 통과시키는 최소 구현. 과하게 만들지 않는다.
3. **Refactor**: 테스트 초록 상태를 유지하며 정리. 매 리팩터 후 재실행.
4. 다음 시나리오로 반복. 모든 시나리오가 초록이면 구현 완료.

## 완료 보고

통과한 시나리오 목록(S1~Sn 체크), 실행 명령과 출력, 커버 못한 시나리오와 이유.
"미구현 시나리오를 침묵으로 넘기지 않는다."

## section9 관련 구현의 테스트

`S9_ROOT=$(mktemp -d)` 격리 필수 — 라이브 vault를 오염시키지 않는다. UI 구현이면
`browser-verify` 스킬의 실브라우저 검증(WSL이면 `s9 shot`)까지가 Green 조건이다.

## 빠른 시험 규칙 (REQ-20260830-027 — 일회성이 아니라 앞으로 모든 시험의 기준)

전체 스위트는 병렬(--jobs)로 도는 구조다. 새 시험은 그 구조를 깨지 않아야 하고,
그 자체로 빨라야 한다. 실측 근거: 느린 것은 로직이 아니라 **프로세스 기동**이다
(s9 subprocess 1회 0.15~0.18초 × 수천 회 = 직렬 523초).

- **s9 subprocess 를 아껴라**: setUp 마다 init+new 를 반복하지 말고 setUpClass 로
  한 번, 판정은 CLI 왕복 대신 모듈 로드(SourceFileLoader) 후 함수 직접 호출로.
- **sleep 폴링 금지**: 고정 sleep 대신 조건 대기(짧은 간격 폴 + 타임아웃).
  실서버 기동은 클래스당 1회를 넘기지 마라.
- **병렬 안전이 기본**: 임시 루트(tmproot 가 자동)와 portpool 밖의 전역 자원
  (실제 repo state/·고정 포트·환경변수)을 만지면 그 파일은 러너의 SERIAL
  목록(tests/__main__.py)에 올려야 한다 — 올리는 순간 전체 실행의 직렬 꼬리가
  길어지니 애초에 안 만지는 설계가 우선이다. 물려받은 환경(S9_TESTS_NESTED 등)에
  기대지 말고 setUp 에서 정리하라.
- **실행 습관**: 개발 중 `python3 tests/ --changed`(변경에 닿는 것만) 또는 표적
  패턴, review/done 전 전체는 `python3 tests/ --jobs 8`. 종료 코드는 파이프에
  가리지 말고 실측하라(`; echo exit=$?`).
