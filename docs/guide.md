# section9 사용자 가이드

verified 2026-08-24 · Settings › 저장소 verified 2026-09-02 · dashboard http://127.0.0.1:9909 · 캡처는 실제 화면(개발 인스턴스)    

## 1. section9이 뭔가요

터미널에서 Claude Code에게 일을 시키면, 모든 요청이 자동으로 카드가 되어 기록됩니다. 대시보드에서 그 카드들의 진행 상황을 실시간으로 보고, 완료된 작업을 승인하거나 반려해서 조종합니다. 즉 section9은 AI 작업의 **외부기억(모든 것이 문서로 남음)**이자 **관제탑(보고 판정하는 화면)**입니다.

여러분이 할 일은 두 가지뿐입니다 — 터미널에서 평소처럼 일을 시키는 것, 그리고 가끔 대시보드를 열어 확인 대기 중인 카드를 판정하는 것. 기록·상태 관리·재작업은 시스템이 알아서 합니다.

## 2. 최초 설치

출발점은 **관리자가 알려 준 팀 저장소(인스턴스 저장소) URL**입니다 — 예: `git@github.com:your-org/your-org-work.git`. 필요한 코드는 그 안에 전부 들어 있으므로, 그 하나만 받으면 됩니다. 새 머신(또는 새 계정)에서 다섯 단계면 끝납니다. 관리자가 이미 설치해 둔 환경이라면 4·5단계만 확인하시면 됩니다.

이 가이드의 예시는 clone 위치를 `~/your-org-work` 로 통일합니다. 실제로는 아무 경로나 됩니다 — clone 한 그 디렉토리가 곧 여러분 팀의 작업 공간이 됩니다.

0 **선행 조건 — Claude Code CLI** 

section9은 Claude Code 위에서 동작합니다. 아직 없다면 먼저 설치하세요. **로그인은 지금 하지 않아도 됩니다** — 5장의 `s9 code` 를 처음 실행할 때 로그인 화면이 자연스럽게 뜨고, 안내대로 로그인하면 그대로 세션이 시작됩니다.

```
npm install -g @anthropic-ai/claude-code   # 또는 공식 네이티브 인스톨러
```

1 **팀 저장소를 받습니다** 

관리자에게 받은 인스턴스 저장소 URL을 clone 합니다. 위치는 자유입니다(예시는 `~/your-org-work`).

```
git clone git@github.com:your-org/your-org-work.git ~/your-org-work
```

2 **설치 스크립트를 실행합니다** 

Claude Code 훅(자동 기록 장치)·스킬·역할 에이전트를 설치하고, **대시보드 서버가 자동으로 기동됩니다.**

```
cd ~/your-org-work && bin/s9-install
```

Windows(WSL 아님)에서는 `bin\s9-install.cmd` 를 실행합니다.

3 **Claude Code 세션을 재시작합니다** 

스킬과 역할 에이전트는 세션 시작 시 로드되므로, 열려 있던 세션은 한 번 껐다 켭니다. 켜는 방법은 터미널에서 `~/your-org-work/bin/s9 code` 실행 — 자세한 사용법은 5장 '터미널에서 Claude Code 쓰기'를 보세요.

4 **브라우저에서 대시보드를 엽니다** 

```
http://127.0.0.1:9909
```

5 **사용자를 등록합니다** 

```
~/your-org-work/bin/s9 user add <이름>
```

대시보드는 **서버를 띄운 OS 계정으로 나를 자동 인식**합니다 — 고를 것이 없습니다. 우상단에 **이름 @ 머신 [역할]** 라벨이 표시되고, 승인/반려가 이 이름으로 기록됩니다. 미등록 계정이면 라벨 자리에 등록 안내가 뜹니다. OS 계정명과 다른 이름으로 등록했다면 `~/your-org-work/bin/s9 user attach <이름>` 으로 한 번만 연결하세요.

**서버가 꺼져도 걱정 없습니다.** 대시보드 서버는 머신을 재부팅하는 등으로 꺼져 있어도, 다음 Claude Code 세션이 시작될 때 자동으로 되살아납니다. 수동으로 띄우려면 `~/your-org-work/bin/s9 serve`. **동료와의 공유는 git입니다.** 카드·문서·프로젝트 자료는 전부 이 디렉토리 안의 파일이고, `git push` / `git pull` 로 팀 저장소와 오갑니다 (시스템이 스스로 push하지는 않습니다). 저장소를 만들고 운영하는 쪽 이야기는 8장 '운영(관리자)'에 있습니다 — 팀원은 몰라도 됩니다. 

## 3. 3분 개념 — 카드 하나의 일생

터미널에 입력한 요청 하나가 어떻게 흘러가는지만 이해하면 전부 이해한 것입니다.

터미널 프롬프트 "결제 모듈 구현해줘"  자동 기록    REQ 카드 open — 접수  착수     in-progress 작업 중 · 녹색 점멸=실작업  완료 보고    review 사람의 판정 대기   ✓ 승인   done 완료   ↺ 반려 — 사유를 적어 되돌림 ~30초 내 백그라운드 작업이 떠서 반려 사유를 반영하고 다시 review로 올림  ⛔ blocked = 다른 작업 완료 대기 (사유가 카드에 표시)     
- **프롬프트 → 카드.** 터미널에서 일을 시키면 그 즉시 REQ 카드가 open 상태로 만들어집니다. 여러분이 따로 등록할 것은 없습니다. 
- **착수.** AI가 작업을 시작하면 in-progress로 바뀝니다. 카드의  녹색 점멸은 "지금 실제로 작업이 돌고 있음"이라는 실시간 신호입니다. 
- **사람 판정.** 방향 확인이 필요한 작업은 review로 올라옵니다. 카드의 **✓ 승인**을 누르면 done, **↺ 반려**를 누르고 사유를 적으면 다시 작업으로 돌아갑니다. 
- **반려하면 저절로 다시 합니다.** 약 30초 안에 백그라운드 작업이 떠서, 적어 주신 반려 사유를 반영해 다시 review로 올립니다. 자리를 지키고 있을 필요가 없습니다. 

### 카드 위의 실시간 신호 읽기

in-progress 카드 왼쪽의 점(dot)은 "문서상 진행 중"이 아니라 **지금 이 순간의 실제 동작**을 나타냅니다.

점의미해석  녹색 점멸일하는 중 · 기록도 나감이 요청을 맡은 것이 2분 내에 실제로 움직였고, 문서에도 적히고 있습니다. 가장 확실한 신호.  초록 링 + 심일하는 중 · 기록은 아직붙어서 돌고는 있는데 문서에 아직 적힌 것이 없습니다. 숨이 한 박자 느린 것이 그 뜻입니다 — 기다리면 위 녹색으로 바뀝니다.  초록 링살아는 있으나 아직 안 맡음두 가지가 이 얼굴을 씁니다 — 이 요청을 만든 창이 다른 일을 하는 중이거나, 백그라운드 작업이 막 떠서 아직 문서를 집기 전이거나. 둘 다 여러분이 할 일은 같습니다: 잠깐 기다립니다. 어느 쪽인지는 점에 손을 얹으면 나옵니다.  속 빈 사각멈춤붙어 있는 것도 없고 문서도 한동안 그대로입니다. 카드의 **▶ 이어가기**로 멈춘 자리에서 이어받게 할 수 있습니다.  채운 사각맡았던 것이 멎음이 요청을 맡았던 작업이 도중에 죽었습니다. 까닭이 남아 있으면 점에 손을 얹었을 때 함께 보입니다.  줄 그은 사각사람이 중단해 둠사람이 손으로 중단해 둔 요청입니다 — 사고가 아니라 뜻입니다. **▶ 이어가기**를 누르기 전에는 저절로 이어지지 않습니다.  작은 회색 링모름진행 중으로 기록돼 있지만 신호가 없습니다. 방치된 것일 수 있으니 눈여겨보세요. 

모양이 「무엇이 붙어 있나」, 채움이 「기록이 나가고 있나」를 말합니다 — 색은 둘째 신호라, 색을 못 보는 눈에도 일곱이 그대로 갈립니다.

진행 중인 요청에 담당이 없으면, 서버가 백그라운드 작업을 띄우고 그 작업이 요청을 이어받습니다 — 요청은 여러분이 자리를 비워도 멈추지 않습니다. 요청마다 이것을 꺼 둘 수 있습니다: 문서 화면 맨 위의 **자동 이어받기 끄기**를 누르면 **▶ 이어가기**를 누를 때까지 이어지지 않습니다.

### TDD 배지와 blocked 표시

- TDD 3/5 — 검증 커버리지입니다. 이 작업이 스스로 세운 검증 시나리오 5개 중 3개를 통과했다는 뜻. TDD 5/5 초록이 되면 객관적 검증이 끝난 것입니다. **반려하면 시나리오가 개정되어 0부터 다시 채워집니다** — 숫자가 줄어든 것처럼 보여도 정상입니다. 
- **⛔ 대기 사유** — blocked 카드에는 "무엇을 기다리는지"가 그대로 표시됩니다. 기다리던 작업이 done이 되면 자동으로 풀립니다. 

## 4. 화면별 기능

대시보드는 여섯 개 탭으로 구성됩니다. 상단 필터(검색·user·project·tag·type)는 모든 탭에 공통으로 적용됩니다.

### Board kanban

![Board 탭 — 상태별 칸반 컬럼과 카드](guide-assets/01.png)

Board — 상태별 컬럼. in-progress의 녹색 점멸, TDD 배지, blocked의 ⛔ 사유, review 카드의 승인/반려 버튼

- 상태별 컬럼(open → in-progress → blocked → review → done)에 요청 카드가 놓입니다. 
- **review 카드에서 바로 판정합니다**: ✓ 승인 = done, ↺ 반려 = 사유를 적어 재작업. 카드에는 "무엇을 확인해 달라는지"(확인 포인트)가 보라색으로 표시됩니다. 
- 카드를 **드래그**해 다른 컬럼에 놓아도 상태가 바뀝니다 — 허용되는 전이 컬럼만 점선으로 표시됩니다. 
- 상단 **내 것만** 토글을 켜면 내가 멤버인 프로젝트의 문서만 남고, 그 위에 MY PROJECTS 스트립이 나타납니다. 

![내 것만 토글을 켠 Board](guide-assets/02.png)

내 것만 ON — MY PROJECTS 스트립과 내 프로젝트로 좁혀진 보드

### Docs 문서 목록 · 뷰어

![Docs 탭 — 요청 문서 뷰어와 스트림 터미널](guide-assets/03.png)

Docs — 요청 문서. 메타데이터 표, 상태 전이 버튼, TDD 체크리스트, 그리고 "이 요청의 스트림" 터미널

- 좌측 목록에서 문서를 고르면 우측에 전문이 열립니다. 모든 요청 문서는 **원문(Original) + 작업 기록(Notes) + 상태 이력(History)**의 완결된 기록입니다. 
- 문서 상단의 전이 버튼(→ done, → review …)으로 이 화면에서도 상태를 바꿀 수 있습니다. 
- 요청 문서 하단의 **"이 요청의 스트림"**을 펼치면, 이 요청을 처리한 터미널 구간이 그대로 재생됩니다 — AI가 실제로 무슨 명령을 치고 무슨 결과를 받았는지 확인할 수 있습니다. 
- 검색창 옆 **본문** 토글을 켜면 제목뿐 아니라 문서 본문 내용까지 검색됩니다. 

### Graph 관계도

![Graph 탭 — 문서 관계도와 병목 표시](guide-assets/04.png)

Graph — 문서 관계도. 앰버 호+숫자 = 미완료 파생 병목, 링 = 상태(점멸 in-progress · 실선 blocked · 점선 review)

- 문서 사이의 관계(부모-자식, 참조)를 별자리처럼 봅니다. 노드를 드래그하고, 휠로 줌하고, 클릭하면 그 문서가 열립니다. 
- **앰버 호(호+숫자)가 병목입니다**: 끝나지 않은 파생 작업 N건이 이 문서에 매달려 있다는 뜻. 호가 클수록 병목이 큽니다. 
- FORCE(물리 배치) / DAG(계층 배치) 토글로 시점을 바꿀 수 있습니다. 
- **프로젝트 단위로 보려면** 상단의 project 필터(또는 '내 것만' 토글)를 쓰면 됩니다 — Board·Docs·Graph가 같은 필터를 공유합니다. 
- 세션(로그) 노드는 기본으로 숨겨져 있습니다. 상단 범례의 `session`을 클릭하면 표시/숨김이 토글되고, request·knowledge도 같은 방식으로 끌 수 있습니다. 

### Audit 이벤트 타임라인

![Audit 탭 — 세션 이벤트 타임라인](guide-assets/05.png)

Audit — 모든 세션의 프롬프트/응답/질문 이벤트가 시간순으로

- "언제 누가 무엇을 시켰고 무엇이 돌아왔나"를 한 줄씩 최신순으로 보여줍니다. 카드가 되지 않은 단순 질문(QUESTION)도 여기에는 남습니다. 
- 이벤트 속 REQ ID를 클릭하면 해당 문서로 이동합니다. 

### Stream 세션 터미널 미러

![Stream 탭 — 세션 터미널 미러](guide-assets/06.png)

Stream — 세션 하나의 터미널 흐름. 진행 중이면 ● live + follow로 실시간 추적

- 세션을 고르면 그 세션의 터미널이 통째로 재생됩니다 — 사용자 발화(노랑), AI 응답, 도구 호출(⚒), 결과. 
- 진행 중인 세션은 **● live**가 붙고, follow를 켜 두면 턴 중간에도 실시간으로 따라갑니다. 

### Settings 계정 · 개인화 · 디스플레이

![Settings 디스플레이 — 스킨/톤/밀도](guide-assets/07.png)

Settings › 디스플레이 — skin 10종 × tone 6종 × density. 내 계정에 저장되어 기기 간 동기화

- **디스플레이** — 대시보드의 겉모습을 바꿉니다. skin(디자인 언어 10종: ledger·calm·soft·glass·terminal·grid·slate·cobalt·field·cork) × tone(색 6종) × density(밀도 2종)를 자유 조합. 등록 계정이면 자동으로 계정에 저장되어 어느 기기에서나 같은 모습입니다. 
- **내 계정** — 프로필(표시 이름·이메일)과 개인화 설정을 편집합니다. 
- **저장소** — 이 저장소와 GitHub 사이를 손으로 맞춥니다(**pull**·**push**). 바로 아래에서 따로 다룹니다. 
- **사용자 관리** — admin 전용. 등록·역할(admin/member/viewer) 관리와 **시점 미리보기**(다른 사용자의 화면을 그대로 확인). 

![Settings 내 계정 — 개인 선호 편집](guide-assets/08.png)

Settings › 내 계정 — 개인 선호(pref). 말투·보고 방식을 저장/수정/삭제, 매 턴 자동 반영

**개인 선호(pref)**가 특히 유용합니다. "반말로 짧게 보고" 같은 **말투·작업 방식 선호**를 저장해 두면 AI가 매 턴 자동으로 반영합니다. 여기서 직접 추가/수정/삭제해도 되고, 터미널에서 *"앞으로 반말로 해줘"*라고 말하면 자동으로 저장됩니다.

### Settings › 저장소 pull · push

이 저장소와 GitHub 사이를 **화면에서 손으로 맞추는** 판입니다. 지금까지는 터미널을 열어 `git pull`·`git push` 를 직접 쳐야 했고, 이 저장소가 GitHub 과 얼마나 벌어졌는지도 화면은 말해 주지 않았습니다. Settings 좌측 목록의 **저장소** 줄이 그 자리입니다.

**판을 열지 않아도 거리가 보입니다.** 좌측 목록의 **저장소** 줄 밑에 「push 할 것 2개 · pull 할 것 1개 · 고치던 파일 12개」가 부제로 붙기 때문입니다. 판을 열면 같은 셈이 큰 글씨로 서고, 그 왼쪽에 지금 어디에 서 있는지가 `main → origin/main` 으로 뜹니다.

- **push 할 것 N개** — 여기서 이미 commit 했는데 GitHub 에는 아직 없는 것. 
- **pull 할 것 N개** — GitHub 에 새로 올라왔는데 여기에는 아직 없는 것. 
- **고치던 파일 N개** — 아직 commit 하지 않은 편집. 파일 이름까지 펼쳐 볼 수 있습니다. 

**셈마다 나이가 다릅니다.** push 할 것과 고치던 파일은 이 컴퓨터 안에서만 세면 되므로 판이 열려 있는 동안 10초마다 다시 셉니다. pull 할 것은 GitHub 에 물어야 알 수 있어서 **저절로 묻지는 않습니다** — 며칠 열어 둔 화면이 30초마다 물으면 하루에 2,880번을 두드리게 됩니다. 사람이 **지금 확인**을 누를 때와 pull·push 앞뒤에만 묻고, 대신 나이를 숨기지 않습니다: 「GitHub 에는 5분 전에 물어봤습니다」. 한 번도 안 물어봤으면 그렇다고 적습니다.

**이 판이 하지 않는 일 셋.** ① 화면은 **commit 하지 않습니다** — 이미 commit 한 것만 push 합니다. ② 여기와 GitHub 이 각각 앞서 **갈래가 갈리면 합치지 않습니다** — 어떻게 합칠지는 사람이 정할 일입니다. ③ 고치던 파일을 **치워 두었다 되돌리지 않습니다** — 그 명령이 남의 미완성 작업을 지운 적이 있어서, 이 화면은 아예 부르지 못하게 짜여 있습니다. 단추 왼쪽의 회색 글자(`git pull --ff-only`·`git push`)가 화면이 실제로 돌리는 명령 전부입니다 — 숨은 강제 옵션도, 합치는 방식을 고르는 인자도 없습니다. 

**push 만 확인 창을 지납니다.** 무엇이 나가는지(짧은 해시와 제목)를 보여 주고 묻습니다. 한 번 나간 것은 다른 사람도 가져가므로 이 화면에서는 되돌릴 수 없기 때문입니다. pull 은 창 없이 바로 하고, 끝나면 「파일 N개가 바뀌었습니다」로 결과를 말합니다. 방금 오간 commit 목록은 그 밑에서 펼쳐 볼 수 있습니다.

### 단추가 잠기는 이유

잠긴 단추 옆에는 언제나 **왜 못 하는지가 한 줄로 서 있습니다** — 눌러 봐야 아는 화면을 만들지 않으려는 것입니다. 그 문장은 서버가 짓고, 누른 순간 서버가 같은 판정을 한 번 더 합니다. 그래서 단추 옆 사유와 실제 거절 사유가 갈리지 않습니다. 사유가 여럿 겹쳐도 **먼저 걸린 하나만** 보입니다.

pull·push 를 **둘 다 잠그는 사유는 일곱**입니다. 위에 있는 것이 먼저 걸립니다.

- **이 자리는 git 저장소가 아닙니다.** 팀 저장소를 clone 한 자리가 아니라 그냥 만든 디렉토리에 설치된 경우입니다 — 2장의 설치를 다시 보세요. 
- **GitHub 의 어느 갈래와도 짝지어 두지 않았습니다.** 터미널에서 `git push -u origin main` 을 **한 번** 해 두면 그다음부터는 화면에서 됩니다. 화면이 그 명령을 그대로 적어 줍니다. 
- **지금 @누구 시점으로 보는 중입니다.** admin 이 Settings › 사용자 관리의 **시점 미리보기**로 남의 화면을 보는 동안에는 둘 다 잠깁니다 — 저장소를 바꾸는 일은 남의 이름으로 하지 않습니다. 내 시점으로 돌아오면 열립니다. 
- **저장소를 바꾸는 일은 admin 만 합니다.** 거리를 읽는 것은 등록 사용자 모두 됩니다 — 잠기는 것은 단추 둘뿐입니다. 
- **여기와 GitHub 에 각각 새 commit 이 있습니다.** 갈래가 갈린 것입니다. 합치는 일은 화면이 하지 않으니, 터미널에서 `git pull --rebase` 로 맞춘 뒤 다시 오세요. 
- **지금 도는 일 N건이 있습니다.** 백그라운드 작업이 이 저장소의 파일을 아직 바꾸고 있습니다. 화면 오른쪽 위의 「도는 일 N건」과 같은 숫자입니다 — 끝나면 저절로 열립니다. 
- **GitHub 에 묻지 못했습니다.** 90초 안에 답이 없거나 연결이 안 될 때입니다. git 이 남긴 마지막 한 줄이 그대로 뜹니다. 잠시 뒤 **지금 확인**을 다시 눌러 보세요. 

여기에 더해, **한쪽만 잠기는 자리가 셋** 있습니다.

- **pull** — **고치던 파일이 N개 있습니다.** pull 하면 덮일 수 있어서, commit 한 뒤에 pull 할 수 있습니다. push 는 이것으로 막히지 않습니다 — 나가는 것은 이미 commit 한 것뿐이니까요. 
- **pull** — **pull 할 것이 없습니다.** GitHub 에 새로 올라온 것이 없다는 뜻입니다. 방금 확인한 것이 아니라면 **지금 확인**을 먼저 눌러 보세요. 
- **push** — **push 할 것이 없습니다.** commit 한 것이 있어야 push 합니다. 고치던 파일은 commit 하기 전까지 여기에 세지 않습니다.

project 필터 선택 시 — 프로젝트 정보 패널에서 멤버·권한·만료를 관리

**열람 격리**: 화면에 보이는 문서는 서버가 자동 인식한 내 계정에 따라 다릅니다. 일반 사용자는 자기가 멤버인 프로젝트의 문서(그리고 자기가 만든 문서)만 보이고, admin은 전체가 보입니다. 사람마다 목록이 다른 것은 고장이 아니라 이 격리가 동작하는 것입니다. admin은 Settings › 사용자 관리의 **시점 미리보기**로 다른 사용자의 화면을 그대로 확인할 수 있습니다.

## 5. 터미널에서 Claude Code 쓰기

### 먼저: Claude Code 실행하기 — `s9 code` 한 줄

터미널을 열고 아래 한 줄만 실행하면 됩니다. 어느 디렉토리에서 실행해도 됩니다.

```
~/your-org-work/bin/s9 code
```

`s9 code` 는 실행 전에 스스로 점검합니다 — **대시보드가 꺼져 있으면 켜고**, 훅이 설치돼 있지 않으면 **자동으로 설치**하고, 사용자가 등록돼 있지 않으면 이름을 물어 등록한 뒤, Claude Code를 인스턴스 디렉토리(`~/your-org-work`) 기준으로 띄웁니다(규약·스킬·역할 에이전트가 이 폴더에서 로드됩니다). **Claude에 로그인돼 있지 않아도 괜찮습니다** — 이어서 뜨는 화면에서 안내대로 로그인하면 그대로 세션이 시작됩니다.

권한 모드 등 claude 인자가 필요하면 뒤에 그대로 붙입니다: `s9 code --permission-mode acceptEdits`. 계정 기본값으로 저장하려면 `s9 user config <이름> s9code_args '--permission-mode acceptEdits'`. (직접 `cd ~/your-org-work && claude` 로 열어도 되지만, 위 자가 점검은 건너뜁니다.)

실행하면 프롬프트 입력창이 나옵니다. 특별한 명령어 없이 **평소 말하듯 한국어로** 입력하면 됩니다:

이렇게 치면이렇게 됩니다 *"결제 모듈에 환불 API 추가해줘"*REQ 카드가 자동 생성되고(화면에 기록 안내가 뜹니다), 착수→완료까지 대시보드에서 추적됩니다 *"이 함수는 왜 이렇게 짰어?"*질문으로 분류 — 카드 없이 답만 받습니다 *"앞으로 보고는 세 줄 이내로 해줘"*개인 선호로 저장 — 다음 턴부터 계속 적용됩니다 

세션을 끝내려면 `Ctrl+C` 또는 `/exit`, 다시 시작하려면 `s9 code` — 시작할 때 진행 중 작업 요약(digest)을 자동으로 넘겨받으므로 "아까 어디까지 했지?"를 물을 필요가 없습니다. WSL 사용자는 Windows 터미널에서 WSL 셸에 들어온 뒤 실행합니다.

**그다음은, 그냥 일을 시키면 됩니다.** section9을 의식하고 쓸 것은 아무것도 없습니다.

- **요청은 자동으로 기록·추적됩니다.** "결제 모듈 구현해줘"라고 치는 순간 카드가 생기고, 착수·완료 보고까지 문서에 자동으로 쌓입니다. 
- **질문이나 짧은 말은 카드가 되지 않습니다.** "이 함수 뭐 하는 거야?", "ㅇㅋ" 같은 것은 세션 로그에만 남아 보드를 어지럽히지 않습니다. 
- **선호는 말로 저장됩니다.** "앞으로 반말로 해줘", "보고는 세 줄 이내로" — 이런 말은 개인 선호로 자동 저장되어 다음 턴부터, 그리고 다음 세션에서도 계속 적용됩니다. 
- **반려 후 자리를 비워도 됩니다.** 대시보드에서 반려하면 백그라운드 작업이 반려 사유를 읽고 알아서 재작업합니다. 
- **새 세션을 열어도 이어집니다.** 어제 하던 작업이 궁금하면 새 세션에서 그냥 이어서 시키면 됩니다 — 세션이 시작될 때 진행 중 작업 요약(digest)을 자동으로 넘겨받습니다. 

### 알아 두면 좋은 CLI 다섯 가지

전부 선택 사항입니다. 대시보드로도 같은 것을 볼 수 있습니다. (`~/your-org-work/bin/s9`, PATH에 넣어 두면 `s9`)

명령용도 `s9 digest`지금 진행 중인 작업의 전체 요약 — "어디까지 됐지?"의 답 `s9 ls --status in-progress`상태·사용자별 요청 목록 (`--user`, `--project` 조합 가능) `s9 show REQ-20260824-001`요청 문서 하나의 전문 — 원문·작업 기록·이력 `s9 search 결제 --body`본문까지 포함한 키워드 검색 `s9 blocked`대기 중인 요청과 대기 사유 일람 

## 6. FAQ

일을 시켰는데 카드가 안 생겨요. 질문("이거 왜 그래?")이나 짧은 파편("ㅇㅋ", "좋아")은 의도적으로 카드를 만들지 않습니다 — 세션 로그(Audit 탭)에는 남습니다. 요청인데 질문으로 잘못 분류된 경우에도 AI가 대화 중에 스스로 정정해 카드를 만듭니다. 명령형으로("~해줘", "~구현해") 말하면 확실하게 카드가 됩니다. in-progress인데 녹색 점멸이 안 떠요. 점은 문서 상태가 아니라 실시간 동작 신호입니다. 초록 링이면 아직 이 요청을 맡기 전(다른 일을 하는 창이거나, 막 뜬 백그라운드 작업), 작은 회색 링이면 최근 2분간 아무 신호가 없는 것입니다. 회색이 오래 가면 그 세션에 말을 걸거나 새 세션에서 이어받으세요 — 자동으로 이어집니다. blocked는 언제 풀리나요? 카드의 ⛔ 줄이 무엇을 기다리는지 알려줍니다. 기다리던 요청이 done이 되면 자동으로 해제됩니다. 지금 무엇이 왜 막혀 있는지는 `s9 blocked` 또는 Board의 blocked 컬럼에서 한눈에 봅니다. TDD 숫자가 5/5였는데 0/6으로 줄었어요. 반려하면 검증 시나리오가 반려 사유를 반영해 개정되고, 카운터는 새 시나리오 기준으로 0부터 다시 채워집니다. 숫자가 준 것이 아니라 검증을 새로 시작한 것입니다. 문서가 안 열려요 / 화면이 이상해요. 문서 뷰어의 **다시 시도** 버튼을 누르거나 브라우저를 새로고침하세요. 대시보드는 매 요청마다 파일을 다시 읽으므로 새로고침이 곧 최신 상태입니다. 대시보드 서버가 꺼졌어요. 다음 Claude Code 세션이 시작될 때 자동으로 되살아납니다. 지금 바로 필요하면 `~/your-org-work/bin/s9 serve` 로 수동 기동하세요 (기본 포트 9909). 사람마다 보이는 문서가 달라요. 정상입니다. 서버가 자동 인식한 계정 기준으로 열람이 격리됩니다 — 일반 사용자는 자기 프로젝트의 문서만, admin은 전체를 봅니다. 보여야 할 문서가 안 보이면 프로젝트 멤버로 추가되었는지(프로젝트 정보 패널) 확인하세요. 우상단에 "미등록 계정" 경고가 떠요. 이 OS 계정이 아직 등록되지 않았습니다. 터미널에서 `~/your-org-work/bin/s9 user add <이름>` 으로 등록하세요. 이미 다른 이름으로 등록해 둔 계정이 있다면 `s9 user attach <이름>` 으로 현재 OS 계정을 그 계정에 연결하면 됩니다. 반려했는데 아무 일도 안 일어나요. 이것은 계정별 설정입니다 — Settings 의 「백그라운드 작업」에서 「맡기기」를 켭니다 (터미널에서는 `s9 user config <이름> auto_resume on`). 꺼져 있어도 잃는 것은 없습니다: 반려된 요청은 그 세션에 다음 프롬프트가 입력되는 순간, 또는 새 세션이 시작되는 순간 최우선으로 자동 재개됩니다. 

## 7. 프로젝트 — 일을 묶고 격리하기

카드가 쌓이기 시작하면 "결제 건", "사내 도구 건"처럼 **일감 단위로 묶고 싶어집니다**. 프로젝트가 그 묶음입니다 — 요청·문서·화면을 프로젝트 단위로 모아 보고, **멤버가 아닌 사람에게는 그 프로젝트의 문서가 아예 보이지 않게** 격리합니다.

4장의 '프로젝트 정보 패널과 열람 격리'가 바로 이 기능의 화면입니다. 이 장에서는 만드는 것부터 운영까지 순서대로 다룹니다. 프로젝트는 어디까지나 인스턴스(팀 저장소) **안**의 묶음입니다 — 보안 경계 자체가 다른 조직·고객이라면 프로젝트가 아니라 인스턴스를 분리(8장)하는 것이 맞습니다.

### 프로젝트 만들기

터미널에서 한 줄이면 됩니다 (예시는 `pay` 라는 이름의 결제 프로젝트):

```
~/your-org-work/bin/s9 project add pay --name "결제 시스템"
```

이렇게 출력되면 성공입니다:

```
PRJ-20260824-002  (pay)  owner=sjpark1
  ↳ 에셋 공간: projects/pay/ — CONTEXT.md(진입점) + assets/
```

- **만든 사람이 자동으로 owner**가 됩니다. 
- `pay` 자리가 **slug**(프로젝트의 짧은 식별자)입니다 — 영문·숫자·`._-` 만 쓸 수 있고, 이후 필터·명령 어디서나 이 이름으로 부릅니다. 
- 두 가지가 함께 생깁니다: **PRJ 문서**(멤버·이력이 기록되는 관리 문서)와 **파일 공간** `projects/pay/` (아래에서 설명). 

### 요청을 프로젝트에 넣기

터미널에서 일을 시킬 때 *"이건 pay 프로젝트 건이야"*처럼 프로젝트를 밝히면, AI가 카드를 기록하면서 그 프로젝트로 귀속시킵니다. 직접 넣을 때는 `--project` 를 씁니다:

```
~/your-org-work/bin/s9 new request --title "환불 API 추가" --project pay --size M --body "..."
```

프로젝트로 귀속된 요청이 접수되면 그 프로젝트의 **CONTEXT.md가 세션에 자동 주입**됩니다 — 배경 설명을 매번 반복하지 않아도 AI가 프로젝트 맥락을 알고 시작한다는 뜻입니다.

### 멤버와 역할

![Docs 탭 — 프로젝트 정보 패널의 인라인 멤버 관리](guide-assets/10.png)

Docs — project 필터 선택 시 목록 위에 열리는 프로젝트 정보 패널. 역할 셀렉트·직무·만료일·+ 추가 / − 제거를 이 자리에서 바로

대시보드 상단의 **project 필터**에서 프로젝트를 고르면 **프로젝트 정보 패널**이 열립니다 (Board·Docs·Graph 어느 탭에서든). 멤버 추가·역할 변경·만료일·제거를 전부 이 패널에서 인라인으로 합니다 — 맨 아랫줄에서 사용자와 역할을 고르고 **+ 추가**.

역할은 네 가지이고, 위로 갈수록 할 수 있는 일이 늘어납니다:

역할할 수 있는 일 `viewer`열람만 `contributor`+ 기여 — 이 프로젝트로 요청·문서를 만들 수 있음 (새 멤버의 기본 역할) `maintainer`+ 관리 — 프로젝트 설정 변경, 멤버 추가·제거·역할 변경 `owner`+ 소유 — owner 지정·변경까지. 프로젝트의 최종 책임자 

패널의 **직무**(PM·개발자 등)는 권한과 무관한 표시용 자유 텍스트이고, **만료**일을 지정하면 그 날짜가 지난 멤버는 자동으로 비활성됩니다(문서에서 사라져 보임). 터미널로도 같은 일을 할 수 있습니다: `~/your-org-work/bin/s9 project member pay add bob --role maintainer`

### 프로젝트 공간 — projects/<slug>/

프로젝트를 만들면 생기는 파일 공간입니다. 규약은 딱 세 자리입니다:

위치무엇을 넣는 곳인가 `CONTEXT.md`프로젝트의 배경·용어·핵심 링크를 담는 **단일 진입점**. 요청 접수 시 세션에 자동 주입되므로, 여기만 잘 관리하면 AI가 늘 맥락을 갖고 시작합니다 `assets/`작업 재료 — 스펙, 계약서, 회의록, 데이터 샘플, 외부 API 문서 등 (하위 구조 자유) `agents/`이 프로젝트 전용 AI 에이전트 정의 (`*.md`, 바로 아래에서 설명) 

### 프로젝트 에이전트

`projects/<slug>/agents/` 에 에이전트 정의 md 파일을 넣어 두면, **다음 Claude Code 세션이 시작될 때 자동으로 동기화**되어 그 프로젝트 전용 역할 에이전트(`<slug>--이름`)로 쓸 수 있게 됩니다. 세션 도중에 넣은 파일은 **다음 세션부터** 보입니다.

- **`agents/worker.md` 는 특별합니다** — 반려 뒤 백그라운드 작업이 뜰 때, 이 파일이 그 프롬프트 봉투로 자동 주입됩니다. "우리 프로젝트의 재작업은 이런 규칙으로 해라"를 적어 두는 자리입니다. 
- 지금 상태 확인·즉시 동기화: `~/your-org-work/bin/s9 project agents ls` / `sync` 

### 화면에서 프로젝트 단위로 보기

![Board 탭 — 상단 project 필터로 프로젝트 선택](guide-assets/11.png)

Board — 상단 project 필터에서 프로젝트를 고른 모습. 정보 패널이 열리고 보드가 그 프로젝트의 카드로만 좁혀진다

![Graph 탭 — project 필터로 좁힌 관계도](guide-assets/12.png)

Graph — 같은 필터가 관계도에도 적용된다. 프로젝트 하나의 문서들만 별자리로

- 상단 **project 필터는 Board·Docs·Graph 공통**입니다 — 한 번 고르면 탭을 오가도 유지됩니다. 
- 주소에 `?project=pay` 를 붙여 열면 처음부터 그 프로젝트로 필터된 화면이 열립니다 — 동료에게 링크로 공유할 때 편리합니다. 
- **내 것만** 토글은 "내가 멤버인 모든 프로젝트"로 좁히는 단축 버튼입니다. 

### 하지 말아야 할 것

**assets/ 에 비밀정보를 넣지 마세요.** 비밀번호·API 키·자격증명·고객 개인정보는 금물입니다 — 이 공간은 프로젝트 멤버 전원과 AI 세션이 읽는 공유 재료함이고, 파일 자체가 암호화되지는 않습니다. 열람 격리는 대시보드 화면 기준의 가드레일이지 금고가 아닙니다. **마지막 owner를 제거·강등하려고 하지 마세요.** 어차피 차단됩니다 — *"마지막 owner는 제거할 수 없다 (다른 owner를 먼저 지정하라)"*. 인수인계할 때는 새 owner를 먼저 지정한 뒤에 기존 owner를 내리면 됩니다. 

## 8. 운영(관리자) — 인스턴스 만들기와 배포

이 장의 독자는 **팀 저장소를 만들고 관리하는 사람**입니다. 1~7장으로 충분한 일반 팀원은 읽지 않아도 됩니다.

section9은 두 종류의 저장소로 운영합니다. 팀원에게는 인스턴스 하나만 알려 주면 됩니다 — 코드는 이미 그 안에 들어 있습니다.

저장소무엇인가누가 아는가 **upstream** = section9프레임워크(하네스 코드만: bin·web·harness·docs). 개선은 여기서만 일어납니다관리자·하네스 개발자 **인스턴스** = 팀 저장소작업 공간(사설). 데이터(vault·users·projects·streams)를 track하고, 코드는 upstream에서 merge 로 받습니다모든 팀원 

인스턴스는 remote 를 둘 가집니다: `origin`(팀 사설 저장소, push/pull 대상) + `upstream`(section9, 하네스 업그레이드 수신용).

### 인스턴스 만들기 — `s9 instance init` 한 번

관리자 머신의 section9 카피(예: `~/section9`)에서 실행합니다. 사설 저장소 URL 하나만 주면 clone → remote 구성 → 데이터 track 전환 → 초기 commit → push 까지 자동입니다.

```
cd ~/section9 && bin/s9 instance init git@github.com:your-org/your-org-work.git
```

실제 출력입니다 (경로·URL은 각자 환경에 따라 다르게 표시됩니다):

```
① 베이스 clone: /home/admin/section9 → /home/admin/your-org-work
② remote: upstream=git@github.com:your-org/section9.git  origin=git@github.com:your-org/your-org-work.git
③ 데이터 track 전환 + 초기 commit 완료
⑤ push 실패 — 원격 저장소가 아직 없을 가능성이 크다. 절차:
  1. https://github.com/new 에서 저장소 생성 — 이름 your-org-work, Private,
     'Add a README/.gitignore/license' 전부 체크하지 말 것
  2. 서버측 보호(코어 경로): Settings > Branches > main 보호 규칙 +
     .github/CODEOWNERS 의 @OWNER 를 admin 계정으로 교체
  3. 다시 push: cd /home/admin/your-org-work && git push -u origin main

다음 단계(사용 시작):
  cd /home/admin/your-org-work && bin/s9-install    # 이 머신의 훅·스킬 설치(멱등)
  bin/s9 code                          # 세션 시작 — 이후 평소처럼 프롬프트
팀원 합류: git clone git@github.com:your-org/your-org-work.git 후 위 두 줄과 동일.
업그레이드(관리자): cd /home/admin/your-org-work && git fetch upstream && git merge upstream/main && git push
```

- ⑤의 "push 실패"는 원격 사설 저장소를 아직 안 만든 첫 실행의 정상 경로입니다 — 출력이 알려 주는 세 단계대로 저장소를 만들고 다시 push하면 끝. 
- `gh` CLI가 설치돼 있다면 `--create` 를 붙여 사설 저장소 생성까지 한 번에 할 수 있습니다. 
- clone 위치를 바꾸려면 `--dir <경로>` (기본은 `~/<저장소이름>`). 

### 팀원 초대

인스턴스 저장소 URL과 아래 세 줄만 전달하면 됩니다 (2장과 같은 내용입니다):

```
git clone git@github.com:your-org/your-org-work.git ~/your-org-work
cd ~/your-org-work && bin/s9-install
bin/s9 code
```

팀원이 사설 저장소에 접근할 수 있도록 GitHub에서 collaborator(또는 팀)로 추가하는 것을 잊지 마세요.

### 하네스 업그레이드 배포

upstream(section9)에 개선이 올라오면, 관리자가 인스턴스에서 세 명령으로 배포합니다:

```
cd ~/your-org-work
git fetch upstream && git merge upstream/main
git push
```

**팀원은 `git pull` 만 하면 됩니다.** pull 후에는 post-merge 훅이 `s9 index rebuild` 와 `s9-install --quiet` 를 자동 실행해 인덱스·훅·스킬·에이전트까지 최신으로 맞춥니다 — 팀원이 따로 할 일은 없습니다.

### 보호 설정 — 코어 경로를 팀원이 못 고치게

인스턴스에서 하네스 코드(`bin/`·`web/`·`harness/`·`.github/`·`.gitignore`)가 수정되면 upstream merge 가 깨끗하지 않게 됩니다. 두 겹으로 막습니다:

- **로컬 1차 — pre-commit 가드**: `s9-install` 이 설치하는 pre-commit 훅(s9-guard)이 admin이 아닌 commit의 코어 경로 변경을 차단합니다. 
- **서버측 최종 — CODEOWNERS + branch protection**: 저장소의 `.github/CODEOWNERS` 에서 `@OWNER` 를 실제 admin GitHub 계정(또는 팀)으로 교체하고, Settings › Branches › main 에 보호 규칙을 추가합니다 — "Require a pull request before merging" + "Require review from Code Owners". 이러면 코어 경로 변경은 admin 승인 없이 main에 들어갈 수 없습니다. 

### 충돌 시 대처 — upstream cherry-pick 원칙

upstream merge 가 늘 깨끗한 이유는 교집합이 없기 때문입니다: 데이터 파일은 upstream에 없고, 코어 파일은 인스턴스에서 수정하지 않습니다. 이 원칙이 깨졌을 때의 대처는 하나입니다:

- **하네스 결함을 발견하면** 인스턴스에서 고치지 마세요. upstream(section9 카피)에서 수정·테스트·push 하고, 각 인스턴스는 다음 `merge upstream/main` 으로 수령합니다. 
- **실수로 인스턴스에서 코어를 고쳤다면** — 비admin은 가드가 commit 을 차단하니 그 자리에서 되돌리면 됩니다. admin commit 이 들어갔다면 그 commit 을 **upstream에 cherry-pick**한 뒤, 인스턴스는 merge로 다시 정렬합니다. 

**하네스 자체를 개발하는 사람만** section9 upstream 카피(`~/section9`)에서 작업합니다. 한 머신에서 upstream 카피와 인스턴스를 병행해도 됩니다 — 훅은 세션의 현재 디렉토리 기준으로 해당 인스턴스의 vault에 기록합니다.
