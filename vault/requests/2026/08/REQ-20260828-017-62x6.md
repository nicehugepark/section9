### 2026-08-28T14:48:24+09:00 response (by nicehugepark)

**설정 화면에 바깥 폴더 칸을 냈고, 없는 폴더는 저장할 때 만든다.**

### 무엇이 생겼나
Settings → 내 계정 → 비밀 키 판 아래에 "바깥 폴더" 한 칸. 경로를 적고 `경로 저장`을 누르면 계정 설정 `external_secrets_path` 로 저장된다(스트림 칸이 쓰는 것과 같은 길 — `POST /api/user/config`). 칸 옆 한 줄이 지금 그 경로가 실제로 쓰이는지 말한다.

### 침묵을 깼다 → 이제는 아예 만든다
`external_secret_dir()` 은 `os.path.isdir` 이 참일 때만 그 값을 인정하고 아니면 조용히 "" 로 떨어진다. 처음에는 그 사실을 화면에서 읽히게만 했는데, 그건 문제를 설명하고 남겨 두는 것이라 **저장할 때 폴더를 만들도록** 바꿨다(권한 0700, 새로 만들 때만 — 이미 있는 폴더의 권한은 건드리지 않는다).

- **만드는 자리는 `do_user_config_set()` 한 곳뿐이다.** CLI(`s9 user config`)도 대시보드도 이 함수를 지나므로 두 길이 갈리지 않는다.
- **읽는 쪽은 그대로 두었다.** `external_secret_dir()` 은 비밀을 읽을 때마다·커밋 가드·훅에서도 불린다. 읽기가 폴더를 만드는 부작용을 가지면 오타 하나가 엉뚱한 자리에 폴더를 만들고 아무도 모른다.
- **못 만들면 성공으로 치지 않는다.** 권한 없음·상위 경로 없음은 그 사유가 칸 옆에 그대로 뜨고 설정도 저장되지 않는다.
- **저장소 안 경로는 거부한다** (저장소는 공유·공개된다). `~` 는 펴서 절대 경로로 저장한다.

### 칸 옆 한 줄 (판정은 서버가 낸다)
화면은 `os.path.isdir` 을 볼 수 없고, 두 곳에서 재면 언젠가 답이 갈린다. `external_secret_state()` 한 곳이 내고 `/api/secrets` 가 실어 보내며 `s9 secret ls` 도 같은 것을 읽는다.

| 상태 | 화면 | 언제 |
|---|---|---|
| ok | **읽는 중** · 이 폴더의 파일도 비밀로 함께 읽고 있습니다. | 평상시 (저장하면 곧바로 여기) |
| missing | **폴더 없음** · 지워졌거나 연결이 끊긴 것 같습니다… 경로 저장을 다시 누르면 만듭니다. | 만든 뒤 폴더가 사라짐 |
| inrepo | **쓰면 안 됩니다** · 저장소 안의 폴더입니다… | 설정을 손으로 고친 경우 |
| unset | **정하지 않음** · 저장소 안에 둔 비밀만 씁니다. | 안 적었을 때 |

색만으로 구분하지 않는다 — 앞의 낱말이 먼저 답하고 색(--c-done/--c-inprogress/--c-blocked)은 글자에만 얹힌다. 색면·세로 띠 없음.

### 값을 넣는 곳은 여전히 저장소 안이다
`s9 secret set` 도 화면의 ＋넣기도 **언제나 저장소 안**에 쓰고, s9 는 바깥 폴더를 **읽기만** 한다. 오해하면 값이 엉뚱한 데로 가므로 설명문에 그대로 적었다: "s9 는 이 폴더를 읽기만 합니다: 위의 ＋넣기도 s9 secret set 도 언제나 저장소 안에 씁니다. 밖에 둘 값은 그 폴더에 직접 파일로 넣어 주세요 — 파일 이름이 곧 키 이름입니다."

### 곁가지로 고친 것
목록의 "둔 곳" 칸이 바깥 경로 접두사로 판정하고 있었다. 바깥 경로가 저장소 안(예: `users/`)을 가리키면 **저장소 안의 키까지 "저장소 밖"으로 뒤집혀** 표가 거짓말을 했다(실제로 캡처로 봤다). 내부 폴더와 견주는 방식으로 바꿨다 — CLI 와 화면 둘 다.

### 확인 방법
`?extdbg` 로 손 없이 눌러 본 결과(넷째 캡처): 못 만드는 경로 → 사유가 뜸 · 없던 폴더 → 저장만으로 생기고 곧바로 "읽는 중" · 원래 값으로 되돌림. 값 비노출 규율은 그대로다(경로는 본인 것만, 키 값은 여전히 응답에 없다).

### 왜 폼을 두 벌로 만들지 않았나
"internal 항목이랑 좌우 형태로 같이 등록"을 그대로 읽으면 폼이 두 벌이다. 세 가지를 재고 접었다.

| | 폼 두 벌(안쪽 폼 · 바깥쪽 폼) | **목적지 두 칸(채택)** | 목록을 좌우 두 열로 |
|---|---|---|---|
| 값 입력 | 두 번 — 옮기려면 지우고 다시 침 | **한 번**, 목적지만 바꿈 | 같음 |
| 어디로 가는지 | 어느 폼에 쳤는지로만 알 수 있음 | 고른 칸 + **버튼 문구**가 말함 | 열 위치로 |
| 바깥이 잠겼을 때 | 죽은 폼이 자리를 통째로 차지 | 칸 하나만 잠기고 그 자리에 이유 | 열 하나가 빔 |
| 같은 이름이 양쪽에 | 두 줄로 보이고 어느 쪽이 이기는지 안 보임 | 한 줄 + **가려짐** 표시 | 두 줄 |

좌우로 나란한 것은 **결정**이지 폼이 아니다. 고른 칸은 색면이 아니라 ●/○ 모양과 잉크 밑줄 2px로 선다 — 색을 못 보는 눈에도, 썸네일에서도 읽힌다.

### 쓰는 자리는 한 곳
새 `secret_write(user, key, value, where)` 하나가 파일을 연다. `s9 secret set` 도 `POST /api/secret/set` 도 이 함수를 지나고, 핸들러·CLI 어디에도 `os.open` 이 없다(계약 시험 `test_f1_no_second_writer`). 지우는 쪽도 `secret_remove()` 하나다.

### 바깥이 안 되면 큰 소리로 안 된다
경로를 안 정했거나(`unset`) 폴더가 없거나(`missing`) 저장소 안을 가리키면(`inrepo`) **바깥 칸이 잠긴다.** 칸에는 짧은 상태 이름(`경로 미설정`), 아래 줄에는 문장과 다음 행동(`경로 정하기` — 누르면 아래 경로 칸으로 데려가 커서를 놓는다). 판정은 앞 판에서 만든 서버의 `external_secret_state()` 하나를 그대로 읽는다 — 화면이 다시 재지 않는다.

서버도 같이 막는다: `where=external` 인데 상태가 `ok` 가 아니면 저장을 거부하고 사유를 낸다. **조용히 저장소 안으로 떨어뜨리는 길은 없다** — 사용자는 밖에 넣은 줄 아는데 값이 안에 들어가 있는 상태가 이 기능에서 가장 나쁜 결말이다.

### 넣었는데 안 쓰이는 경우를 말한다
같은 이름이면 저장소 안이 이긴다(`secret_keys` 가 그렇게 정해져 있다). 그래서:
- **넣기 전** — 확인 창: "저장소 안에도 있습니다 · 같은 이름이면 저장소 안의 값이 쓰입니다 — 지금 밖에 넣는 값은 쓰이지 않습니다." (`그래도 넣기` / `그만두기`)
- **넣은 뒤** — 서버가 판정한 사실을 알림에 붙인다(사이에 다른 세션이 넣었을 수도 있다).
- **목록** — 그 줄에 `밖의 같은 이름은 가려짐 — 안의 값이 쓰입니다`.
- **CLI** — `s9 secret ls` 는 `(밖의 같은 이름은 가려진다)`, `set --external` 은 걷어내는 명령까지 알려 준다.

가려진 이름은 목록에 아예 안 나온다(안쪽이 이기므로). 그래서 `/api/secrets` 가 `shadowed` 를 함께 보내고, 칸의 키 수도 가려진 것을 센다 — 안 그러면 "바깥에 넣었는데 사라졌다"로 읽힌다.

### 지우기는 어디 것인지 말한다
확인 창이 `저장소 밖에 있는 파일을 지웁니다` / 양쪽에 있으면 `저장소 안과 밖 양쪽에 있는 파일을 지웁니다` 라고 먼저 말하고, 지운 뒤 알림이 실제로 사라진 자리를 다시 말한다. CLI `s9 secret rm` 도 화면과 같아졌다(무지정 = 양쪽, `--internal`/`--external` 로 한쪽만) — 전에는 CLI 만 저장소 안을 지워 같은 말이 자리마다 다른 뜻이었다.

`postJSONRaw` 가 서버 응답을 버리고 `{ok:true}` 만 돌려주고 있었다. 그래서 **"이 값은 가려져 쓰이지 않습니다"가 응답에는 있는데 화면에는 안 떴다** — 캡처로 발견해 고쳤다(응답을 그대로 넘긴다). `--external` 이 `argparse` 의 REMAINDER 에 먹혀 조용히 무시되던 것도 같이 고쳤다(값이 저장소 안으로 갈 뻔했다).
