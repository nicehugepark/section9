### 검토 — worktree가 우리 문제를 푸는가

### 우리가 실제로 겪은 것

    2026-08-26  워커가 남의 미커밋 편집 위에 덮어써 테스트 파일 하나가 디스크에서 사라짐
                (커밋 전이라 git 으로도 복구 불가)
    2026-08-27  리드의 커밋에 워커의 진행 중 편집이 섞여 반쪽 상태로 들어감
    2026-08-27  디자이너: "web/index.html 을 나 말고 누군가 함께 만지고 있다"
    2026-08-28  무인 작업자 둘과 디자이너 하나가 같은 파일에 동시에 붙음

**네 번 다 같은 파일 하나였다** — `web/index.html`. 화면 작업이 그 한 파일에 몰려 있다.

### worktree가 주는 것

각 주체가 **자기 작업 디렉터리**를 갖는다. 남의 미커밋 편집을 볼 수도, 덮을 수도
없다. 합칠 때 겹치면 git 이 **충돌로 보여 준다.**

이게 핵심 이득이다 — 충돌이 없어지는 게 아니라 **조용한 소실이 보이는 충돌로
바뀐다.** 지금은 나중에야 "내가 쓰지 않은 코드가 있다"로 알아챈다.

### 그런데 그대로 쓰면 더 나빠진다

**이 저장소는 코드만 있는 곳이 아니다. 데이터가 같이 산다.**

    vault/     문서 — s9 note · s9 status 가 매 순간 쓴다
    index/     카탈로그 — 문서를 쓸 때마다 다시 만든다
    state/     세션 바인딩·클레임 — 여러 주체가 동시에 읽고 쓴다
    users/     프로필·설정

worktree를 그냥 만들면 **데이터도 함께 갈라진다.** 그러면
- 워커가 남긴 노트를 대시보드가 못 본다 (다른 사본에 썼으니까)
- 클레임·live 판정이 서로 다른 상태를 본다 — 오늘 고친 것들이 통째로 무의미해진다
- 합칠 때 `index/`·`state/` 가 매번 충돌한다. 그건 사람이 풀 수 있는 충돌이 아니다

**코드를 가르려다 진실을 가르게 된다.** 이 저장소의 제1 원칙("판정이 두 벌이면
한 벌만 고쳐진다")을 정면으로 어긴다.

### 그래서 이렇게 한다

**코드는 갈리고, 데이터는 하나다.**

    작업 디렉터리   worktree마다 따로   ← web/index.html · bin/ · tests/
    S9_ROOT         언제나 본 저장소     ← vault · index · state · users

`ROOT` 는 `$S9_ROOT` 가 있으면 그것을 쓰고 없으면 `bin/s9` 의 부모를 쓴다. 그러니
워커 환경에 `S9_ROOT=<본 저장소>` 를 박으면 **문서·상태는 한 곳에 모이고 코드만
갈린다.** 훅도 "명시된 S9_ROOT 가 항상 우선"이라 따라온다.

### 남는 것과 값

- 합칠 때 같은 구역을 만졌으면 여전히 충돌한다. **그건 이득이다** — 지금은 그
  자리에서 남의 것이 사라진다.
- worktree마다 저장소 사본이 하나씩 늘어난다(작업 파일만, 히스토리는 공유).
- 워커가 `bin/s9` 를 고치면 그 워커의 s9 는 고친 코드로 돈다. 그건 맞는 동작이다.
- **worktree를 안 거둬 두면 쌓인다.** 오늘 포트에서 겪은 것과 같은 종류의 누수라,
  만들 때부터 거두는 자리를 함께 만든다.

### 단계

1. `s9 worktree add/ls/rm` — 올바른 `S9_ROOT` 고정까지 함께 세워 준다. (지금)
2. 무인 작업자·서브에이전트가 그것을 쓰게 한다. (스위치로 켠다 — 기본은 끔)
3. 합치는 자리를 정한다: 워커는 자기 가지에 커밋하고 리드가 합친다.

### 2026-08-28T12:51:08+09:00 response (by nicehugepark)

2·3단계 구현 (TDD, python3 tests/ worker_worktree)

1단계(`s9 worktree add/ls/rm`)는 만들어 뒀지만 **아무도 쓰지 않았다** — 사람이 손으로 만들 때만 쓰이는 장치는, 사고가 나는 자리(무인 워커·서브에이전트)에 없는 것과 같다.

2단계 — 워커가 자기 자리에서 돈다
- `worker_workspace(doc_id, cfg, cwd)`: 계정 설정 `worker_worktree` 가 켜져 있으면 워커마다 전용 worktree를 만들고 그 자리를 cwd 로 준다. **S9_ROOT 는 언제나 본 저장소로 못박는다** — 데이터까지 갈리면 워커 노트를 대시보드가 못 보고 클레임·live 판정이 서로 다른 상태를 본다. 못 만들면 조용히 원래 자리로 물러난다(갈라 주는 것은 편의지 전제가 아니다).
- `_spawn_worker` 는 이 함수 하나만 부른다 — 스폰 경로가 하나이므로 규율도 한 곳이다.

3단계 — 합치는 자리
- worktree 모드에서는 워커에게 주는 규율이 뒤집힌다. 기존 "커밋하지 마라(리드 몫)" 는 worktree에서 **정반대로 위험하다**: 커밋하지 않은 것은 그 자리를 거둘 때 사라진다. 그래서 "wt/<이름> 가지에 커밋하라, 합치는 것은 리드 몫" 으로 바꿨다.
- `s9 worktree merge <이름>`: 미커밋 변경이 남아 있으면 거부(먼저 커밋하라), 합칠 커밋이 없으면 그냥 거둠, 있으면 --no-ff 로 합치고 worktree·가지를 거둔다. 충돌하면 git 이 막는다 — **그게 이득이다**. 지금은 그 자리에서 남의 것이 소리 없이 사라진다.

거두는 자리 (안 만들면 쌓인다)
- `worktree_sweep()`: 주인 pid 가 죽었고 · 만든 지 10분 넘었고 · **미커밋 변경도 안 합친 커밋도 없을 때만** 거둔다. 남길 것이 있으면 남긴다 — 그걸 지우는 것은 이 기능이 막으려던 바로 그 소실이다. serve 의 30초 틱에 물렸고 `s9 worktree sweep` 으로 손으로도 돈다.
- 이 자리를 함께 만든 이유는 오늘 실증됐다: 지워진 worktree 경로를 가리키는 훅 8개가 아무 소리 없이 죽어 있었다 (REQ-20260828-014-62x6). worktree 잔재는 조용하다.
- `s9 worktree ls` 가 "미커밋 · 안 합친 커밋 N" 을 함께 보인다 — 뭐가 남았는지 안 보이면 거둘지 합칠지 판단할 수 없다.

TDD 시나리오: N1 기본 꺼짐이면 아무것도 갈리지 않는다 · N2 켜면 자기 자리를 받되 S9_ROOT 는 본 저장소 · N3 merge 가 가지를 본 저장소로 들여오고 거둔다 · B1 미커밋 있으면 sweep 이 남긴다 · B2 안 합친 커밋 있으면 남긴다 · B3 주인 떠나고 남길 것 없으면 거둔다 · B4 주인이 살아 있으면 손대지 않는다.

**스위치를 켰다**: `s9 user config nicehugepark worker_worktree on`. 이 저장소가 같은 사고를 네 번 겪었고(전부 web/index.html), 켜지 않으면 이 요청의 목표가 성립하지 않는다. 끄려면 `s9 user config nicehugepark worker_worktree ""`.
