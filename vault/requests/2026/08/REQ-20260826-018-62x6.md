### 설계 원칙 두 가지

**① 서버는 사실만, 화면이 정책을.** `/api/serveinfo`(코드 낡음)는 `stale` 이라는 **판정**을 서버가 준다 — 지문 비교는 사실이기 때문이다. 반면 "이 사건을 사람에게 보여줄 만큼 최근인가"는 표시 정책이라 화면이 판단한다. 그래서 이 API 는 `state: "recovered"` 같은 필드를 주지 않는다. 대신 사실(감시자가 돌고 있는가 · 언제 죽었는가 · 몇 번 되살렸는가)만 준다.

**② 응답에 서버 시각(`now`)을 담는다.** 신선도 계산의 기준이 브라우저 시계면, 시계가 틀어진 기기에서 "6시간 전 사건"이 "방금"으로 보인다. 로그의 `ts` 는 전부 서버 시각이니 기준도 서버가 줘야 한다. 화면은 `now - ts` 로만 경과를 잰다.

```json
    "ts": "2026-08-27T00:14:32+09:00",
    "event": "died",

```

| 필드 | 값 | 뜻 |
|---|---|---|
| `port` | int | 이 서버가 듣는 포트 (`s9_port()`) |
| `now` | ISO8601 | 응답을 만든 서버 시각 — 화면 신선도 계산의 유일한 기준 |
| `guard` | `"watching"` / `"gave-up"` / `"none"` | 자동 복구가 지금 유효한가 |
| `guard_pid` | int / null | `_guard_alive(port)` 의 pid. watching 아니면 null |
| `guard_since` | ISO8601 / null | 마지막 `start` 이벤트의 `ts` |
| `restarts` | int | `guard_since` 이후 `died` 건수 = 자동으로 되살린 횟수 |
| `last_death` | object / null | 마지막 `died`·`gave-up`·`spawn-error` 이벤트 (tail 포함) |
| `events` | array | 최신순 최대 30건. 로그 줄의 필드를 **그대로** 통과 (모르는 키도 버리지 않는다) |

`guard` 판정 규칙 (셋 다 이미 있는 함수로 나온다):
- `_guard_alive(port)` 가 pid 를 주면 → `"watching"`
- 아니고, 마지막 `start` **이후에** `gave-up` 이벤트가 있으면 → `"gave-up"`
- 그 외 → `"none"`

### 실패·빈 상태

- `state/serve-guard.log` 가 없다 → `{"port":…, "now":…, "guard":"none", "guard_pid":null, "guard_since":null, "restarts":0, "last_death":null, "events":[]}` (200). 화면은 이 응답에 **아무것도 그리지 않는다**.
- JSON 파싱 실패한 줄 → 조용히 건너뛴다. 한 줄이 깨져도 나머지 기록은 살아야 한다.
- 로그가 커졌을 때: 파일 끝에서 뒤로 읽어 최근 30건만 파싱하는 편이 좋다(현재 크기론 전체 읽기도 무방).

### 크기

`tail` 은 기록 시점에 이미 `GUARD_TAIL_LINES`(20줄)로 잘려 있다. 30건 × 20줄이면 최악 ~60KB — 폴 주기가 20초라 감당된다. 더 줄여야 하면 `events` 건수를 깎되 `last_death.tail` 은 반드시 남겨라. "왜 죽었나"의 답이 거기 있다.

### 화면이 이 계약에 거는 것 (tests/test_serve_guard_ui.py)

- 화면은 `/api/serveguard` **하나만** 부른다. 로그 파일을 직접 읽지 않고, 사망 여부를 자체 추측하지 않는다.
- 응답이 없거나(404·무응답) 형태가 다르면 **직전 판정을 그대로 두고 조용히 넘어간다** — 서버 재기동 중의 무응답이 "사건 없음"으로 오독되면 안 된다. 그래서 이 API 가 아직 없는 지금도 화면은 아무 흔적을 남기지 않는다(회귀 안전).
- 신선도 판정에 `Date.now()` 를 쓰지 않고 `now` 필드를 쓴다.

**어휘 충돌은 주체로 갈랐다.** 위 알림이 말하는 재기동은 **사람이 하는 일**이고, 여기가 말하는 자동 복구는 **감시자가 하는 일**이다. 터미널의 `stale`(세션 무응답)은 또 다른 사실이라 그 단어는 쓰지 않았다. 셋이 같은 말을 쓰면 어느 것도 못 믿게 된다.

**나타나고 걷히는 규칙이 이 화면의 본체다.** 상시 표시하면 그 줄은 곧 배경이 되어 진짜 사고 때도 안 읽힌다. 그래서
- 사건이 없으면 **자리표시자조차 남기지 않는다**
- 되살아난 사건은 **6시간**, 자동 복구가 멈춘 사실은 **24시간** 동안만 말한다. 잠잠해지면 스스로 걷힌다 — 걷히는 것까지가 설계다
- 접으면 한 줄로 줄고, **다음 사건이 나면 다시 펼쳐진다**(접힘이 사건 시각에 묶여 있다)

| 상태 | 화면 |

| 조용함 | 아무 흔적 없음 |

되살아난 사건은 **설명**이고 복구가 멈춘 것은 **경고**다 — 후자만 사람의 행동을 요구하므로 색·마크·명령 제공이 갈린다. 색 없이도 마크(↻/▲)와 문장으로 읽힌다.

**명령은 대신 실행하지 않는다.** 감시자를 다시 세울지는 사람의 판단이라 붙여넣을 문자열까지가 화면의 몫이다(코드 낡음 알림과 같은 원칙).

**기록 패널**은 [기록 보기]로 헤더 안에서 열린다. 다른 자리로 보내면 방금 읽은 알림과의 연결이 끊긴다 — 대신 높이를 묶고(44vh·최대 320px) 자체 스크롤을 준다. 한 행 = 시각 · 종류 · 사유/생존시간/잇따른 횟수/되살리기 대기, 그리고 **[직전 출력 N줄]** 로 죽기 직전 출력을 펼친다. 종류는 사용자 말로 옮긴다(`died`→멈춤, `gave-up`→감시 포기 …) — 원래 값을 그대로 두면 기록이 아니라 암호다. 8건 + `+ N개 더 보기`(밀도 규칙), 빈 기록도 한 줄로 말한다.

### 조용히 무너질 자리 셋을 계약으로 박았다

1. **무응답을 사건 없음으로 읽지 않는다.** 서버가 죽어 있는 동안 이 폴은 실패하는데, **그 순간이 이 알림이 존재하는 이유**다. 실패를 "아무 일 없음"으로 읽으면 알림은 정확히 필요할 때 침묵한다 → 응답이 없으면 직전 판정을 두고 다음 폴을 기다린다.
2. **신선도는 서버 시각으로 잰다.** 기록의 시각이 전부 서버 것이므로 기준(`now`)도 서버가 줘야 한다. `Date.now()` 를 쓰면 시계가 틀어진 기기에서 6시간 전 사고가 "방금"이 된다.
3. **화면이 자체 추측하지 않는다.** 판단 근거는 읽기 전용 API 하나이고 로그 파일을 직접 읽지 않는다.

**① 서버는 사실만, 화면이 정책을.** `recovered`·`attention` 같은 판정 필드를 주지 않는다. "이 사건을 사람에게 보여줄 만큼 최근인가"는 표시 정책이고, 그게 서버와 화면 두 곳에 있으면 둘이 갈렸을 때 어느 쪽도 못 믿는다. 테스트 G3 이 그 필드들이 다시 생기는 것을 막는다.

**② 응답에 서버 시각을 담는다.** 신선도 기준이 브라우저 시계면 시계가 틀어진 기기에서 "6시간 전 사건"이 "방금"으로 보인다.

- **되살린 횟수는 마지막 감시 시작 이후만 센다.** 어제 죽은 횟수를 오늘 감시자의 성적으로 보고하면 숫자가 거짓말을 한다.
- **깨진 줄은 조용히 건너뛴다.** 사고 기록은 사고 중에 쓰이므로 마지막 줄이 반쯤 쓰이다 만 상태가 정상이다. 그 한 줄 때문에 "왜 죽었나"를 통째로 못 읽으면 안 된다.
