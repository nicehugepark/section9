#### 1. 무엇이 문제인가 — 실제로 겪은 충돌 예시 2건

- **예시 A · 두 머신 동시 발번**: 데스크톱과 노트북이 아침에 git 동기화를 마친 상태(오늘 마지막 번호가 REQ-20260825-012라 가정)에서, 오후에 각자 요청을 하나씩 만들면 **둘 다 REQ-20260825-013을 발급**한다. 저녁에 동기화하는 순간 "같은 번호, 다른 내용"인 문서 2개가 부딪힌다.
- **예시 B · rm 후 재발번 (오늘 오전 실제 발생)**: 오전에 REQ-20260825-006이 rm으로 삭제되자 오늘 최대 번호가 005로 내려갔고, 다음 요청(지금 이 문서)이 **삭제됐던 006 번호를 그대로 다시 받았다**. 예전 대화·링크가 가리키던 006과 지금의 006이 서로 다른 문서가 된 것이다.

원인은 발번 방식 자체다. 현행은 "오늘 날짜의 vault 파일을 스캔해 가장 큰 번호+1"이라, 머신 간 동기화 지연(예시 A)과 파일 삭제(예시 B)에 그대로 뚫린다. 같은 머신 안의 동시 실행만 락으로 안전하다. REQ만이 아니라 DOC·SES·PRJ 등 순번 발번 전체의 공통 사항이다.

#### 2. 선택지 4안 — 각 안에서 번호가 실제로 어떻게 보이나

- **A안 · 머신 대역(band) — 권고안**: 머신마다 번호 구간을 미리 배정한다 — 데스크톱 001~200, 노트북 201~400, 세 번째 머신 401~600. 예시 A를 다시 돌리면 데스크톱은 REQ-20260825-013, 노트북은 **REQ-20260825-201**을 발급 — 통신 없이도 겹치는 것이 구조적으로 불가능하다. 표시 형식(REQ-YYYYMMDD-NNN)과 "6번 문서"라고 부르는 가독성은 그대로다. 비용은 하나: 번호가 연속이 아니게 된다 — 목록에서 013 다음이 201로 점프해 보인다.
- **B안 · 랜덤 접미(ULID)**: 예: REQ-20260825-K7QX. 충돌은 원천 차단되지만 번호로 부를 수 없어진다 — 사용자가 호평한 현행 가독성(순번 구두 지칭)을 포기하는 안.
- **C안 · 중앙 발번 서버**: 번호를 한 곳에서 배급. 유일성은 보장되나 오프라인이거나 서버가 죽으면 문서 생성 자체가 막힌다.
- **D안 · 내부 UUID + 표시번호 분리**: 참조는 UUID로, 표시만 순번으로. 가장 근본적이지만 기존 문서 전체(약 200건)의 마이그레이션이 필요해 장기 과제로만 남긴다.

#### 3. 어느 안을 골라도 필요한 선행 수정 — rm tombstone

예시 B(재발번 사고)는 A~D 어느 안에서도 다시 일어날 수 있다(당일 같은 대역 안에서 삭제 후 재발번). 삭제를 "파일 소거"가 아니라 **tombstone**(문서를 남기고 status: removed로만 표시)으로 바꾸면 최대 번호가 내려가지 않아 재발번이 구조적으로 막힌다. A~D 판단과 독립이므로 먼저 적용할 가치가 있다.

#### 4. 안전망 (판단 대상 아님, 참고)

s9 sync(REQ-20260824-048 설계)의 pull-merge 단계에서 중복 id가 검출되면 늦게 만든 쪽을 다음 빈 번호로 자동 리네임하고 참조를 rewrite한다 — 대역 미설정 구버전 머신 같은 예외를 흡수하는 마지막 방어선.

#### 5. 확인 포인트 — 판단해 주실 것 3가지

1. **A안(머신 대역) 채택 여부** — 판단 기준 예시: "노트북에서 만든 오늘 첫 문서가 REQ-20260825-201로 보여도 괜찮다"면 채택. 연속 번호가 더 중요하면 B안(가독성 포기)·C안(오프라인 포기) 중 재논의.
2. **대역 크기 200/일 적정 여부** — 한 머신이 하루 200건까지 발번 가능. 실측 최다는 2026-08-23의 84건이라 2배 이상 여유이고, 초과 시 경고 후 빈 상위 대역을 이어 쓴다. 대역이 200이면 하루 4대(001~800)+예비(801~999), 500으로 키우면 1대+예비뿐이다. **200 유지를 권고.**
3. **tombstone 선행 적용 여부** — 3절의 rm 재발번 금지를 A~D 결정과 무관하게 먼저 적용해도 되는가. 오늘 사고의 직접 원인 제거라 **적용을 권고.**

답변 형태 예시: "A안 채택, 200 유지, tombstone 선행 적용" — 이 세 답이면 구현 범위 확정에 충분하다.

#### 0. 반려 질문 직답
- "A안은 머신 계층만 해결하면 끝인가? 다른 사용자가 각자 머신에서 동시에 001 발번은?" → A안에서는 대역이 달라 001 자체가 안 겹치지만, 정확히 지적대로 **대역 배정이라는 합의가 또 하나의 분산 문제**이고(두 머신이 동시에 같은 대역을 잡는 경합), 대역 크기라는 소진 한계가 구조에 박힌다. 그래서 A는 접는다.
- 사용자 계층은 별도 대역이 필요 없다: 같은 머신의 여러 사용자는 파일 락으로 직렬화되어 이미 안전하다. 충돌의 원천은 오직 "머신 간 동기화 지연"이다.

#### 1. D-정밀판: 정식 식별자(uid)와 표시(display)의 분리 — git 커밋 해시 원리
- **uid(정식·파일명·참조 저장용)**: `REQ-YYYYMMDD-NNN-<지문4>` — NNN은 그 머신의 그날 순번(로컬 락, 001부터), 지문4는 머신 지문(머신명+홈경로 해시의 base36 4자, 예: k3f2). **통신·합의·대역 없이 전역 유일**: 순번이 겹쳐도 지문이 달라 uid·파일명은 절대 안 겹친다. 소진 개념 없음 — 사용자·머신·요청 수 무제한, 하루 1000건 넘으면 NNN이 4자리로 자연 확장.
- **display(렌더 시점)**: 기본은 지금과 똑같은 `REQ-20260825-001`. **같은 (타입·날짜·순번) 문서가 vault에 2건 이상일 때만** 지문을 붙여 `REQ-20260825-001-k3f2`로 확장 — git이 짧은 해시를 쓰다 모호할 때만 길게 쓰는 것과 동일. 혼자/한 머신으로 쓰는 날은 화면이 지금과 완전히 같다.
- **resolve(짧은 지칭 해석)**: `s9 show REQ-20260825-001` → 유일하면 그 문서. 2건이면 후보를 나열하고 지문 포함 재지정을 요구(git 방식). 문서 본문·링크·note에 기록되는 참조는 항상 uid 전문 — 저장은 무모호, 표시만 축약.

#### 2. 예시 — "두 사용자가 각자 머신에서 동시에 001 발번"
- 데스크톱(지문 k3f2): 파일 `REQ-20260825-001-k3f2.md` / 노트북(지문 9x7q): 파일 `REQ-20260825-001-9x7q.md`
- 동기화: 파일명이 달라 **git 충돌 자체가 없다**. 해소랄 것이 없음(B안의 "충돌 해소 미지수"가 원천 제거).
- 대시보드 목록: 겹침을 감지한 그 순번만 `001-k3f2`, `001-9x7q`로 확장 표시. 나머지는 짧게.
- 구두 지칭 "1번 문서": 후보 2건 제시 → 지문으로 특정.

#### 3. 마이그레이션 — D안의 원래 약점 제거
기존 문서(~220건)는 파일명 그대로 "지문 없는 레거시 uid"로 인정, resolve가 정확 일치 우선 처리. **신규 발번부터만** uid 체계 적용 — 일괄 마이그레이션이 필요 없다(원래 D 기각 사유였던 전체 개편 비용 소멸).

#### 4. 동반 사항
- rm tombstone 선행(3회째 권고): 같은 머신 내 재발번(오늘 006 사고) 방지 — uid가 달라도 같은 표시 번호의 재사용은 혼란이다.
- 수정 범위: next_id(uid 발급)·locate/normalize_ids(prefix resolve·후보 제시)·대시보드 렌더(축약+겹침 확장)·digest 표기. 크기 M. sync 안전망(v1의 4절)은 지문 충돌(36⁴분의 1)이라는 이론적 잔여만 커버하는 최후 방어로 유지.

#### 5. 확인 포인트 — 판단 2가지
(1) **D-정밀판 채택** — 판단 기준: "겹친 날에만 일부 번호가 REQ-20260825-001-k3f2처럼 길어져 보여도 괜찮다"면 채택. (2) **tombstone 선행 적용** — 오늘 사고 직접 원인 제거, 권고. 답변 예: "D-정밀판 채택, tombstone 선행".
