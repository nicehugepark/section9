이건 판독을 뒷받침한다 — 새로고침이 고친다는 것은 서버 데이터가 아니라 **클라이언트에 남은 필터 상태**가 원인이라는 뜻이다. 새로고침하면 타입 선택이 초기값으로 돌아가니 보드가 다시 채워진다. 사용자가 "가끔"이라고 느낀 이유도 같다: Docs 에서 타입을 고른 적이 있는 세션에서만 재현된다.

### 2026-08-26T09:15:24+09:00 designer (by nicehugepark)

리드 판독이 맞다. 코드로 확인했고, 재현 조건을 특정해 고쳤다 (web/index.html).

원인
헤더의 타입 필터(#f-type)는 탭에 속하지 않는 전역 상태다. filtered()가 모든 탭에서 같은 조건을 적용하고, 탭 전환은 render()만 다시 부를 뿐 필터를 건드리지 않는다. REQ-20260825-084로 Board가 request 전용이 된 뒤 이 컨트롤은 보드에서 할 일이 없어졌는데도 계속 걸렸다 — knowledge/session/project 중 무엇이든 걸려 있으면 rows에 request가 0건이 되어 OPEN/IN-PROGRESS/REVIEW/DONE 네 컬럼이 전부 빈 상태 문구만 남는다. 화면은 "요청이 하나도 없다"고 말하지만 실제로는 250건이 있다. 084 이전에는 KNOWLEDGE/SESSION 컬럼이 남아 있어 이 상태에서도 화면에 무언가는 보였다 — 그래서 084가 이 결함을 드러냈다.

재현 조건 (사용자가 "가끔"이라고 느낀 이유)
1) 한 번이라도 Docs 타입바 칩 또는 헤더 타입 셀렉트로 request 외 타입을 고른다.
2) 새로고침 없이 Board 탭으로 간다 (출발 탭은 무관 — Docs든 Terminal이든 Graph든 같다. 007이 같은 원인인 이유).
→ 전 컬럼 0건. 필터는 URL 해시에도 localStorage에도 저장되지 않으므로 F5 한 번이면 type: all로 돌아가 정상이 된다("새로고침하니 정상이 됐다" 관측이 이 진단의 증거다). 즉 "타입을 고른 적이 있는 세션"에서만, 그 세션이 끝날 때까지 재현된다. 조작 이력에 의존하는 조건이라 사용자에게는 무작위로 보인다.

수정 (3곳, 전부 web/index.html)
- filtered(): `const typeOff = skipType || tab === "board"` — Board에서는 타입 조건을 건너뛴다. 값을 지우지 않고 적용만 멈춘다.
- syncTypeFilter(): Board에서 #f-type을 hidden. render() 첫머리에서 호출.
- CSS `.hrow2 select[hidden]{display:none}` — 10개 skin의 select override가 display를 걸어도 지지 않도록 명시.
값을 보존하는 것이 핵심이다: Board를 들렀다 Docs로 돌아오면 고른 타입이 그대로 살아 있고 타입바 칩도 활성이다(캡처 03).

대안 비교
(가) 채택 — 보드에서 타입 컨트롤을 감추고 조건도 건너뛴다. 결과가 0건이 되는 경로가 구조적으로 사라진다. 사용자 조작 0회, 되돌릴 것 없음. 감춰도 보드가 request 전용이라는 사실은 스탯 줄의 `250 전체 요청`이 이미 말하고 있어 설명이 따로 필요 없다.
(나) Board 진입 시 #f-type을 request로 고정 — 화면과 값은 일치하지만 Docs로 돌아갔을 때 사용자가 고른 knowledge가 request로 바뀌어 있다. 요구가 명시적으로 금지한 "엉뚱한 초기화". 기각.
(다) 셀렉트를 남기고 disabled — 조작할 수 없는 컨트롤이 툴바 자리를 계속 차지하고, 왜 못 쓰는지는 말해 주지 않는다. 기각.
(라) "이 필터는 보드에 적용되지 않습니다" 안내 배너 — 툴팁·안내문으로 구조 문제를 덮는 것(s9-design 기준 1). 기각.
