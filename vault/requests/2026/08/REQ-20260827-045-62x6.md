## Original

사용자 제안: "permission도 하네스 내부에서 미러를 뜨고 있다가 다른 머신에 가서도 덮어쓸 수 있게 하는건 어때?"

## Notes

### 2026-08-27T20:23:04+09:00 analysis (by nicehugepark)

**좋은 생각인데, 권한만은 그대로 옮기면 안 된다. 그 이유가 방금 우리가 겪은 일이다.**

**옮길 값이 있는 것** — 지금 머신을 바꾸면 잃는 것들이다.

    model · theme · remoteControlAtStartup · agentPushNotifEnabled · env
    (hooks 는 이미 `s9-install` 이 재생성한다 — 옮길 필요가 없다)

이건 취향과 편의라 미러해서 복원하면 그대로 이득이다.

**권한(permissions)은 다르다.**

방금 이 세션에서 게이트가 두 번 막았다. ① `git push` ② **그 push 를 허용하도록
settings.json 을 고치는 것.** 두 번째가 막힌 이유가 핵심이다 — 막힌 능력을 스스로
열도록 설정을 고치는 동작이기 때문이다.

그런데 제안하신 구조는 **그 두 번째를 우회하는 길을 만든다.** 내가 vault 에 쓰면
(막히지 않는다) → 동기화되고 → 다른 머신이 그것으로 settings.json 을 덮는다.
**이 머신에서 막힌 것을 저 머신에서 열게 된다.** 의도가 아니어도 구조가 그렇다.

한 겹 더: 이 리포는 **공개**다. 권한 파일이 vault 에 실려 흐르면, "어느 머신이 무엇을
자동 허용하는가"가 공개 기록이 된다. 그건 설정이 아니라 **공격 표면 지도**다.

**그래서 이렇게 가르기를 제안한다**

    자동 복원   model · theme · env · UI 취향       — 위험이 없다
    수동 승인   permissions                          — 옮기되 적용은 사람이
    안 옮김     자격증명·토큰                        — 비밀은 REQ-20260827-035-62x6 자리로

`permissions` 는 미러는 하되 **자동 적용하지 않는다.** 새 머신에서
`s9 config apply` 를 부르면 **무엇이 달라지는지 diff 로 보여주고**, 권한 항목이
있으면 그것만 따로 세워 "이 명령들을 자동 허용하게 됩니다"라고 적고 `--yes` 를
요구한다. 사람이 한 번은 눈으로 봐야 한다 — 오늘 푸시에서 우리가 확인한 그
"사람 관문"이 값을 하려면 **실제로 보고 누르는 것**이어야 한다.

**리드 의견**: 권한을 옮기는 것 자체는 반대하지 않는다. 다만 **말없이 덮는 것**은
반대다. 그건 게이트를 없애는 것이지 옮기는 게 아니다.

### 2026-08-27T21:08:30+09:00 decision (agent: worker:auto-resume, by nicehugepark)

**이 워커는 이 요청을 구현할 수 없다 — 구현할 자리가 전부 `bin/` 이다.**

무인 적용 세션의 수정 범위는 `web/`·`vault/`·`tests/` 안이고 `bin/`·`harness/`·설정
파일은 제안만 남기게 돼 있다. 그런데 이 요청은 `s9 config` 명령 한 벌이 전부라
범위 안에 손댈 곳이 없다. `web/index.html` 은 지금 다른 주체의 미커밋 변경이 올라
있어 그쪽도 손대지 않는다.

무엇보다 — **이 요청은 "막힌 능력을 스스로 열지 못하게 하는 게이트"에 관한 것**이다.
그 게이트를 만드는 작업을 하면서 내 쪽 범위 게이트를 넘어가는 것은 앞뒤가 맞지 않는다.

그래서 설계는 판정까지 끝내 지식으로 떼어 두고(DOC-20260827-006-62x6), 구현은 아래
명세로 리드에게 넘긴다.

### 원래 판단에서 한 군데를 바꿨다

앞선 분석 노트는 "permissions 도 **미러는 하되** 적용만 수동"이었다. 그건 부족하다.
**이 리포는 공개다**(REQ-20260827-036-62x6). 적용 시점을 늦춰도 **싣는 순간** "어느 머신이
무엇을 확인 없이 실행하는가"는 이미 공개 기록이 된다. 막아야 할 곳은 적용이 아니라
**적재**다. permissions 는 리포로 흘리지 않고, 사람이 파일 하나를 손으로 옮긴다 —
비밀값이 이미 그렇게 다니고 있다(REQ-20260827-035-62x6 의 `external_secrets_path`).

### 명세 (bin/s9 — 리드 몫)

    s9 config export [--out PATH] [--with-permissions]
      claude_home()/settings.json 을 읽어 층별로 가른다.
      기본 출력 = users/<이름>/config/harness/claude.json   (리포로 흐른다)
      --with-permissions 면 permissions 만 따로 리포 밖에 쓴다 — 기본 자리는
      external_secrets_path 옆, 없으면 --out 을 요구한다. 파일 권한 0600.

    s9 config apply [FILE] [--yes] [--dry-run]
      기본 입력 = users/<이름>/config/harness/claude.json
      항상 무엇이 달라지는지 먼저 찍는다 (현재값 → 새값). 같으면 "달라진 것 없음".
      permissions 가 든 파일이면 그 항목만 따로 세워
        "이 명령들이 확인 없이 실행됩니다: …"
      로 적고, --yes 가 없으면 아무것도 안 고치고 비영 종료한다.
      hooks·statusLine 등 s9-install 소관 키는 병합 대상에서 뺀다.

    MIRROR_KEYS   model · theme · remoteControlAtStartup · agentPushNotifEnabled
                  outputStyle · spinnerTipsEnabled · env(ENV_MIRROR_KEYS 만)
    ENV_MIRROR_KEYS  기본 빈 목록. env 에는 API 키가 흔히 들어앉는다 —
                     통째로 실으면 비밀 차단을 옆문으로 뚫는다. 이름을 적어
                     넣는 것이 사람의 행위여야 한다.

### TDD 시나리오 (tests/test_config_mirror.py)

    1. export 기본 출력에 permissions 가 들어가지 않는다
    2. export 는 env 중 허용목록 밖 키를 떨어뜨린다 (값도 남지 않는다)
    3. apply --dry-run 은 settings.json 을 고치지 않고 diff 만 찍는다
    4. permissions 가 든 파일을 --yes 없이 apply → 비영 종료 + 파일 무변경
    5. apply 가 hooks 키를 건드리지 않는다 (s9-install 재생성 소관)
    6. 커밋 가드: users/*/config/harness/claude.json 에 permissions 가 있으면 막는다
    7. claude_home() 이 CLAUDE_CONFIG_DIR 을 따른다 (프로필 세션에서도 맞는 파일)

6번을 빠뜨리면 손으로 한 번 붙여 넣는 것만으로 지금 세운 경계가 조용히 사라진다.
