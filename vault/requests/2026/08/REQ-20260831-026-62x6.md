- **G1 (A→done)**: TDD 노트 N/N 체크 + `python3 tests/` 전체 `echo $?` 실측 0 + CLI/웹 동일 경로 확인. 통과해야 B2 착수.
- **G2 (B→review)**: s9 shot(포트 9909, ?skin=&theme= 매트릭스) 캡처 `--attach` + C 문구 표 1:1 대조 + designer·ux-writer·tech-writer·translator 4인 판정(하나라도 빠지면 반려 대상, 규약 7). review 카드는 사용자 언어 300자·갈래 3.
- **G3 (D→done)**: 전체 스위트 녹색 + 거부 경로 실측 + 폼 보존 회귀. 통과 후 parent 026 review — 확인 포인트는 "프로젝트 화면에서 생성→멤버→설정이 눌러서 되는가"만.

한계: 생성 권한의 주체(admin 한정 vs 등록 사용자 전원)는 PO 판정 대기 — G0에서 확정해야 A의 TDD 가 닫힌다. 1단계 타 역할(PO·architect·designer) 산출과 이 분해가 어긋나면 리드 종합에서 이 표를 개정한다.

### 결론 먼저

**이 기능은 절반이 이미 만들어져 있다.** bin/s9 실측 결과 PRJ 문서 모델·권한 4단계(project_can, 마지막 owner 가드)·CLI(project add/set/member/authz)·GET /api/projects·멤버 편집 API(do_member_set 단일 경로)·#proj-info 멤버 편집 패널까지 전부 존재한다. 2단계는 **빈 곳 넷**만 채우면 된다: 생성/설정 API, 1급 화면, 문구, 검증. 이 발견이 계획의 크기를 L 전면 신축이 아니라 "증축 4건"으로 줄인다.

### 요지 (전체 표는 노트에)

**① 파생 REQ 4건** — A 생성·설정 API(backend, M: do_project_create/update 단일 경로 → CLI와 POST /api/project/add·set 공유), B 프로젝트 화면(frontend+designer, L: **신규 web/app/project.js + web/css/project.css 로 격리**, B1 mock 골격 → B2 실연동), C 문구 4인 판정(ux-writer 주도, S: 표만 산출, 코드는 안 잡음), D 회귀·브라우저 검증(QA, M). 각각 goal 판별 문장 초안 포함.

**② 순서** — W1 병렬(A ∥ B1 ∥ C) → W2 B2(A done + C 확정 대기) → W3 D → parent review. 크리티컬 패스 A→B2→D, 기대 1.5일/최악 2.5일.

**③ 파일 충돌 지도** — bin/s9 는 W1 동안 backend 단독(타 REQ 보류), 프론트는 신규 파일 격리로 app.js/index.html 은 W2 후반 등록 지점 최소 diff 한 번, skins.css 접점은 리드가 순서 조정, 커밋은 리드 단독.

**④ 리스크 4건** — R1 PRJ 하위 호환(by-project 인덱스·자동매핑·워커 preamble이 기존 필드를 읽는다 → additive-only+회귀 선행), R2 폴링 재렌더 폼 파괴(REQ-055 E7 가드 밖 신화면 → TDD에 명시), R3 권한 옆문(viewer_of 자기신고 → 핸들러는 do_* 중계만, 거부 테스트 4종 의무), R4 같은 파일 두 손(지도+격리+리드 커밋).

**⑤ 게이트** — G1(A: TDD N/N + `python3 tests/` echo $? 실측 0) 통과 전 B2 금지, G2(B: s9 shot 스킨×테마 캡처 --attach + 4인 스탬프) 없으면 반려 대상, G3(D 녹색) 후에만 parent review.

**리드 판정 필요 1건**: 프로젝트 생성 권한 주체(admin 한정 vs 등록 사용자 전원) — PO 산출과 함께 G0 종합에서 확정해야 A의 TDD가 닫힌다.

### 결론 — 프로젝트의 집은 문서다. 새 탭도 새 화면도 만들지 않는다

**전제부터 고친다: 프로젝트 관리 화면은 이미 절반이 지어져 있다.** REQ 원문은 "시각적으로
노출되어 있지 않다"고 하지만, 실물은 다르다 — 헤더 필터에서 프로젝트를 고르면 Board 위에
`#proj-info` 패널이 서고, 그 안에 **고객·현업 담당자·멤버 표(권한 셀렉트·직무·참여일·만료·
상태)와 추가/제거 버튼이 전부 배선돼 있다**(`web/app/app.js:152-275`, `web/css/header.css:163-235`,
서버 `/api/project/member`, `/api/project/member/rm`).

그러니 진짜 결함은 "없다"가 아니라 **셋**이다.

1. **찾을 수 없다** — 그 패널은 헤더 필터를 특정 프로젝트로 바꿔야만 나타난다. 기본값이
   「프로젝트: 전체」라 아무도 마주치지 않는다. 기능은 있는데 문이 없다.
2. **한 사물에 얼굴이 둘인데 양쪽 다 반쪽이다** — 같은 프로젝트가 두 자리에 산다.
   Board 위 패널은 고객·담당자·멤버를 보여 주되 History·Notes가 없고, Docs의 PRJ 문서 뷰
   (`#docs/PRJ-20260823-001`)는 status·summary·History를 보여 주되 **멤버도 고객도 안 그린다**.
   어느 쪽도 "이 프로젝트가 무엇인가"에 온전히 답하지 못한다.
3. **관리 도구가 작업 화면을 밀어냈다** — 실측: 1440×900에서 패널이 세로 **244px**
   (여백 포함)을 먹어 Board 컬럼 머리가 y=169 대신 y=413에서 시작한다. 뷰포트의 27%,
   카드 두 장 높이다. 900×760에서도 190px(25%)이다. Board의 결정은 "무엇을 다음에
   옮길까"인데 그 위에 권한 셀렉트 표가 앉아 있다 — 「한 화면 한 결정」 위반.

빠진 것은 **생성 흐름 · 프로젝트 목록 · 설정(고객·담당자·상태·개요) 편집** 셋뿐이다.
이 셋을 어디에 놓느냐가 이번 판정이다.

### 1. 자리 판정 — 대안 셋과 권고

### 대안 A — 새 탭 「Projects」

Board·Docs·Graph·Audit·Stream·Terminal·Settings 옆에 여덟 번째 탭을 세우고 목록·상세·
생성을 전부 담는다.

- 얻는 것: 진입이 가장 짧다(1클릭). 목록↔상세 왕복이 한 화면 안이다.
- 잃는 것 ①: **탭은 "일하는 모드"의 축이지 사물의 목록이 아니다.** 지금 일곱은 전부
  동사다 — 옮긴다·읽는다·본다·감사한다·흘려본다·친다·설정한다. 여기에 명사 하나가
  끼면 축이 깨진다.
- 잃는 것 ②: **빈도가 자리를 정당화하지 못한다.** 프로젝트 생성은 수명에 한 번,
  멤버 변경은 드물다. 매일 여섯 번 쓰는 탭들의 시선 비용을 늘려 1년에 세 번 쓰는 일에
  상시 자리를 주는 거래다.
- 잃는 것 ③(실측): 900px 폭에서 툴바가 이미 2행→3행으로 wrap 한다(태그 필터가 아래로
  떨어짐). 탭 줄은 아직 한 줄이지만 서버 상태 칩과 남은 여유가 얼마 없다 — 여덟 번째
  탭은 좁은 화면에서 브랜드 행마저 두 줄로 민다.
- 잃는 것 ④: 얼굴이 셋이 된다. 지금 둘로 갈라진 진실을 셋으로 늘린다.

### 대안 B — Settings 안 「프로젝트」 섹션

Settings는 이미 좌측 섹션 목록 + 우측 패널의 **2단 관리 셸**이고, 섹션이 디스플레이 ·
내 계정 · **사용자 관리** · 시스템 · 가이드다.

- 얻는 것: 셸이 공짜다. 탭 0 추가. **사람(사용자 관리) ↔ 프로젝트**의 대칭이 곱다.
  「조직 관리는 Settings에 산다」는 선을 사용자 관리가 이미 넘어 놓았다.
- 잃는 것 ①: **두 번째 진실이 굳는다.** 이 시스템의 뼈대는 "모든 것은 문서다"이고
  `PRJ-20260823-001`이 프로젝트의 정본이다. 관리 화면이 문서 밖에 서면 History·Notes·
  백링크·검색·Graph 노드를 전부 버리고 시작한다 — 그리고 그것들이 바로 "관리 정보"다.
- 잃는 것 ②: Settings는 **내가 나에게 하는 설정**의 자리다(스킨·톤·계정). 사용자 관리가
  예외로 들어와 있으나, 그건 admin 한 명의 전역 작업이라 성격이 다르다. 프로젝트는
  여럿이 오가는 협업 대상이다.
- 잃는 것 ③: Settings는 **필터가 걸리지 않는 섬**이다. 헤더의 프로젝트 필터·검색·태그가
  Settings에서는 아무 일도 하지 않는다. 프로젝트를 그 안에 넣으면 "지금 보고 있는 범위"와
  "관리하는 프로젝트"가 서로 모르는 채로 있게 된다.

### 대안 C — 권고: **문서가 집, 목록은 이미 있는 자리, Board 위는 한 줄로**

새 탭 0, 새 화면 0. 있는 두 자리를 각각 온전하게 만들고, 셋째 자리(Board 위 패널)는
문맥 띠로 줄인다.

| 무엇 | 어디 | 왜 거기 |
|---|---|---|
| **목록 · 생성** | Docs 좌측 타입 진입점 `PROJECT` | 이미 목록이다(캡처에 `PROJECT 1`). 누르면 프로젝트만 걸러진 문서 목록이 뜬다. 머리에 「+ 새 프로젝트」 한 줄만 얹으면 끝 |
| **상세 · 멤버 · 설정 편집** | PRJ 문서 뷰 | 정본이 여기다. History가 이미 아래에 있어 "누가 언제 무엇을 바꿨나"가 같은 화면에서 읽힌다 — 관리 정보의 정의가 그것이다 |
| **지금 보는 범위** | Board/Graph 위 `#proj-info` | 표를 걷어내고 한 줄 문맥 띠로. 결정을 가리지 않는다 |

권고 근거 넷:

1. **진실이 하나가 된다.** 지금 반쪽씩 나뉜 정보가 문서 한 자리로 합쳐진다. 멤버를
   바꾸면 History에 줄이 남고(서버가 이미 그렇게 쓴다 — `member update … (by nicehugepark)`),
   그 줄을 같은 화면 아래에서 바로 읽는다. 관리 화면을 따로 지으면 이 연결이 끊긴다.
2. **세 화면 모두에서 「한 화면 한 결정」이 선다.**
   Board = 무엇을 다음에 옮길까 / Docs›PROJECT = 어느 프로젝트인가, 새로 만들까 /
   PRJ 문서 = 이 프로젝트를 어떻게 고칠까.
3. **탭 비용 0, 신규 컴포넌트 0.** 문서 뷰의 메타 격자·표·`.acts` 버튼·`s9dlg` 다이얼로그가
   전부 있는 부품이다. 새 패턴 발명은 최후 수단이라는 규율에 맞는다.
4. **Board가 244px를 돌려받는다.**

**왕복 우려에 대한 답**: 목록(Docs)과 상세(같은 Docs 뷰어)는 **같은 탭 안**이다 —
Docs는 좌측 목록 + 우측 뷰어의 2단이라, 프로젝트 행을 누르면 오른쪽에 상세가 뜬다.
Settings에 목록을 두는 B는 오히려 Settings→Docs 탭 점프가 생긴다. C는 그 점프가 없다.

### 2. 화면별 와이어프레임 (서술)

### (a) Docs › PROJECT — 목록 + 생성 진입

좌측 타입 진입점에서 `PROJECT n` 을 누른 상태. 좌측 목록 패널 안:

```
PROJECT                                    + 새 프로젝트
─────────────────────────────────────────────────────
● Section9 하네스 시스템                        ACTIVE
  PRJ-20260823-001 · section9
  멤버 1 · 열린 요청 3 · 4분 전
─────────────────────────────────────────────────────
● 고객사 포털 개편                              ACTIVE
  PRJ-20260901-002 · portal
  멤버 5 · 열린 요청 12 · 어제
─────────────────────────────────────────────────────
+ 보관됨 2개
```

- 「+ 새 프로젝트」는 mono 소형 텍스트 버튼(밑줄 hover) — 「N개 더 보기」와 같은 문법.
  만들 권한이 없으면 **아예 안 그린다**(회색 버튼 금지).
- 행 첫 글리프는 7px 사각점(`.cdot`) — active는 프로젝트 타입 잉크, archived는
  `--c-cancelled` #868c96. 색 없이도 `ACTIVE`/`ARCHIVED` 글자가 오른쪽에서 같은 말을 한다.
- 셋째 줄(멤버 수 · 열린 요청 수 · 마지막 활동)이 이 목록의 값이다 — **관리 정보의 요약**.
  마지막 활동은 그 프로젝트에 속한 문서의 최신 `updated`.
- **정렬 기본은 최근 활동순**, 이름순이 아니다. 일하는 사람은 최근 것을 찾는다.
- 20개 초과 시 20 + 「N개 더 보기」(밀도 규칙).

### (b) PRJ 문서 뷰 — 상세 · 멤버 · 설정

지금의 뷰 구조(경로 줄 / 제목+ID / 메타 격자 / NOTES / HISTORY / 치우기)를 **유지한 채**
메타 격자를 넓히고 그 아래 멤버 표를 끼운다.

```
vault/projects/section9.md
Section9 하네스 시스템  PRJ-20260823-001                       ● ACTIVE
[이어 말하기]

SLUG              section9
STATUS            ● active                        ← maintainer+ 면 셀렉트
SUMMARY           프롬프트 audit·외부기억 하네스…    ← 클릭하면 그 자리 입력
CUSTOMER          내부(자체)
CONTACT           — (이름 · 소속 · 메일 · 전화)
CREATED/UPDATED   2026-08-23T19:12 → 2026-08-23T20:33

MEMBERS  1 활성 / 1                                         (표 캡션)
사용자          권한        직무      참여일      만료      상태
nicehugepark·ME [owner ▾]  [PM/오너]  2026-08-23 [연-월-일] 활성   [− 제거]
[e7test ▾]      [contrib▾]  [직무    ] —          [연-월-일]        [+ 추가]

NOTES
HISTORY
 · 2026-08-23T20:33 member update nicehugepark role=owner position=PM/오너
이 문서 치우기 [보관][삭제]
```

- 멤버 표는 **지금 `#proj-info` 의 표를 그대로 옮긴다** — 마크업·CSS·배선이 이미 있다.
  `.proj-info` 셀렉터를 문서 뷰 맥락으로 옮기거나 공통 클래스로 승격하는 것이 2단계 몫.
- 메타 격자 라벨은 mono 10.5px uppercase(기존 `.pi-k`/문서 뷰 라벨과 동일).
- 표 위 「MEMBERS 1 활성 / 1」이 표의 이름이자 `<caption>`이다.

### (c) Board/Graph 위 — 문맥 띠 (표 제거)

```
● Section9 하네스 시스템 · section9 · ACTIVE · 멤버 1 · 요청 45      프로젝트 문서 열기 →
────────────────────────────────────────────────────────────── (hairline)
```

- 한 줄. 높이 ~32px(244px → 32px). 아래 hairline 한 줄로 Board와 나눈다.
  **좌측 세로 색 띠 금지 · 배경 색면 금지** — 상태는 앞머리 점이 말한다.
- 「프로젝트 문서 열기」는 doclink 문법(점선 밑줄 mono). 누르면 (b)로 간다.
- `#my-strip`(MY PROJECTS)은 그대로 둔다 — 그것은 "내 범위 고르기"라 축이 다르다.

### 4. 조작별 인터랙션 스펙

### (1) 프로젝트 만들기 — 다이얼로그

- **진입**: Docs›PROJECT 목록 머리 「+ 새 프로젝트」.
- **형식 판정**: 인라인 폼이 아니라 **`s9dlg` 다이얼로그**. 근거 — 입력이 여럿이고
  생성은 문서를 만드는(되돌리기 비싼) 행위다. 인라인 폼은 목록을 밀어낸다.
- **필드는 넷만**: 표시명(필수) · slug(자동 후보, 고칠 수 있음) · 개요(선택) · 고객(선택).
  **담당자 4필드(이름·소속·메일·전화)는 넣지 않는다** — 만들 때 필요한 정보가 아니다.
  만든 뒤 문서에서 채운다. 이 다이얼로그의 결정은 하나다: "이 프로젝트를 무엇이라 부를까".
- slug는 표시명을 치는 동안 후보를 보여 주되(한글은 자동 로마자화하지 않는다) 비면 진행 불가.
  중복이면 그 자리에서 「이미 있는 이름입니다」.
- **만든 사람은 자동으로 owner** — 묻지 않는다. 정해 주고 나중에 바꿀 수 있게.
- **성공 → 방금 만든 프로젝트 문서로 이동**한다. 목록으로 되돌리지 않는다: 갓 만든
  프로젝트에는 할 일(멤버·담당자)이 남아 있고, 그 자리가 문서다.
- 실패 → 다이얼로그 안 실패 줄. 입력값 보존.

### (2) 멤버 추가 — 표의 마지막 행, 즉시 저장

- 후보 셀렉트(아직 멤버 아닌 등록 사용자만) · 권한 · 직무 · 만료일 · 「+ 추가」.
- 확인 창 없음(되돌리기 = 제거가 바로 옆에 있다).
- 후보 0명: 위 상태 표 참조.

### (3) 멤버 빼기 — 확인 창 (예외 인정)

- 규율은 "파괴적 행동에 확인 대신 되돌리기"지만, **여기는 그 예외 조건에 해당한다**:
  제거 즉시 서버가 접근을 끊고 History에 줄을 쓴다 — 5초 취소로 되돌릴 수 있는 상태가
  아니다. 지금의 `s9dlg confirm`을 유지한다.
- 지금 문구가 좋다: 「프로젝트 문서는 그대로 남고, 이 사람의 접근만 끊깁니다」.
- **자기 자신을 뺄 때는 무게가 다르다** → 다른 문구. 초안: 「자신을 빼면 이 프로젝트를
  더 볼 수 없습니다」 (확정은 ux-writer 몫).
- 마지막 owner: 버튼 disabled + 이유.

### (4) 설정 고치기 — 인라인 즉시 저장

- **판정: 「설정 고치기」 버튼 + 다이얼로그가 아니라 값 자리 인라인 편집.**
  근거 ① 대개 한 번에 하나만 고친다(상태를 archived로, 고객명 오타). 다이얼로그는 여섯
  필드를 다 열어 "무엇을 고칠지"를 다시 고르게 만든다. ② 바로 아래 멤버 표가 이미
  인라인 즉시 저장이다 — 한 화면에 저장 규칙이 둘이면 안 된다.
- 실패 시 원복 + 실패 줄(멤버 표의 `post()` 규칙 그대로 재사용).
- **status만 예외 — 확인 창을 준다.** active→archived는 그 프로젝트의 모든 문서가
  목록에서 접히는 큰 사건이다. 셀렉트가 툭 바뀌고 끝나서는 안 된다.
- maintainer 미만: 컨트롤 없이 값만.

### (5) 프로젝트 지우기 — 새로 만들지 않는다

문서 뷰 하단에 「이 문서 치우기 · 보관 · 삭제」가 **이미 있다**. 두 번째 삭제 버튼을
만들면 어느 쪽이 진짜인지 묻게 된다. 일상적 "치우기"는 `status=archived`가 맡는다.

### 5. 시각 언어 · 접근성 준수

**금지 준수**
- 색면 하이라이트 없음 — 상태는 7px 사각점 + 글자색 + 대문자 mono 라벨.
- 좌측 세로 띠 없음 — Board 문맥 띠는 아래 hairline 하나로만 나눈다.
- 무채색 미니멀 아님 — 상태색(active/archived/만료임박)이 잉크로 살아 있고, 목록의
  「멤버 · 열린 요청 · 마지막 활동」이 밀도를 만든다.
- 라운드 0 · 그림자 0. 표는 `border-collapse` + hairline 행 구분(현행 `.proj-info table` 그대로).

**타이포**: 메타 라벨·ID·slug·카운트·상태는 전부 mono 10~11px uppercase + letter-spacing.
제목만 본문체 600. 위계는 크기·굵기로, 색은 신호로만.

**배율 불변**: 새 홀수 치수·소수 테두리를 만들지 않는다. 점은 확정된 7px 무대
(`.livedot`/`.cdot`)를 그대로 쓰고 새로 그리지 않는다. 표 행 높이는 4/8 배수.

**접근성**
- 멤버 표에 `<caption>`(「MEMBERS 1 활성 / 1」), `<th scope="col">` — 지금 `scope`가 없다.
- 「− 제거」는 어느 행인지 스크린리더가 모른다 → `aria-label="<이름> 멤버 빼기"`.
- 표 행 안 컨트롤의 터치 타깃 44px 최소 높이 확보 — 특히 `density=compact`에서.
  s9-design 「칠은 과녁이 아니다」: 시각을 맞추려고 과녁을 깎지 말 것.
- 포커스 링은 기존 `.proj-info select:focus` 규칙(보더 잉크색)이 있으나 outline이
  `none`이다 — 키보드 사용자에게 보더 색 변화만으로는 약하다. 2단계에서 재검토 대상.
- 대비: 만료 행을 `--faint`까지 낮추면 4.5:1을 놓친다 → `--muted` 선에서 멈춘다.

**부품의 여섯 얼굴** — 쉼·hover·포커스·눌림·busy·disabled. 이 설계에서 새로 서는
컨트롤은 「+ 새 프로젝트」·「프로젝트 문서 열기」·인라인 메타 편집 셋이다. **hover 칠이
이웃 글자를 파고들지 않는지, 반전 스킨(terminal)에서 피드백이 배경과 같은 색으로
사라지지 않는지**는 정적 캡처로 판정되지 않는다 — 2단계 구현에서 CDP 실포인터로
1·1.25·1.5 배율 캡처 필수.

### 6. 2단계로 넘기는 것

- **문구 전량 초안이다.** 「+ 새 프로젝트」·「보기 권한입니다」·「자신을 빼면…」·빈 상태
  두 갈래·확인 창 문구 — ux-writer(형식) · tech-writer(무엇을 옮기고 무엇을 둘지:
  slug·owner·maintainer·contributor·viewer·archived) · translator(옮길 것) 3인 판정.
  특히 **role 넷은 확립 업계어라 그대로 두는 쪽에 무게가 있다**(순우리말 되돌림은
  s9-design 6절이 기계 직역과 같은 결함으로 본다) — 판단은 tech-writer 몫.
- **서버**: 프로젝트 생성 API(`/api/project/add`)와 설정 변경 API(`/api/project/set`)가
  없다. CLI `s9 project add|set`만 있다. architect·backend 몫.
- **미검증**: 프로젝트가 1개뿐이라 N개 목록·보관 접힘·정렬을 실물로 못 봤다. 2단계에서
  더미 프로젝트를 넣고 확인해야 한다.
- **경계 하나**: `.proj-info` CSS를 문서 뷰로 옮길 때 셀렉터를 공통 클래스로 승격할지
  복제할지 — 복제하면 스킨 수만큼 색을 다시 적게 된다(벨트 글리프 때의 그 함정).
  관문은 한 곳이어야 한다.

### 결론

**전제부터 뒤집힌다 — 프로젝트 관리 화면은 이미 절반이 지어져 있다.** 헤더 필터에서 프로젝트를 고르면 Board 위에 `#proj-info` 패널이 서고, 그 안에 **고객·현업 담당자·멤버 표(권한·직무·참여일·만료·상태) + 추가/제거가 전부 배선돼 있다** (`web/app/app.js:152-275`, `web/css/header.css:163-235`, 서버 `/api/project/member`, `/api/project/member/rm`).

진짜 결함은 셋이다.

1. **문이 없다** — 그 패널은 기본값 「프로젝트: 전체」를 특정 프로젝트로 바꿔야만 나타난다. 기능은 있는데 아무도 마주치지 않는다.
2. **한 사물에 얼굴이 둘인데 양쪽 다 반쪽** — Board 위 패널은 멤버·고객을 보여주되 History가 없고, Docs의 PRJ 문서 뷰는 status·summary·History를 보여주되 **멤버도 고객도 안 그린다**.
3. **관리 도구가 작업 화면을 밀어냈다** — 실측: 1440×900에서 패널이 **244px**을 먹어 Board 컬럼 머리가 y=169 대신 y=413에서 시작한다(뷰포트 27%, 카드 두 장). 900×760에서도 190px.

빠진 것은 **생성 흐름 · 목록 · 설정 편집** 셋뿐이다.

### 자리 판정 — 권고 C: 새 탭 0, 새 화면 0

| 대안 | 판정 |
|---|---|
| A. 새 탭 「Projects」 | **탈락**. 지금 탭 일곱은 전부 동사(옮긴다·읽는다·본다…)인데 명사 하나가 끼면 축이 깨진다. 수명에 한 번 쓰는 일에 상시 자리를 주는 거래. 실측: 900px에서 툴바가 이미 3행으로 wrap — 여덟 번째 탭은 브랜드 행마저 민다. 얼굴이 셋이 된다 |
| B. Settings 「프로젝트」 섹션 | **탈락**(가장 아깝다). 2단 관리 셸이 공짜고 사용자 관리와 대칭이 곱다. 하지만 문서 밖에 서면 History·백링크·Graph 노드를 버리고 시작하는데 **그것들이 바로 관리 정보다**. Settings는 헤더 필터가 안 걸리는 섬이다 |
| **C. 문서가 집** | **권고**. 목록·생성 = Docs 좌측 타입 진입점 `PROJECT`(이미 목록이다, 머리에 「+ 새 프로젝트」만 얹음) / 상세·멤버·설정 = PRJ 문서 뷰 / Board 위 패널 = 244px 표를 32px 한 줄 문맥 띠로 축소 |

왕복 우려에 대한 답: Docs는 좌측 목록 + 우측 뷰어 2단이라 **목록↔상세가 같은 탭 안**이다. B가 오히려 Settings→Docs 점프를 만든다.

세 화면 모두에서 「한 화면 한 결정」이 선다 — Board: 무엇을 옮길까 / 목록: 어느 프로젝트인가 / 문서: 이 프로젝트를 어떻게 고칠까.

### 인터랙션 판정 셋

- **생성 = 다이얼로그**, 필드는 **넷만**(표시명·slug·개요·고객). 담당자 4필드는 뺀다 — 만들 때 필요한 정보가 아니다. 만든 사람은 자동 owner(묻지 않음). 성공하면 목록이 아니라 **방금 만든 문서로 이동**한다(할 일이 남았다).
- **설정 = 인라인 즉시 저장**(다이얼로그 아님) — 대개 하나만 고치고, 바로 아래 멤버 표가 이미 인라인이라 한 화면에 저장 규칙이 둘일 수 없다. **status만 확인 창**(archived는 전 문서가 접히는 사건).
- **멤버 빼기 = 확인 창 유지** — "확인 대신 되돌리기" 규율의 예외 조건에 해당한다(서버가 즉시 접근을 끊고 History를 쓴다). 단 자기 자신을 뺄 때는 문구가 달라야 한다.
- **삭제 버튼은 만들지 않는다** — 문서 뷰 하단 「치우기·보관·삭제」가 이미 있다.
