실제 사고 2026-09-18 13:44: 릴리스 노트 0.9.2 절을 파일에 쓰는 bash 호출이 거부됐다.

  [s9-git-gate] ... 거부 — 이 저장소의 작업 트리를 되돌리는 명령은 남의 미커밋 작업을 지운다

그 명령은 python3 heredoc 으로 docs/RELEASE-NOTES.md 에 글을 쓰는 것이었고, 거부를 부른 것은 본문에 든 낱말 둘이다(「망을 타는 git 셋」 과 「s9 stash」). 작업 트리를 되돌리는 일은 하지 않았다.

우회하지 않고 본문을 파이썬 파일로 옮겨 실행했다 — 검사를 두드려 지나가지 않았다.

문제는 검사의 무늬가 **명령줄 전체 문자열**을 보는 것이다. 문서를 쓰는 일이 늘어날수록(릴리스 노트·가이드·요청 본문) 글 안의 낱말로 막히는 일이 늘어난다. 막는 것이 옳은 명령을 놓치지 않으면서, 인용부·heredoc 안의 본문은 명령이 아니라는 것을 가려야 한다.

경계 넷: ① `git stash` 를 실제로 실행 → 막는다 ② heredoc 본문에 그 낱말 → 막지 않는다 ③ 따옴표 안 문자열 인자에 그 낱말(예: commit 메시지) → 막지 않는다 ④ `echo x | git stash` 처럼 파이프 뒤 → 막는다.

### 2026-09-18T14:01:42+09:00 response (agent: lead:claude-opus-5, by nicehugepark)

원인 — 무늬가 재는 것이 argv 가 아니라 **줄글**이었습니다. `\bgit\b[^|;&]*\bstash\b` 의 틈은 줄바꿈까지 건너뛰므로, 한 화면 안에 'git' 과 'stash' 가 각각 적혀 있기만 하면 한 명령으로 읽힙니다. 릴리스 노트 본문(「망을 타는 git 셋」 … 「s9 stash」)이 그렇게 걸렸습니다. 앞선 고침(REQ-20260902-003-62x6)이 세운 「글은 지우고 잰다」는 여기서 듣지 않습니다 — python3 heredoc 본문은 인터프리터가 받는 글자라 일부러 지우지 않고 재기 때문입니다.

고친 방법 — 틈을 좁히는 대신 읽는 법을 바꿨습니다. 셸이 명령을 시작하는 자리(`;` `|` `&&` 줄바꿈 괄호 역따옴표)로 잘라 토막을 만들고, 토막 안의 `git` 낱말 뒤를 argv 로 읽는다: 전역 옵션(값을 받는 -C·-c 는 값까지)을 걷어내고, 그 다음 낱말 하나가 하위명령, 나머지가 인자입니다. 판정은 하위명령과 인자 목록으로만 합니다(stash 는 list/show 만 통과, reset 은 인자에 --hard/--merge, checkout 은 --·-f·., restore 는 --staged 단독일 때만 통과, clean 은 짧은 옵션 묶음의 f/d/x 와 --force, commit 은 --no-verify·n 이 든 짧은 옵션 묶음, 전역 옵션의 core.hooksPath). 그래서 'git' 다음이 '셋' 이면 하위명령이 아니라 글입니다.

곁가지 — clean 의 `--force` 긴 이름이 옛 무늬에는 없어 지나갔다; argv 로 읽으면서 함께 막힙니다.

검증 — tests/test_git_gate.py 에 두 갈래를 더했다: g15(본문 한 줄에 두 이름이 떨어져 있는 일곱 모양 — 갈래마다 하나씩 — 이 지나갑니다) · g16(파이프 뒤·서브셸·-C·경로 붙은 git·clean --force·인터프리터 본문에 붙어 있는 두 낱말은 그대로 막힙니다). git_gate·no_metaphors·stash_cmd·windows_entry·install_owned_hook 47건 통과. 이 세션의 첫 재현 시도(python3 heredoc 으로 낱말 둘이 든 글을 쓰는 명령)가 실제로 훅에 거부됐고, 고친 뒤 같은 모양이 지나갑니다 — 사고를 그 자리에서 재현하고 고친 뒤 다시 걸었습니다. commit c6d8359b0.
