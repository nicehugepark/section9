### ① 진짜 원인

카탈로그 한 목록이 **두 가지 물음**에 답하고 있었다.
- "화면이 무엇을 그릴 것인가" — 보드용 창(bin/s9.py `catalog_window`)이 답한다.
  열린 일 전부 + 최근 닫힌 400건. 실측 1380건 중 **403건**.
- "이 문서가 있는가" — `catFind`(state.js)·`resolveShortRef`(refs.js)가 **같은
  목록**에 묻는다.

그림의 정책이 존재의 사실을 가린 것이 원인이다. 그래서 창 밖의 옛 문서는 없는
문서로 판정돼 정식 id 조차 링크가 서지 않았고, 축약 번호는 더 나쁘다 — 없으면
안 걸리는 데서 그치지 않고 **더 오래된 다른 문서로 풀린다**(창에 남은 것 중 최신).
전량을 늘 싣는 것으로 갚을 수 없다: 전량 응답은 이 서버에서 가장 무거운 단건이다
(gzip 168KB · 보드 창 56KB).

### ② 고른 방향과 값

링크 판정에 실제로 필요한 것은 **id 와 created 둘뿐**이다(제목·상태는 안 쓴다).
그래서 존재를 묻는 자리를 따로 열었다 — `/api/docindex` 는 전량의 [id, created]
쌍만 준다. 실서버 실측 **76KB · gzip 11KB**(보드 카탈로그 gzip 56KB 의 1/5,
전량 168KB 의 1/15). ETag·gzip·세대 캐시는 카탈로그와 같은 길을 쓴다.

받는 때는 부팅 1회뿐이고, 그 뒤로는 **카탈로그가 색인이 모르는 id 를 물어올
때만** 다시 받는다(새 문서는 열린 일이라 늘 보드 창에 실려 온다). 색인과
카탈로그는 나란히 출발하고, 첫 판은 늦은 쪽을 1.5초까지 기다렸다 그린다 —
안 기다리면 사람이 실제로 읽는 첫 판에서만 링크가 빠진다. 색인이 안 오면
그냥 그린다(색인 도입 전과 동일 동작).

**판정 엔진은 늘리지 않았다.** `catalog` 를 잠깐 색인으로 바꿔 끼우고 원래
`catFind`·`resolveShortRef` 를 부른다(withDocIdx). 규칙이 두 벌이 되면 화면과
서버가 다른 문서를 가리키는 자리라(REQ-20260828-021-62x6 이 계약표까지 만들어 막은
자리), 데이터만 갈아 끼우고 규칙은 한 벌로 뒀다.

손댄 곳: bin/s9.py(엔드포인트) · web/app/app.js(색인 적재·판정 헬퍼) ·
web/app/ccrender.js(catFind→anyDoc, resolveShortRef→anyShortRef) ·
tests/test_doc_index.py(신규 6건). docs.js 는 건드리지 않았다.

### ③ 실브라우저 확인

- `REQ-20260828-021-62x6 → REQ-20260828-021-62x6 [확정]` — 백틱 안·밖 모두 링크.
- `REQ-017 → REQ-20260824-017 [짐작]` — 고침 전에는 (안 품).
- 없는 `REQ-20260828-999` 는 맨 글자 그대로.
Chrome·WebKit 두 벌 동일(첨부).

### 한계 (내 파일 범위 밖)

`?shortref` 판 **위쪽 계약표**는 아직 ✗ 4줄이다 — boot.js 가 `resolveShortRef`
를 카탈로그로 직접 부르기 때문이고, 같은 창 증상이다. 아래 실제 렌더는 ✓ 이라
같은 판이 서로 다른 말을 한다. refs.js 한 줄(`catalog` → 색인 우선)이면 이
false 경보까지 사라진다 — 제약(세 파일)에 걸려 손대지 않았고 리드 판단에 맡긴다.

예산: 도구 30회 배정, **약 38회** 사용. 초과분은 실브라우저 확인에서 났다 —
web 묶음(`/app/all.js`)이 서버 안에 캐시돼 있어 편집이 화면에 반영되지 않았고,
캡처 3장을 헛으로 찍은 뒤에야 `serve --restart` 로 확인했다.
