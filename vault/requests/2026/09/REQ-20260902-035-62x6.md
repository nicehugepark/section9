### 왜 여기서 적용하지 않았나

고칠 자리가 전부 bin/s9 다. 무인 적용 모드의 수정 범위(web/·vault/·tests/) 밖이고,
지금 그 파일에는 commit 안 한 다른 작업의 변경이 얹혀 있다(git status 의 " M bin/s9").
덮어쓰면 남의 작업이 사라진다. 게다가 이 봉투의 allowlist 는 s9 로 시작하는 명령만
허용해 python3·cp 가 막혀 있다 — 고쳐도 재는 자가 없다. 그래서 적용 대신 그대로
옮겨 심을 수 있는 사양을 남긴다.

### 지금 값 (코드·파일 실측)

- rebuild_index(bin/s9:1612)는 쓰기마다 walk_docs() 로 vault 전체를 read_doc 한다.
  호출 자리 31곳이고 거의 전부 write_doc 직후다.
- 문서 906건 · index/catalog.jsonl 835,546 바이트 = 행당 약 920 바이트. 20,000 문서면
  18MB 이고, 그것이 그대로 /api/catalog 응답이다(핸들러 20433 이 전량 직렬화).
- index/ 는 .gitignore 안이다 — 파생물이라 곁들이는 새 파일이 동기화에 얹히지 않는다.
- 읽는 관문은 load_catalog()(793) 한 곳뿐이다. 캐시 키가 catalog.jsonl 의 stat 이고
  _poll_fingerprint(727)·id_alias(965)가 그 키에 매달려 있다 — 증분을 넣을 때 이 셋이
  같은 키를 봐야 대시보드가 갱신을 놓치지 않는다.

### 설계 넷

### 1. 델타 한 줄 — 쓰기 비용을 문서 수에서 떼어낸다

catalog.jsonl 을 그 자리에서 고치려면 전체를 다시 써야 한다(20,000행이면 18MB).
그래서 덧붙임 파일을 곁에 둔다.

    CATALOG_DELTA = CATALOG + ".delta"   # index/ 안 — 로컬 파생물
    CATALOG_DELTA_MAX = 200              # 넘으면 다음 증분이 접는다

- index_upsert(paths): 그 문서만 read_doc → catalog_row 로 행을 짓고 델타에 한 줄
  덧붙인다(fsync). 파일이 없거나 .trash 면 묘비 한 줄({"id": ..., "_gone": true}).
  비용이 문서 수와 무관해진다.
- load_catalog(): base 를 읽은 뒤 델타를 id 로 덮어쓴다(묘비는 삭제), id 순 정렬.
  캐시 키를 (base stat, delta stat) 로 넓힌다 — _poll_fingerprint 도 함께 넓혀야
  한다. 안 넓히면 증분 갱신이 화면에 안 보인다.
- by-* 색인 md: rebuild_index 의 keys 표를 _row_index_keys(r) 로, 쓰기 루프를
  _write_index_files(rows, only=None) 로 뽑아낸다. 증분은 바뀐 행의 옛 키와 새 키의
  합집합만 다시 쓴다(보통 다섯 개 이하). 비게 된 파일은 지운다.
- 접기(compact): 델타가 MAX 를 넘으면 델타를 .delta.compacting 으로 rename 한 뒤
  합친 결과를 catalog.jsonl 로 원자 교체하고 그 임시본을 지운다. rename 을 먼저 하는
  이유 — 접는 도중 다른 프로세스가 덧붙인 줄은 새 델타로 가서 살아남는다.
  acquire_lock 을 쓰면 안 된다: doc_lease_acquire(9736 부근)가 락을 쥔 채로
  rebuild_index 를 부르고 있어 재진입이 아니다.

### 2. write_doc 경계 하나 (31곳을 고치지 않는다)

write_doc(559) 의 주석이 이미 그 규율을 적어 두었다 — "부르는 자리가 36곳이라 여기
한 곳만 고치면 전부가 함께 고쳐진다". 같은 자리에 index_upsert(path) 를 건다. 그러면
write_doc 뒤에 붙은 rebuild_index(quiet=True) 는 지울 수 있다.

다만 대량 쓰기 두 곳(cmd_backfill · cmd_normalize)은 문서 수만큼 증분을 돌면 전량보다
느리다. index_defer() 컨텍스트 매니저로 그 구간의 upsert 를 멈추고 끝에서
rebuild_index() 한 번. 삭제·이동(휴지통·보관)은 write_doc 을 지나지 않으므로 그 자리에는
index_upsert(옛 경로, 새 경로) 를 직접 건다.

전량은 남긴다 — s9 index rebuild(명시 호출·post-merge 훅)와 드리프트 검지.

### 3. pull 뒤에는 바뀐 파일만

pull 자리가 셋이다: _pull_if_stale(4065) · sync_poll(9736) · sync_resolve(10074).
셋 다 앞뒤 HEAD 를 알거나 알 수 있다(sync_poll 은 이미 before/after 를 들고 있다).

    changed = git diff --name-only <before> <after> -- vault
    vault 아래 .md 만 골라 index_upsert(경로들)
    diff 실패 · 변경 300건 초과면 rebuild_index() 로 물러난다

post-merge 훅은 s9 index rebuild 를 부른다(cmd_index) — 훅 파일은 harness/ 라 이 REQ
범위 밖이다. s9 index sync --since <rev> 를 붙여 두면 다음에 훅만 바꾸면 된다.

### 4. /api/catalog 기본 응답 창

지금은 보관 아닌 가시 행 전량이다(20469 부근). 20,000 문서면 18MB 가 15초마다 간다.
보드는 이미 하루 지난 완료를 화면에서 내리고 있으므로(REQ-20260827-057-62x6) 그 행들은
보내는 순간부터 버려지는 바이트다.

    기본(window=board): 열린 것 전부(open·in-progress·review·blocked) +
                        닫힌 것은 status_since 최신 400건
    ?window=all: 전량 — Docs 탭 진입·보관함·그래프·검색이 쓴다

응답은 배열 그대로 둔다(클라이언트의 Array.isArray 계약이 web/app/app.js:97 ·
web/app/tidy.js:46 두 곳에 있다). 창 사실은 헤더 X-S9-Catalog-Window: sent/total 로
알린다. 폴링 벨트(app.js 의 refreshCatalog)는 기본 창을, Docs 탭은 진입 시 한 번
window=all. _CATALOG_RESP 캐시 키에 window 를 더해야 한다 — 안 더하면 두 창이 서로의
본문을 받는다.

### 남는 값

문서 906건 기준 쓰기당 전량 재생성 0.27s 가 델타 한 줄 덧붙임과 색인 md 몇 개로 줄고,
그 비용이 문서 수를 따라가지 않는다. 20,000 문서에서 응답은 18MB 에서 1MB 아래로 내려간다.
