읽은 데까지의 사실:
  - 프로젝트 줄 자체는 선다(/api/projects 는 vault/projects/*.md 를 읽는다).
  - 그 행을 열면 loadDoc → GET /api/doc?id=PRJ-20260823-001 이 404 다(docs.js:405).
  - 서버의 `locate()` 는 ① catalog 의 path ② 파일 이름이 `<id>.md` 인지로 찾는다.
    프로젝트 문서의 파일 이름은 slug(`section9.md`)라 ②는 못 찾는다 — 즉 이 문서를
    여는 길은 **catalog 에 PRJ 행이 있을 때뿐**이다. catalog 에 없거나 path 가 낡으면 404.
  - 이 실행 자리(worktree)에는 index/catalog.jsonl 이 없어 서버가 새로 짓는다 —
    그 재생성이 project 문서를 담는지 확인이 필요하다.

다음 사람이 할 일: ① 서버를 띄워 /api/catalog 에 PRJ 행이 있는지 본다.
② 없으면 catalog 재생성이 vault/projects 를 담게 고친다(근원). 있으면 doc_visible 쪽을 본다.
③ 파일 이름이 slug 인 문서를 id 로 못 찾는 것 자체가 fallback 의 구멍이니 함께 판단한다.

### 뿌리를 실측했다 — 이 자리의 문서 목록이 **비어 있다**

접수 때 적은 짐작(catalog 에 PRJ 행이 없다)이 맞았는데, 이유가 더 단순했다.
worktree 뿌리로 서버를 띄워 API 를 직접 물었다:

```
/api/whoami                        200  {"user":"nicehugepark","role":"admin","registered":true,…}
/api/projects                      200  {"projects":[{"id":"PRJ-20260823-001","slug":"section9",…}]}
/api/doc?id=PRJ-20260823-001       404
/api/catalog                       200  []          ← 0행
```

`index/catalog.jsonl` 이 이 worktree 에 **없다.** 파생 색인이라 커밋하지 않으므로
worktree 를 만들 때 함께 만들어지지 않았고, 아무도 다시 짓지 않았다.

그래서 갈라진다. `/api/projects` 는 `vault/projects/*.md` 를 직접 읽어 줄이 서지만,
문서를 여는 `locate()` 는 ① catalog 의 path ② 파일 이름이 `<id>.md` 인지로 찾는다 —
프로젝트 문서의 파일 이름은 slug(`section9.md`)라 ②가 못 잡고, catalog 가 비었으니
①도 못 잡아 404 다. 목록은 서고 문서는 안 열리는 화면이 그래서 나온다.

같은 뿌리로 이 자리에서 함께 실패하는 것들: `short_ref`(코퍼스 0건 → 0으로 나눔) ·
`docs_recent_order` · `stalled_claim` · `progress_claims` 등. 전체 테스트 2518건 중
실패 16 · 오류 27 의 대부분이 이것이다.

### 할 일 둘

① **자리(worktree)를 고친다 — bin/ 몫이라 제안만 남긴다.** worktree 를 세울 때
   `s9 index rebuild` 로 파생 색인을 함께 짓거나, 서버가 색인 파일이 없을 때 첫
   `/api/catalog` 에서 스스로 짓게 한다. 지금은 빈 목록을 정상으로 돌려주고,
   그것을 받은 화면은 「문서가 하나도 없다」로 그린다 — 없는 것과 안 지은 것은 다르다.
② **문서 목록 없이도 열리게 할 것인가는 판단이 필요하다.** 파일 이름이 slug 인
   문서를 id 로 못 찾는 것은 `locate()` 의 구멍이다(프로젝트 문서만 해당). 색인을
   고치면 증상은 사라지지만 구멍은 남는다.
