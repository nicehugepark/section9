### 2026-09-02T18:58:53+09:00 response (agent: lead:claude-opus-5, by nicehugepark)

구현 (bin/s9 상시 계기 · bin/s9-audit-session · tests/test_metrics.py)

**무엇을 적나** — `state/metrics/YYYY-MM-DD.jsonl` 한 타임라인에 15초마다:
  api  api.anthropic.com 전 구간 (dns→tcp→tls→http, 단계마다 ms)
  ctl  1.1.1.1 로 바로 — 이름 풀이를 건너뛴 대조군
  dns  이름 풀이 단독 (풀린 IP 도 함께 — 주소가 바뀐 것도 사건이다)
  sys  부하·가용 메모리·TCP inuse/orphan/TIME_WAIT·소켓·임시 포트 폭·conntrack·열린 파일
갈래를 셋으로 나눈 것이 곧 판정이다: 셋 다 죽으면 회선, api 만 죽으면 저쪽,
dns 만 죽으면 이름 풀이, 밖은 멀쩡한데 늦기만 하면 timeout 의 전조.

**어떻게 서나** — 바깥 스케줄러를 쓰지 않기로 한 저장소라(REQ-20260825-096-62x6)
serve 감시자와 같은 방식이다: setsid + double fork, 잠금 하나로 멱등,
세션 시작 훅(ensure_metrics)이 매번 조용히 세운다. 제 잠금만 쓰고 serve 의
잠금·포트에는 닿지 않는다.

**쓰는 법** — `s9 metrics status | start | stop | sample | report --at <시각> | prune`.
report 는 그 시각 앞뒤 창의 표본으로 한 줄 판정을 낸다.

**053 과의 관계** — 접수는 'api error', 정정은 'request timeout' 이었고,
화면 증거는 `error type server_error` 였다. 그래서 판정에 '느려짐' 갈래를
더했다(닿긴 하는데 2000ms 초과가 창의 20% 이상). 이 계기가 다음번에
'로컬이 멀쩡했다'를 짐작이 아니라 기록으로 말한다.

**남는 공백 하나** — 기계가 다시 뜬 뒤 첫 세션이 열리기 전까지는 수집이 없다.
그 구간은 부팅 표식으로 드러나며, 메우려면 /etc/wsl.conf 의 boot command 가
필요하다(root 권한 + wsl --shutdown). 사람의 손이 필요한 일이라 파생으로 뗀다.
