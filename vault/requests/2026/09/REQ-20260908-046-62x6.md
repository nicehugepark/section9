■ ① 지금 무엇이 어디에 사는가 (확인)

  `s9 new` 본문의 절대경로가 ingest_assets(bin/s9.py:14074)로 여기 옮겨지고 본문이
  `assets/<문서ID>/<파일명>` 상대경로로 재작성된다. 여기 들어가면 id·날짜·project·
  가시성(doc_visible)·검색·/api/asset 서빙·.trash 수명이 전부 따라온다.

갈래를 정하는 코드는 없다. 첨부 명령을 쓰면 앞, 파일을 직접 쓰면 뒤 — 그뿐이다.

■ ③ 검색 (확인)
"하나도 없다"는 아니다. 정확히는 **문서에 붙은 것은 찾히고 프로젝트 에셋만 밖에 있다.**
· `s9 search <kw>` = catalog 메타(id·title·summary·tags·project·slug)만. 에셋 0.
· `s9 search <kw> --body` = 문서 본문 + **첨부 추출 본문 사이드카**
  (assets/<문서ID>/.text/<파일명>.txt, asset_texts() bin/s9.py:14022). pdf·py·txt 는
  내용까지 찾힌다.
· 그런데 png 는 추출 0자라 사이드카를 만들지 않는다(의도된 설계, bin/s9.py:14000).
  **870개 중 860개는 내용 검색 대상이 아니다.** 다만 ingest 가 본문에
  `assets/<REQ>/<파일명>.png` 를 적어 두므로 **파일명은 --body 로 찾힌다** — 이미지에
  대해 오늘 작동하는 축은 이 하나뿐.
· projects/<slug>/assets/ 는 두 모드 어디서도 안 훑는다. cmd_search 가 프로젝트에서
  보는 것은 CONTEXT.md 하나뿐(bin/s9.py:13081-13097).
· 대시보드에는 목록 API 가 없다. /api/asset·/api/asset-text 는 (문서ID, 파일명)을
  **이미 알아야** 부를 수 있다.
축 넷의 현황: 이름=첨부만 ○ / 종류=× (TYPE_GROUPS 는 있으나 필터로 노출 안 됨) /
만든 요청=첨부는 경로에 구조적으로 ○, 프로젝트 에셋은 × / 만든 때=× (문서 날짜가 대리).
**판정: 같은 문이다 — 다른 문을 내지 않는다.**
근거 셋. ① 이 하네스에서 산출물의 정체성은 "그것을 만든 요청"이다. 사람이 실제로 묻는
말("그때 만든 그 영상")은 REQ 로 풀리지 파일 이름으로 풀리지 않는다. ② 다른 문은 두 번째
인덱스를 뜻하고, 두 번째 인덱스는 원본과 어긋날 수 있는 두 번째 진실이 된다 — 이 저장소는
index/ 를 gitignore 하고 첨부 텍스트를 catalog 에서 뺀 판정을 이미 두 번 내렸다.
③ 기각안: (A) `s9 assets find` + 별도 에셋 인덱스 — 유지 대상 하나 증가, 묻는 자리 둘.
(B) 에셋을 catalog.jsonl 에 싣기 — 대시보드가 폴링마다 전량을 받으므로(지금 1.4MB) 상시
전송량이 에셋 수에 비례해 는다. bin/s9.py:13985 가 이미 같은 이유로 기각한 안이다.
같은 문에 **면(facet)만 더한다**: `--attach`(첨부 보유) · `--type image|doc|code` 를
질의 시점에 파일시스템에서 계산(사이드카를 그때 읽는 방식 그대로). 1,479 문서 stat ≈ 수십 ms.

■ ④ 권고
[REQ-045 무게] 전제를 깨지 않고 셋만 한다. (1) **캡처 규격 상한** — `s9 shot` 이 저장 전에
폭 1280 으로 줄이고 PNG-8 로 양자화한다. 상위 4개가 4~5MB 인 것은 1440 전체페이지 원본이라
그렇고, 5배만 줄여도 에셋 9.3→1.9MB/일, .git 19.7→12.3MB/일, 1GB 도달이 2026-10-14 에서
~11월 하순으로 밀린다. 값은 캡처 화질뿐이고 판정에 쓰는 그림은 1280 으로 충분하다.
(2) **파일당 상한 게이트** — s9-git-gate 에 10MB 경고·25MB 거부. 100MB 벽을 commit 시점의
보이는 거절로 바꾼다. 이력에 들어간 뒤에는 이력 재작성 말고 길이 없으므로, 이것이 재발
방지의 본체다. (3) **세는 자리 하나** — digest 에 "에셋 총량 · 일 증가율 · 최대 파일" 한 줄.
숫자가 안 보이면 다음에도 15일 뒤에야 안다.
채택하지 않는 안과 그 값: **Git LFS** — 파일은 제자리에 있고 경로로 commit 되니 전제를 절반만
깨지만, ① 어느 머신에서든 도는 것이 목표인 하네스에 `git lfs` 설치 의존이 생기고, 없으면
그림 자리에 포인터 텍스트가 들어가 "깨진 문서"로 보인다 ② GitHub LFS 무료 1GB/월 저장·대역이
9.3MB/일이면 ~107일에 소진되고 clone 마다 대역을 먹는다 ③ note 마다 commit 하는 sync 루프에
독립적으로 실패하는 두 번째 네트워크 대상이 생긴다. **지금은 안 쓴다.** 다시 볼 조건은
"한 종류의 산출물이 상시 25MB 를 넘을 때"(=영상)이고, 그때도 `*.mp4|*.mov` 같은 좁은 패턴에만
걸고 `*.png` 에는 절대 걸지 않는다. **외부 저장(S3 등)** — 문서가 파일 대신 URL 을 갖게 되므로
전제를 완전히 깬다: vault 가 자립성을 잃고, `--body` 검색이 내용을 못 읽고, 오프라인에서
문서가 비고, 죽은 URL 이 문서를 조용히 빈 것으로 만든다. 글자로 읽을 필요도 오프라인에서 볼
필요도 없는 원본 영상 한 종류에만 방어 가능하고, 그 밖에는 값이 이득보다 크다.

[REQ-046 검색] 같은 문으로 간다. 셋. (1) **뿌리 고침 — 산출물은 projects/<slug>/assets/ 에서
태어나지 않는다.** 요청이 만들게 한 문서·영상·미디어는 그 요청에 붙인다
(`s9 note <REQ> --attach <파일>`). 그러면 id·날짜·소유 요청·가시성·검색·서빙·수명이 공짜로
따라오고, 오늘 작동하는 파일명 축이 그대로 듣는다. projects/<slug>/assets/ 는 원래 역할
(CONTEXT.md 가 가리키는 프로젝트 상시 참고자료 — bin/s9.py:18796 이 이미 그렇게 적어 뒀다)로
되돌리고, 거기 남길 것은 **CONTEXT.md 에서 참조되어야 한다** — CONTEXT.md 는 검색 대상이므로
그것이 그 디렉토리의 이미 작동하는 문이다. 지금 있는 014-sync-design/ 14파일은 그 요청 문서의
첨부로 옮기는 것이 맞다. (2) **면 두 개 추가** — `s9 search --attach`, `--type image|doc|code`
(TYPE_GROUPS 재사용, 질의 시점 계산, catalog 불변). 축 넷 중 종류·만든 때가 이걸로 선다
