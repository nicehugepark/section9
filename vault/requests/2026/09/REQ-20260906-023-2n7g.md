`[2026-09-06 17:00:15 KST - 타치코마]`

결론부터 말씀드리면, 그 방식으로는 clone 이 가벼워지지 않고 이력 삭제는 손해입니다. 목표가 「가벼운 clone 과 문서 없는 이력」이라면 답은 브랜치 분리가 아니라 저장소 분리입니다.

**브랜치로는 안 되는 이유.** git 의 branch 는 한 저장소 안에서 같은 객체 저장소를 나눠 씁니다. `git clone` 은 기본으로 모든 branch 를 받으므로 dev 에 문서가 있으면 main 만 원하는 사람도 dev 까지 받습니다. `--single-branch` 를 붙이면 피할 수 있지만 그것은 받는 쪽의 선택이고 저장소 쪽에서 강제할 수 없습니다. 「전체 브랜치를 다 가져가지 않는 이상」이라는 조건이 기본값에서 이미 깨집니다.

**이력을 지울 필요는 없습니다.** 실측으로 .git 은 154MB 이고, 커밋 1143개 중 제품 경로에 닿는 것은 370개입니다. `git filter-repo` 로 제품 경로만 남기면 그 370개의 코드 이력(blame·bisect)을 지키면서 문서가 한 번도 실리지 않은 이력이 됩니다. 저장소를 지우고 처음부터 시작하면 그 이력을 잃는 대신 얻는 것이 없습니다.

**「main 에 정리해 넘기기」의 비용.** 이것은 앞서 평가한 장수 release 브랜치와 같은 일입니다. 정리를 사람이 하면 cherry-pick 이고, 스크립트가 하면 생성 브랜치입니다. 어느 쪽이든 같은 저장소 안에 dev 가 있는 한 clone 무게는 그대로입니다.

**권고안.**

1. **제품 저장소.** 지금 이력에서 filter-repo 로 제품 경로(bin·web·harness·docs·tests·pyproject·README)만 남긴 새 저장소를 만듭니다. 여기서 태그와 릴리스를 합니다. clone 이 가볍고 이력에 문서가 없습니다.
2. **데이터 저장소.** 지금 저장소가 그대로 vault·users·projects 의 동기화 저장소가 됩니다. `s9 sync` 는 이쪽만 바라봅니다.
3. **그때까지의 즉시 완화.** 구조를 바꾸기 전이라도 `git clone --filter=blob:none` 으로 받으면 파일 내용은 필요할 때만 내려받아 clone 이 가볍습니다. GitHub 이 지원합니다.

**분리의 비용은 M~L 입니다.** `s9 sync` 와 pull 뒤 index 재생성 훅이 vault 를 코드와 같은 저장소로 전제하고 있고, users/ 와 projects/ 를 어느 쪽에 둘지, WSL 과 맥 두 머신을 같은 시점에 옮기는 절차가 필요합니다. 실행을 결정하시면 파생 요청으로 갈라 각각 S/M 으로 진행하겠습니다. 이번 검토는 요청 문서에 기록하고 닫았습니다.
