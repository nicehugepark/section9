**① 왕복 구조.** 지금 상시 폴은 boot.js catalog 15초·serveinfo 20초·serveguard 20초·usage 60초, terminal 탭 agents 10초·agentstream 2.5초·chat/target 수초, audit tail 2.5초, target.js 2초, timezone 30초 — 탭 하나가 분당 20~40개의 새 TCP 연결을 만듭니다. 이 환경의 비용은 바이트가 아니라 연결 수와 취소 수이므로, `/api/events` SSE 하나로 서버가 버전 벡터 `{catalog_seq, code_stamp, guard_ts, agents_mtime, doc_mtime}` 를 바뀔 때만 밀어 주고 화면은 바뀐 항목만 fetch 하면 상시 연결이 탭당 1개, 취소는 0에 가까워집니다. 설계 조건 셋: (a) 버전 벡터는 서버 스레드 하나가 1~2초마다 계산해 Condition 으로 배포 — 지금 `/api/stream/sse` 처럼 연결마다 0.25초 파일 폴링을 하면 REQ-20260901-020-62x6 의 좀비 스트림 CPU 문제가 재현됩니다. (b) 이벤트에 `id: <seq>` 를 실어 재연결 시 `Last-Event-ID` 로 「그 뒤 무엇이 바뀌었나」를 첫 이벤트로 받습니다 — 끊김 복구가 fetch 1회로 끝납니다. (c) 5분 만기 재연결에 지터(0~5초)를 주어 여러 탭이 동시에 SERVE_BACKLOG(128)를 넘기지 않게 합니다. **끊길 때 비용**: 재연결 1왕복(RST 노출) + 벡터 대조 fetch 1~3회. FIN 이 서버에 안 오는 이 환경의 좀비 위험은 sse_open 의 세대 은퇴와 `_peer_gone` 을 그대로 재사용해 막고, 3회 연속 실패 시 30초 안전 폴로 후퇴합니다(terminal.js 의 기존 계약과 동일). **단계**: 먼저 (1) frontend 가 진행 중인 탭 범위·document.hidden 가드·간격 통일, (2) `/api/events` + producer 스레드 + catalog·serveinfo·serveguard·usage·agents 폴을 「알림 받으면 fetch」로 교체하고 60초 안전 폴 하나만 남김. 뒤에 (3) audit tail·terminal stream 같은 세션별 내용 스트림은 수명이 달라 채널에 합치지 않음(이득이 실측될 때만), (4) 카탈로그 증분은 (2) 뒤 실측이 요구할 때만.

**② 카탈로그.** `_send_catalog`(bin/s9.py:29300)가 이미 `Cache-Control: no-cache` + 뷰어별 본문 md5 ETag 로 304 를 냅니다. 클라이언트 `s9Fetch("/api/catalog?…")`(app.js:196 부근)는 cache 옵션이 없어 브라우저가 If-None-Match 를 자동으로 붙이고, 304 는 JS 에 캐시 본문 200 으로 보이므로 net.js 의 「2xx 빈 본문 재시도」에도 걸리지 않습니다. 리드 실측 62KB 는 curl 의 cold 값입니다. 캐시 키 (seq, 뷰어, archived, window) 의 seq 는 vault mtime 지문으로 2초 스냅샷마다 판정되므로 세대 번호는 이미 있고, ①의 `catalog_seq` 는 이 값을 그대로 씁니다. 증분을 지금 만들지 않는 까닭: 작업 중 304 적중률이 낮은 것은 사실이나 그때의 62KB gzip 은 0.3초이고 문제의 본체(리셋·재시도)와 무관하며, 삭제·가시성 변경 행을 따로 실어야 해 두 번째 직렬화 경로가 생깁니다. 확인 항목: Playwright/DevTools 「캐시 사용 안 함」 상태에서는 If-None-Match 가 안 붙으므로 QA 실측 표에 304 비율 열을 넣어 주십시오.

**③ 환경.** mirrored 는 127.0.0.1 이 virtioproxy 중계를 지나지 않게 하므로 30~50% 실패는 사라져야 합니다(deep-diver 대조군 0/70). 그러나 왕복 감소는 여전히 필요합니다: (a) 원격 머신의 리셋 1회는 test_id_realscale 부하 시험 중이라 accept backlog/스레드 폭주 계열이고 연결 수 감소가 그쪽 답이기도 합니다. (b) port-guard 가 오늘 16:02~16:06 동적 포트 9846/16384(60%) 상승을 기록했습니다 — 분당 수십 개의 짧은 연결이 원인이고 mirrored 는 이를 줄이지 않습니다. (c) 하네스는 다른 설치 환경에서도 돌아야 합니다. **077 권고 한 줄**: 「networkingMode=mirrored 로 바꾸는 것을 권합니다 — 되돌리기는 .wslconfig 한 줄이고, 지금 값을 고정한 까닭(NAT 실패 이력)은 mirrored 에 해당하지 않습니다(mirrored 는 NAT 의 대안이지 NAT 가 아닙니다); Windows 11 22H2 이상이어야 하고 VPN·Hyper-V 방화벽에서 localhost 접근이 막히면 알려 주시면 리드가 60회 프로브로 잰 뒤 판정합니다.」
