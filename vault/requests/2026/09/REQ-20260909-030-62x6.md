product-owner 판정 — Jira 동기화 수준.

문제 재서술: Jira 에서 보이는 것이 제목·상태뿐이라 티켓만으로는 무엇을 왜 하는지 모른다. 단 캡처 MP1-4 는 description 이 접힌 화면일 수 있다(현재도 summary·goal·담당/크기/상태가 ADF 로 나간다) — 먼저 확인 포인트: 이슈를 열어 Description 을 펼쳤을 때 goal 이 보이면 「비어 보임」은 표시 문제이고 수준 설계와 별개다.

① 동기화 수준 — 찬성. 프로젝트 frontmatter jira: 에 sync_level 한 필드. 단계는 자유 본문이 아니라 허용 목록이다.
- basic: summary 「[REQ-id] 제목」· 상태 transition · label s9-<REQ> · description 은 id 와 대시보드 링크 한 줄.
- summary: + description 에 summary·goal·size·priority·담당·현재 상태. (= 지금 나가는 것)
- body: + Original 원문(사람이 쓴 프롬프트) + 확인 포인트(review 전이 note)·done note 를 Jira 코멘트로. Notes 전량·subagent/tdd 노트·첨부 파일은 어느 단계에도 싣지 않는다 — 에이전트 산출물에는 내부 경로·로그가 섞인다. 첨부는 파일명만.
body 는 security-engineer 가 뺀 것이라 옵트인 + 비밀 패턴 스캔(SECRET 검사 한 곳 재사용) 통과가 전제. Jira priority 필드 매핑은 사이트마다 스킴이 달라 non-goal.

② 기본값: summary. 보안 판정을 뒤집을 새 사실이 없고, 주인의 불만은 접힌 description 으로 설명될 가능성이 있다.

③ 방향: 이 요청은 나가는 것만. Jira 코멘트→우리 노트 pull 은 non-goal — 지금 Jira 에서 코멘트를 쓰는 사람이 없어 임팩트를 셀 수 없고, 코멘트 폴링·루프 방지·actor 귀속이 비용을 키운다. direction 필드는 상태에만 적용.

④ 갱신 시점: description 은 생성 때 + 제목·summary·goal·size 가 바뀔 때 덮어쓴다(문서가 진실, Jira 는 거울 — DOC-20260908-002-62x6 원칙 1). 노트는 덮어쓰지 않고 코멘트 추가, 노트 1건 = 코멘트 1건, 멱등 키는 노트 ts. 노트마다 호출하지 않고 전이 시점에 outbox 로 몰아 보낸다.

⑤ 파생 후보 — (임팩트×확신도)/비용, 각 1~5:
1. [S] 제목 정리 뒤 Jira 반영 — 주인 두 번째 지적(프롬프트 원문이 그대로 summary 가 됨). create_on 을 open→in-progress 전이로 늦추거나, title 변경 시 summary 재push. 4×5/1 = 20.
2. [S] Description 가시성 — MP1-4 실물 확인 + ADF 첫 줄에 goal(접혀도 보이게). 4×4/1 = 16.
3. [M] sync_level 필드 + basic/summary 분기 + ④ 의 덮어쓰기·코멘트 추가 경로. 3×4/2 = 6.
4. [M] body 단계 — Original·확인 포인트 코멘트, 비밀 스캔 게이트. security-engineer 판정 뒤. 3×2/3 = 2.
5. Jira 코멘트 pull: 2×2/4 = 1 → 보류.

non-goals: Notes 전량 동기화 · 첨부 업로드 · priority 필드 매핑 · 코멘트 pull.
AC: 프로젝트 문서에 sync_level 이 없으면 summary 로 동작 / basic 은 description 에 goal 이 없다 / body 는 sync_level: body 가 명시된 프로젝트에서만 Original 이 나가고 비밀 패턴이 잡히면 push 하지 않고 노트에 사유 / 제목 변경 후 push 하면 Jira summary 가 새 제목이다.
