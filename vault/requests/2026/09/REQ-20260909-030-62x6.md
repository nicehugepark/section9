AWS(AKIA), JWT(eyJ…), PRIVATE KEY 블록, Bearer/Authorization 헤더, URL 안의 user:pass@ 를 같은 표(TOKEN_PATTERNS)에 추가 — 검사는 한 곳(secret_leak 과 공유)에 둔다. (b) 절대 경로(/home/<계정>/…, C:\Users\…)와 홈 디렉터리 — 계정명 노출이라 redact. (c) 이메일 주소 — 요청 user 필드·세션 바인딩에 섞이므로 redact. (d) 세션 id·머신 이름·내부 host:port(localhost:포트 포함). (e) 첨부(--attach 파일·assets/ 경로·이미지)는 전량 제외 — 캡처 png 에는 화면의 다른 요청·비밀이 찍혀 있고 검사로 걸러지지 않는다. 링크도 내지 않는다(내부 대시보드 URL 은 (d)). 검사 결과 hit 가 하나라도 있으면 redact 하고 보내는 것이 아니라 그 항목을 보내지 않고 REQ 노트에 blocked 사유를 남긴다(기본 거부; redact 는 알려진 패턴만 잡는다).
② Original 대 Notes — Original 이 더 위험하다. 사람이 친 프롬프트 원문에는 붙여 넣은 로그·토큰·경로·다른 사람 이름이 검사 패턴 밖의 형태로 들어온다(TOKEN_PATTERNS 는 4개 패턴이고 자유 문장은 못 거른다). Notes 는 에이전트가 쓴 구조화 보고라 형식이 예측 가능하고 redact 가 통한다 — 다만 label=subagent/patch 노트에는 diff·파일 경로가 있으니 (b) 검사가 필수. 권고: 단계는 셋 — L0 없음 / L1 이슈·상태(현행 허용 목록) / L2 이슈·상태 + Notes 중 label=response·review 카드만. Original 은 단계에 넣지 않는다(옵션 자체를 만들지 않는다 — 있으면 누군가 켠다). 코드 패치(label=patch)·첨부는 L2 에서도 제외.
③ 기본값 — L1(현행). L2 는 프로젝트 단위 옵트인(project jira set sync_level=notes)이고 사용자 단위로 켜지 않는다 — 요청 문서에 다른 사용자 노트가 섞이므로 한 사람의 취향이 타인의 글을 내보내면 안 된다. 켤 때 만료일 필수(jira_token_expires 와 같은 방식, 기본 90일) — 만료 후 L1 로 자동 복귀.
④ description 덮어쓰기 vs 코멘트 — 덮어쓰기는 Jira 쪽에서 사람이 고친 description(수용 기준·담당자 메모)을 지운다. 실패 시나리오: PM 이 Jira 에서 description 에 일정을 적음 → 다음 전이가 PUT description → 삭제, Jira 이력에는 남지만 화면에서 사라짐. 코멘트 추가 방식이 맞다: 노트 1건 = 코멘트 1건, 멱등 키(노트 ts 를 코멘트 본문 머리 또는 property 로) 로 중복 방지. description 은 최초 생성 시 1회만 쓰고 이후 갱신하지 않는다(title/summary/goal 변경도 코멘트로 알린다). 코멘트도 삭제하지 않는다 — 우리가 쓴 것만 갱신하고, 남이 쓴 것은 읽지도 않는다.
