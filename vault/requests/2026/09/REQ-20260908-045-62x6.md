■ 실측: 파일 시스템은 아프지 않다 (ext4, 이 머신에서 잰 값)
한 디렉토리에 파일 N개를 만들고 잰 것:
   N=1,000    ls -1 0.00s · ls -la 0.00s · find 0.00s
   N=10,000   ls -1 0.00s · ls -la 0.03s · find 0.00s
   N=50,000   ls -1 0.02s · ls -la 0.16s · find 0.03s
   N=200,000  ls -1 0.13s · ls -la 0.66s · find 0.11s · 디렉토리 inode 5.8MB
ext4 는 dir_index(htree)라 한 파일 찾기는 N=200,000 에서도 0.00s 다. **평면 누적의
한계는 파일 시스템이 아니다.** git 도 아니다 — `git status` 는 track 3,113 파일에서
0.00s 다. 실제 한계는 셋이고 순서가 있다:
 1) **사람의 눈** — 수백 entry 부터. 화면 한 장에 안 들어오면 목록은 목록이 아니다.
    지금 가장 뚱뚱한 디렉토리가 이미 여기 있다(아래).
 2) **셸 glob(ARG_MAX)** — 이 머신 2,097,152바이트. 파일명+경로 평균 40바이트면
    `dir/*` 가 **약 50,000개**에서 "Argument list too long" 으로 깨진다. 성능이 아니라
    벽이고, 그때까지 쓰던 스크립트가 그날 갑자기 죽는다.
