문제 재서술: 요청의 상태·존재를 Jira 를 보는 사람에게도 보이게 하되, 이 하네스의 전이 규칙(TDD 게이트·반려 루프·goal 의무)이 Jira 라는 두 번째 입구로 우회되지 않게 한다.

### ① 1차 범위
넣는다: (a) 계정 연결 — 개인 토큰은 `s9 secret`(키 `jira_token`), Jira 사이트·프로젝트 키는 프로젝트 문서 프론트매터 `jira:` (b) 요청→이슈 생성(우리→Jira) (c) 카드·문서에 이슈 키 링크 표시(REQ 프론트매터 `jira_issue`·`jira_url`) (d) 상태 동기화 우리→Jira 단방향.
뺀다(non-goals): Jira→우리 역방향 전이(2차) · 양방향 충돌 해결 · 코멘트/첨부/담당자 동기화 · Jira 에서 만든 이슈 가져오기 · webhook 수신(1차는 push 만) · Notion · Jira 워크플로 자동 생성.
근거: 우리 문서가 원본(source of truth)이다. Jira 에서 바꾼 상태를 그대로 받으면 do_transition 의 가드(review 진입 TDD N/N, goal 없는 done 거부, 300자 규율)가 전부 우회된다 — PROTOCOL 19조 「검사를 우회하지 않는다」와 정면 충돌. 역방향은 「Jira 의 변경을 전이 *요청*으로 받아 가드를 통과시키고, 거부되면 Jira 를 되돌린다」는 설계가 먼저 서야 하므로 2차.

### ② 방향 기본값과 옵션
- 프로젝트 설정 `jira.sync = off | push(기본) | pull | both`. 1차 구현은 off/push 만, pull/both 는 값만 예약.
- 설정 단위: **방향·상태 매핑·내보내기 규칙은 프로젝트별**(Jira 프로젝트와 워크플로가 프로젝트에 속하므로; 사람마다 다르면 한 보드에 규칙이 둘 생긴다). **개인별은 자격증명과 「내 요청을 내보낼지」 opt-in 뿐**(`s9 user config jira_export on|off`, 기본 on — 토큰이 없으면 자동 off).
- Jira 는 거울이지 게이트가 아니다: Jira 호출 실패는 우리 전이를 막지 않고 REQ 노트 한 줄로 남긴다.

### ③ 상태 대응 원칙
- 고정 매핑 불가(워크플로·상태명이 프로젝트마다 다름). 다만 Jira 의 status category 3개(To Do · In Progress · Done)는 모든 워크플로에 공통이므로 **기본 매핑은 카테고리 기준**: open→To Do / in-progress·blocked·review→In Progress / done·cancelled→Done.
- 정밀 매핑은 **프로젝트 owner** 가 프로젝트 문서 `jira.status_map`(우리 상태→Jira 상태명)으로 정하고, 빠진 항목은 카테고리 기본으로 fallback. 워크플로가 그 전이를 허용하지 않으면 실패를 노트로 남기고 넘어간다. blocked 를 flag(impediment)로, cancelled 를 resolution 으로 표현하는 것은 2차.

### ④ 어떤 요청이 나가나
프로젝트에 Jira 가 연결됨 ∧ 요청 creator 에게 토큰 있음 ∧ 프로젝트 `jira.export` 규칙 통과. `jira.export = all(기본) | size:M+ | manual`. 프로젝트에 Jira 를 연결하는 행위 자체가 opt-in 이므로 기본 all 이 주인 원문(「요청이 생기면 동일하게 발번」)에 맞다. 다만 이 저장소는 오늘 하루 요청이 70건(REQ-20260908-070-62x6)이라 all 이면 Jira 에 하루 70 티켓 — section9 프로젝트 자체는 `size:M+` 로 시작하길 권한다. 개별 제외는 `--no-jira`. 파생 REQ(parent 있음)는 Jira 서브태스크가 아니라 issue link 로(서브태스크 타입은 프로젝트마다 다름).
