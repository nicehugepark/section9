### ② 방향 기본값과 옵션
- 프로젝트 설정 `jira.sync = off | push(기본) | pull | both`. 1차 구현은 off/push 만, pull/both 는 값만 예약.

- Jira 는 거울이지 게이트가 아니다: Jira 호출 실패는 우리 전이를 막지 않고 REQ 노트 한 줄로 남긴다.

### ③ 상태 대응 원칙
- 고정 매핑 불가(워크플로·상태명이 프로젝트마다 다름). 다만 Jira 의 status category 3개(To Do · In Progress · Done)는 모든 워크플로에 공통이므로 **기본 매핑은 카테고리 기준**: open→To Do / in-progress·blocked·review→In Progress / done·cancelled→Done.

  - 대안 OAuth 먼저 — 버림: 앱 등록·redirect·refresh 3단계가 붙는데 API token 은 한 줄이고 권한은 그 사람과 같다.
- **프로젝트 연결** = `vault/projects/<slug>.md` frontmatter `jira: {site, project_key, issue_type, direction, create_on, status_map}`. 프로젝트 문서는 이미 catalog·검색·git 동기화 대상.
  - 대안 CONTEXT.md — 버림: 자유 텍스트라 기계가 못 읽음. 대안 users config — 버림: 연결은 팀 공유물, 자격만 개인 것.
- 원칙: 비밀은 사람에게, 연결은 프로젝트에. 누가 전이하든 **그 사람 자격**으로 같은 Jira 프로젝트에 쓴다.

### ② 이슈 생성
- 시점: `s9 new request` 직후(주인 원문 「요청이 생기면」). 프로젝트 옵션 `create_on: open|in-progress`, 기본 open.
  - 대안 in-progress 착수 시만 — 버림: 원문과 다르고 open→review/blocked 로 가는 요청은 이슈가 없게 된다.
- 자격: 요청 `user:` 의 secret → Jira reporter 가 그 사람. 자격 없으면 생성하지 않고 `pending: create` 만 남긴다.
- 멱등: Jira 는 idempotency key 가 없으므로 이슈에 label `s9:<REQ-id>` 를 붙이고, 생성 전 JQL `project=KEY AND labels="s9:<REQ-id>"` 로 선검색. 재시도가 두 번 만들지 못한다.
- 실패(오프라인·401/403·timeout 5초): 요청 생성은 **막지 않는다**. 문서에 `jira: {pending: create, last_error, attempts, next_at}` 를 남기고 워처가 backoff(30초×2^n, 최대 1시간) 재시도. 카드에는 「Jira 미연결」 배지.
  - 대안 동기 호출 실패 시 요청 생성 거부 — 버림: 오프라인에서 일이 멈추고 문서-진실 원칙에 어긋남.

### ③ 문서 필드와 표시
```
jira:
  site: acme.atlassian.net
  key: PROJ-123
  url: https://acme.atlassian.net/browse/PROJ-123
  status: "In Progress"        # Jira 상태명 원문
  synced_at: 2026-09-08T21:30:00+09:00
  synced_by: s9 | jira         # 마지막 동기화를 일으킨 쪽
  pending: "" | create | push
  last_error: ""
```
- 서버 `/api/...` 카드 페이로드에 `jira` 블록을 그대로 싣고, web/app/*.js 는 **그 블록만** 읽는다(링크=`url`, 배지=`status`/`pending`). 문서 화면도 같은 필드로 링크. 브라우저는 Jira 를 직접 부르지 않는다.
  - 대안 카드 렌더 시 Jira 실시간 조회 — 버림: 카드 N개=호출 N회, 오프라인이면 화면이 깨지고 토큰이 브라우저로 흐른다.

### ④ 상태 동기화
- **우리→Jira(push)**: do_transition 성공 후 이벤트 기록 지점 한 곳에서 `jira_push(doc)` 호출 — 즉시 1회 시도, 실패면 `pending: push` + 워처 재시도. do_transition 은 네트워크로 막히지 않는다.
  - 대안 전이 전 동기 호출·실패 시 전이 거부 — 버림: ②와 같은 이유.
- **Jira→우리(pull)**: **폴링**. 워처 안 `jira_poll` 스텝, 기본 60초(`jira.poll_sec`), site+project 당 JQL 1회 `project=KEY AND labels in (s9:*) AND updated >= -<2×주기>`. 자격은 연결 등록자(`jira.registered_by`) 우선, 없으면 자격 있는 아무 사용자.
  - 대안 webhook — 이 제품의 기본으로는 버림: 공개 URL + Jira 관리자 권한이 필요하고 로컬 대시보드는 대개 없다. 공개 URL 이 있는 설치를 위해 후순위 옵션으로 두되, 수신 경로만 다르고 적용은 같은 `jira_apply_remote()` 한 함수.
- **방향 옵션** `jira.direction: push|pull|both`, 기본 `push`. 둘 다 지원하고 선택은 프로젝트별. 기본을 push 로 두는 이유: 문서가 진실인 제품에서 밖→안 변경은 옵트인이어야 한다.
- **충돌 규칙(both)** — 진실은 문서:
  (a) Jira 변경 감지 시 문서의 마지막 전이 시각 > `synced_at` 이면 문서가 이긴다: 우리 상태를 다시 push 하고 Jira 쪽 변경은 노트로만 남긴다.
  (b) 우리만 바뀜 → push. (c) Jira 만 바뀜 → `do_transition(auto=True, note='jira: <who> → <status>')`.
  - 전이 가드(TDD 미완·goal 없음·확인 포인트 길이)에 걸리면 전이하지 않고 `jira.status` 만 갱신 + 카드 「Jira 와 다름」 + 노트. 가드는 우회하지 않는다.
  - 루프 방지: pull 이 일으킨 전이는 `synced_by: jira` 로 표시하고 push 훅이 이를 보고 건너뛴다.
  - 매핑 없는 Jira 상태(예: QA) → 전이 없이 `status` 만 기록.
  - 대안 last-writer-wins 시각 비교 — 버림: Jira 서버와 로컬 시계가 다르고 문서-진실 원칙에 어긋난다.

### ⑤ 상태 매핑
- 기본 표는 코드 한 곳 `JIRA_STATUS_MAP_DEFAULT`: open→To Do · in-progress→In Progress · review→In Review(없으면 In Progress) · blocked→상태 유지+label `blocked` · done→Done · dropped→Done(resolution Won't Do).
- 프로젝트 표 `jira.status_map`(frontmatter)이 있으면 키 단위로 덮어쓴다. 역방향은 자동 도출, 중복이면 `jira.pull_map` 으로 명시.
- Jira transition id 는 워크플로마다 다르므로 **이름으로 GET transitions 에서 찾아 id 로 호출**. 이름을 못 찾으면 `pending: push` + last_error 에 후보 이름 목록.
  - 대안 사용자 전역 설정 — 버림: 워크플로는 Jira 프로젝트가 소유한다.

### ⑥ 파생 요청 (S/M) 과 의존 순서
1. S `s9 jira check` — secret 키 규약 + site 접속·자격 확인.
2. S 프로젝트 frontmatter `jira:` 스키마 + `s9 project jira set <slug> --site --key [--direction --create-on]` + 검증.
3. M 이슈 생성 — `s9 new request` 훅 + label 멱등 + `pending/재시도` 워처 스텝 + frontmatter 기록. (1,2 뒤)
4. S 카드·문서 표시 — API 페이로드 `jira` + web 링크/배지. designer·ux-writer·tech-writer·translator 넷 소집. (3 뒤)
5. M push — do_transition 훅 + 기본 표 + 프로젝트 표 + 이름→id 전이. (3 뒤)
6. M pull — 폴링 스텝 + 충돌 규칙 + 루프 방지. (5 뒤)
7. S 기존 요청 잇기 `s9 jira link <REQ> <KEY>` / `--backfill`. (3 뒤, 4~6 과 독립)
8. 후순위 옵션: OAuth 3LO · webhook 수신 엔드포인트.

### 비기능 숫자·제약
- Jira 호출 timeout 5초 · 워처 jira 스텝 상한 10초(넘으면 다음 회차) · 폴링 60초 · backoff 최대 1시간 · 요청 생성 추가 지연 ≤5초.
- 의존성 추가 없음(stdlib urllib). 하네스 무관: 훅·Claude 에 기대는 자리 없이 bin/s9.py + 워처 안에서 끝난다.
- 비밀은 `s9 secret run` 치환으로만 쓰고 로그·노트·frontmatter 에 값이 남지 않게 `secret_leak` 검사 대상에 포함.
