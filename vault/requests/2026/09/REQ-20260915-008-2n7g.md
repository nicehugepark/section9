## Original

부모 REQ-20260915-004-2n7g 의 ② 를 갈라 세운다.

실제 사고 2026-09-15: 세션 A 가 13:59:50 에 commit 230e94a68 로 tests/test_stdlib_only.py 를 닫았고, 세션 B 가 14:01 에 19926f3bd 로 같은 파일을 덮었다(내용이 같아 잃은 것은 없었다).

지금의 검사(bin/s9-guard 의 concurrent_gate)가 보는 것은 **작업 트리**다 — live_workers 가 있고 담기는 파일의 mtime 이 FRESH_SEC(900초) 안이면 막는다. A 는 이미 commit 을 마쳐 작업 트리에 아무것도 남기지 않았으므로 검사에 걸릴 것이 없었다. 즉 「남이 아직 쓰는 중」은 보지만 「남이 방금 써서 넣었다」는 못 본다.

판단(부모 노트에 적은 대로): 그 commit 해시를 짚어 멈추는 쪽이 맞다. 다만 **누가 담았는지**를 가릴 신호가 지금 없다 — commit 의 author 는 사람·머신까지만 말하고 세션을 말하지 않아, 같은 컴퓨터의 두 세션이 같은 author 로 찍힌다. 그래서 이 요청의 몫은 둘이다: ① commit 에 세션을 남긴다(세션 바인딩에 그 sha 를 적는 쪽이 이력을 더럽히지 않는다) ② concurrent_gate 옆에 검사를 하나 세운다 — 담기는 코드 파일을 마지막으로 만진 commit 이 최근이고 내 세션의 것이 아니면, 그 해시·시각·메시지 한 줄을 적고 멈춘다. 빠져나가는 길은 종전과 같은 표(S9_ALLOW_CONCURRENT).

데이터 경로(vault/·users/·projects/)는 지금처럼 뺀다 — 동기화가 몇 초마다 담는 자리라 이 검사를 대면 아무것도 commit 할 수 없다.
