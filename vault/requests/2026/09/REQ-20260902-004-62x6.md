다음 병목이 드러났다. 실측(2026-09-02 08:2x, `/api/chat/target` 24동시 중
`kill -USR1`, 스레드 27개):

  19  glob._iterdir <- streams_glob <- _binding_activity_paths
                    <- chat_alive <- chat_live <- chat_target   ← 여기
   2  readinto (다음 요청 대기 — 정상)
   0  _proc_table_read                                          ← 024 로 사라졌다

`chat_target` 은 바인딩을 전수로 돌며 후보마다 `chat_live` 를 부르고, 그것이
`_binding_activity_paths` → `streams_glob` 으로 **바인딩마다 streams 디렉토리를
glob** 한다. 실측: 요청 한 번에 `streams_glob` 73회, streams 디렉토리 항목
134개. 직렬로는 17ms 지만 동시 24요청에서 9.8초가 된다 —
`/api/chat/target` 은 신선도 계약(C9/C18) 때문에 폴 스냅샷 게이트 **밖**이라
동시 요청 수만큼 그대로 곱해지는 자리다.

전후(024 마감 시점 실측, 같은 자·같은 부하):
  /api/chat/target  동시 8건  12.75s → 2.58s   동시 24건 37.8s → 9.8s
남은 9.8초가 이 결함이다. 부하 중 `s9 shot` 은 여전히 60초 타임아웃이다.

고칠 방향(판정 필요): 024 가 `/proc` 에 쓴 것과 같은 두 겹이 그대로 맞는다 —
① 요청 스코프에서 streams 목록을 한 번만 뜨고(`proc_scope` 와 같은 자리),
② 바인딩마다 glob 하지 말고 **한 번 뜬 목록에서 sid 로 고르기**. 디렉토리
목록은 요청 스코프 안에서만 나눠 쓰므로 신선도 계약은 그대로 산다.
