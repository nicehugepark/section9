검토 결과.
① 시험을 jade 에서만: 이미 그렇다 — state/test-remote=jade 라 전체 실행(손·post-commit 배경)은 jade 로 간다(95초). 이 머신에 남는 것은 커밋 문의 스모크·표적 실행뿐인데, 그것은 **미커밋 작업 나무**와 이 머신의 git 훅을 재는 자리라 원격이 대신할 수 없다(원격은 commit 된 sha 만 돈다, LOCAL_ONLY 4파일). 수초라 그대로 둔다.
② 문서·소스 GitHub 실시간 동기화: 기계는 이미 있다 — s9 sync remote 모드(문서 이벤트마다 commit→pull --rebase→push, s9 serve 안의 60초 루프, s9doc 병합 드라이버). 다만 지금은 **인스턴스 전용**(.s9-sync 마커가 있어야 켜진다)이고 section9 코드 저장소 자체에는 마커가 없어 어떤 자동 git 쓰기도 없다. 켜는 길: 저장소 뿌리에 .s9-sync 내용 'remote' 한 파일을 commit — track 되므로 jade 는 pull 만으로 물려받는다. 동기화 대상은 vault/users/projects 문서뿐이고 **소스는 지금처럼 사람의 commit** 이다(그 commit 은 sync 의 push/pull 로 양쪽에 실린다).
③ 위험: 문서 노트 하나가 main 커밋 하나가 된다(CONTEXT 의 main 직접 push 정책과는 맞다) · 네트워크 실패 뒤 60초 백오프 「sync: local」 낱말 혼동(0902-037 제안) · state/sessions/*.json 이 track 되는데 머신별 파일명이라 충돌은 없다 · 두 머신이 같은 REQ 를 동시에 고치면 병합 드라이버가 노트를 시각순으로 잇는다(s9-install 을 돌린 머신 전제 — jade 는 돌렸다).
④ 부수 효과: 이것이 곧 0902-037 의 「두 머신이 함께 볼 사설 저장소」다 — 켜면 장면 1~5 를 GitHub section9 main 으로 밟을 수 있다.
⑤ jade 대시보드는 ssh 포트 전달로 본다: s9 secret run -- sh -c '{{secret:jade}} -N -L 9919:127.0.0.1:9909' 뒤 http://127.0.0.1:9919 (이 머신의 9909 와 겹치지 않게 9919).

### 2026-09-06T00:50:28+09:00 response (agent: lead:claude-fable-5-1, by nicehugepark)

jade 대시보드 터널이 「연결 거절」이던 원인: ssh -L 의 바인드 주소 생략 → [::1]+127.0.0.1 이중 바인드를 VirtioProxy 가 공개하지 않음. -4 와 127.0.0.1: 명시로 해결(A/C/D 실측 200, B 000). 지식 문서로 남김.
