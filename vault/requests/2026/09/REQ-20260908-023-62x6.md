### s9 project rename <old> <new> (구현)

 에 (단일 코드 경로) +  + CLI 액션  을 넣었다. 권한은 own(owner) — slug 는 프로젝트의 신원이라 설정 변경(manage)보다 무겁게 잡았다.

**한 번에 옮기는 네 자리**
1. `vault/projects/<slug>.md` 파일 이름 (os.rename)
2. `projects/<slug>/` — CONTEXT.md·assets·agents 통째 (os.rename)
3. 모든 문서의 `project:` — vault 전체(.trash 포함)를 훑되 **frontmatter 의 project 한 줄만** 바꾼다. 본문 글자는 손대지 않는다(본문의 'section9' 까지 바꾸면 그때 무엇을 적었는지가 거짓이 된다)
4. 에이전트 미러 `.claude/agents/<slug>--<이름>.md` — sync_project_agents() 재실행. 매니페스트가 옛 이름을 치우고 새 이름을 세운다
그 뒤 rebuild_index(full=True). 문서 자신의 slug 칸과 History 한 줄(`이름 변경 old -> new (by ...)`)도 같은 트랜잭션 안이다.

**실패했을 때** — 부분 적용을 남기지 않는다. 검사(없는 slug·이미 있는 slug·이미 있는 폴더·허용 문자 밖·같은 이름·권한)는 전부 lock 안에서 쓰기 전에 끝낸다. 쓰기 단계는 옛 글을 손에 쥐고 진행해, 한 건이라도 OSError 면 쓴 것을 전부 되돌리고 → 폴더 이름 되돌리고 → 문서 파일 이름 되돌린 뒤 올린다. S5 시나리오가 대상 문서 하나를 0444 로 막아 이것을 실측한다.

**미검증**: 비-owner 거부 경로는 시험에 넣지 않았다(project_can 이 다른 자리에서 이미 검증된 경로). 대시보드 API(/api/project/*)에는 rename 을 붙이지 않았다 — CLI 한 자리다.
