## Original

실측 2026-09-13 (devops-engineer, REQ-20260913-006-62x6 의 commit 2):
1) 공유 index 에 다른 에이전트의 add 가 섞임 — 17:58 bin/s9_invite.py·tests/test_project_invite.py·bin/s9.py(13 hunk), 18:08 에는 README.md·docs/guide*.md·web/guide.html 까지 6개(s9.py 18 hunk). 각 에이전트의 git diff --cached 가 남의 파일을 보이니 guard 의 동시 작업 검사 표가 서로 죽는다 — 서로 기다리는 꼴.
2) 그래서 임시 index(GIT_INDEX_FILE=<scratch>/idx, git read-tree HEAD → 자기 hunk 만 git apply --cached → 자기 파일 git add)로 commit 했다. guard 는 그 index 를 읽어 5개 파일만 보고 표를 줬고 훅·시험(스모크∪담긴)은 그대로 실행됐다. 그러나 두 번(18:03·18:05) 모두 검사 통과 뒤 `fatal: cannot lock ref HEAD: is at df619179 but expected ef888e56` — 검사가 도는 40초 사이에 s9 sync: serve/lease commit 이 HEAD 를 옮겼다.
3) sync 의 _sync_commit_busy 는 state/commit-in-progress 표식(guard 가 pre-commit 시작에 만듦)과 .git/index.lock 을 보고 회차를 건너뛴다(REQ-20260906-030). 그런데 표식이 생기기 전에 이미 시작된 회차(원격 pull·push 포함)는 그 뒤에 commit 을 얹는다. 임시 index 는 .git/index.lock 을 잡지 않으니 그 보호도 없다.
후보: (a) guard 가 pre-commit 시작 전에 sync 잠금이 신선하면 그 회차가 끝날 때까지 짧게 기다린다 (b) `git commit` 을 sync 의 잠금 아래에서 여는 `s9 commit -- <path>...` 같은 정식 길(자기 hunk 선택 포함) (c) 문서: 여러 에이전트가 한 작업 트리에서 commit 할 때의 규칙(자기 파일은 pathspec commit, 공유 파일은 리드가 담는다).
