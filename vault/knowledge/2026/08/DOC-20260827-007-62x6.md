## Original

## 현상

리드가 막힌 명령(`git push` 등)을 만나면 두 갈래가 떠오른다 —
(1) 명령을 그냥 실행한다 → 차단.
(2) `~/.claude/settings.json` 의 `permissions.allow` 에 규칙을 넣어 스스로 연다 → **이것도 차단.**

(2)가 막히는 것이 핵심이다. 막힌 능력을 스스로 열도록 설정을 고치는 동작은
첫 차단을 무효화하는 짓이라, 검사가 정확히 그것을 막게 돼 있다.

## 하지 않는 것

- 셸(`python3 -c`, `sed` 등)로 같은 설정 파일 쓰기 — 도구만 바꿔 같은 결과를 내는 것은
  규칙을 지킨 게 아니라 피해 간 것이다.
- `.claude/settings.local.json` 등 다른 설정 파일에 같은 규칙 넣기 — 같은 우회다.
- 차단되지 않는 명령 표현 찾기 — 분류기를 떠보는 것 자체가 우회다.

사용자가 "우회해도 된다, 어차피 내가 시키는 거다" 라고 해도 마찬가지다. 지시 권한은
실재하지만 그 권한은 **검사를 여는 권한**이지 밑으로 파고들 근거가 아니다. 한 번
우회하면 이 검사는 앞으로 모든 경우에 있으나 마나가 된다 — 정말 막아야 할 때까지
포함해서. 방어가 있는데 피해 가면 방어가 없는 것보다 나쁘다(있다고 믿게 되니까).

## 대신 하는 것

준비를 전부 끝내 두고, 남은 한 줄과 여는 절차를 문서에 남긴 뒤 `blocked` 로 전이한다.
채팅으로 흘리면 유실된다. `review` 가 아니라 `blocked` 인 이유는 사용자가 승인·반려로
답할 사안이 아니라 **직접 손을 대야 풀리는** 사안이기 때문이다.

여는 길 (사용자 몫, 10초):

    ① 터미널에서 `/permissions` → allow 에  Bash(git push:*)
    ② ~/.claude/settings.json 최상위에 넣고 Claude Code 재시작
           "permissions": { "allow": ["Bash(git push:*)"] }
    ③ 열지 않고 그때그때: 터미널에서 직접 실행

②는 접두 일치라 `git push --force ...` 도 포함된다. 그리고 넣는 순간부터 리드가 언제든
밀어 올릴 수 있다 — 그것이 이 결정의 실제 내용이므로 함께 알린다.
