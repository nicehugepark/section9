## Original

## 왜 필요한가 (오늘 실제로 깨진 것들)

- 위임한 에이전트 2개가 병렬로 돌고 있었는데 대시보드에는 아무 표시도 없었다 — 리드가 클레임(`s9 last --add`)과 `agent_transcript_path` 등록을 잊었기 때문. 사용자가 "병렬진행이 안되나?"라고 물을 만큼 안 보였다.
- 앰버 점멸은 스폰 마커의 600초 창만 보고 켜진다. 그 워커는 fable 한도로 스폰 직후 죽었는데도 10분간 "기동 중"으로 보였다. **신호가 생존을 보증하지 않는다.**
- 문서에는 `agents: ["lead:claude-fable-5", "subagent"]` 처럼 **누가 참여했는지만** 남는다. 어느 항목을 누가 어디까지 했는지는 노트 본문에 흩어져 있어, 이어받는 세션이 재구성해야 한다.
- 워크플로(Workflow 툴) 실행은 추적 대상이 아예 아니다.

## 이미 있는 재료

| 재료 | 현재 하는 일 | 한계 |
|---|---|---|
| 노트 `--agent <타입>` | 노트 헤더·프론트매터 `agents:` 누적 | 값 형식이 자유 — 리드/서브/워커 구분이 규격화돼 있지 않다 |
| 바인딩 `last_req`/`active_reqs` | live 판정의 클레임 원천 | 수동 등록. 잊으면 사라짐. uid 접미사 불일치 버그(REQ-086) |
| 바인딩 `agent_transcript_path` | 위임 에이전트 활동을 live로 잡음 | 단일 값 취급, 등록도 수동 |
| `/api/agents` | 세션 transcript에서 Agent 스폰 파싱(타입·라벨·토큰·경과) | 세션 transcript 안에서만 보임. 문서와 연결 안 됨 |
| `state/auto_resume/<id>.json` | 백그라운드 작업자 스폰 마커 | 생존 확인 없음 |
| SubagentStop 훅 | 서브에이전트 최종 보고를 `--label subagent`로 문서에 캡처 | 보고 1회 = 항목 1개라는 보장 없음 |

즉 **신호는 다 있는데 한 곳에 모이지 않고, 아무도 생존을 확인하지 않는다.**

## 설계

### 1. actor 규격 (한 줄 문자열로 통일)

노트의 `--agent` 값을 자유문자열에서 규격으로 좁힌다:

- `lead:<model>` — 리드가 직접 (예: `lead:claude-opus-5`)
- `sub:<타입>:<agentId8>` — in-process 서브에이전트 (예: `sub:designer:a1fefd40`)
- `wf:<워크플로명>:<runId8>` — 워크플로 실행
- `worker:<사유>` — 무인 auto-resume 워커 (예: `worker:auto-resume`)

기존 값(`lead:claude-fable-5`, `subagent`)은 그대로 두고 파서가 관대하게 읽는다(하위호환).

### 2. contributions — 항목별 처리 이력

문서 프론트매터에 배열 하나를 추가한다. 노트가 붙을 때 훅이 자동 누적한다:

```yaml
contributions:
  - actor: sub:staff-engineer:af69449b
    item: "N1~N8 TDD 구현"
    started: 2026-08-25T21:52
    ended: 2026-08-25T22:03
    result: done            # done | failed | stalled | running
    transcript: /tmp/.../tasks/af69449b.output
```

- `item`은 `s9 note <id> --item '<작업 단위>'` 로 받는다. 생략하면 노트 첫 줄 요약을 쓴다 — **강제하지 않는다**(입력 강제는 훅이 못 채우고 사람만 귀찮아진다).
- 항목 단위의 기본값은 이미 문서 안에 있다: TDD 시나리오 체크박스(N1, P2 …)와 반려 사이클. 이걸 그대로 항목 키로 쓸 수 있게 `--item N1..N8` 형태를 허용한다.

### 3. healthcheck (핵심 — 신호가 생존을 보증하게)

`s9 agents health [--json]` 를 만들고 serve 워처가 30초마다 돌린다. 주체별 판정:

| actor | 살아있음의 근거 | 죽음/정지 판정 |
|---|---|---|
| lead | 세션 transcript mtime < 120s + attach_pid 생존 | pid 없음 → dead |
| sub | agent transcript(output_file) mtime < 180s | 파일 정지 + 종료 통지 없음 → stalled |
| wf | 워크플로 저널 진전 | 진전 없음 → stalled |
| worker | 스폰 pid 생존 **AND** `state/auto_resume/<id>.log` 진전 | 로그에 한도/오류 문자열 → **failed** (오늘의 fable 사례) |

결과를 contributions의 `result`에 반영하고, live_kind를 여기서 산출한다: `direct`(실행 중인 클레임) / `session`(간접) / `spawned`(기동 직후, 아직 첫 진전 전) / **`failed`(신규 — 종료된 작업자)** / `idle`.

대시보드 점멸등에 **실패 상태(빨강 정지등)** 를 추가한다 — 지금은 종료된 작업자가 앰버로 실행 중인 것처럼 보인다.

### 4. 등록 자동화 (사람이 잊는 것을 구조로 막는다)

- 리드가 Agent 툴로 위임하면 훅(PreToolUse/PostToolUse of Agent)이 자동으로 `active_reqs` 클레임 + `agent_transcript_path` append 를 수행한다. 수동 규약(PROTOCOL 9·10항)은 유지하되 **기본은 자동**.
- `agent_transcript_path`는 리스트로 정규화(REQ-086과 동일 지점).

### 5. 재개

`s9 resume-item <id>` — contributions에서 `running`/`stalled`로 끊긴 항목과 그 transcript 경로를 뽑아, "어디까지 했고 무엇이 남았는가" 프롬프트를 만들어 워커를 재스폰한다. 지금은 문서 전체를 다시 읽혀 재작업시키므로 중복 작업이 생긴다.

## 비용과 위험

- **기록 과잉**: 항목이 잘게 쪼개지면 contributions가 수십 줄이 된다 → 노트 1건 = 기여 1건 상한, 같은 actor의 연속 항목은 병합.
- **훅 부하**: healthcheck가 30초마다 pid·mtime을 훑는다. 대상은 활성 in-progress 문서로 한정(현재 5~10건 수준).
- **정확도의 한계**: 항목 경계는 에이전트가 보고한 문장에 의존한다. 자동 추출은 요약일 뿐이며, 정밀 항목은 리드가 `--item`으로 명시할 때만 정확하다. **이 한계를 문서에 명시**하고 과신하지 않는다.
- **워크플로**: in-process라 transcript 파일이 따로 없다. 워크플로 저널(runId)을 경로로 등록하는 별도 작업이 필요하다.

## 단계 (독립 배포 가능 단위)

1. actor 규격 + contributions 누적(훅 자동) — 기존 노트 경로에 얹으므로 위험 낮음
2. `s9 agents health` + live_kind에 failed 추가 + 대시보드 정지등 — 오늘 사고의 직접 대응
3. Agent 위임 시 클레임·transcript 자동 등록
4. `s9 resume-item` 재개
5. 워크플로 추적

REQ-086(진행 점멸등 오판)이 2단계의 선행 절반을 이미 다룬다 — 중복 구현을 막기 위해 086 완료 후 착수한다.
