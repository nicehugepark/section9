### 프로젝트(Project) 모델 · 로드맵

### 원칙
문서가 진실의 원천. 프로젝트도 1급 문서(type=project, prefix PRJ)로 두고, 멤버십/고객/담당자를 그 문서에 담는다. user→project 매핑, board/graph 필터는 문서에서 파생.

### 식별자 (3종)
- `id`: PRJ-YYYYMMDD-NNN — 정본(그래프/불변 참조).
- `slug`: 사람이 읽는 핸들(예: section9), 유일. 파일명 = vault/projects/<slug>.md.
- `title`: 표시명(예: "Section9 하네스 시스템").
요청의 project 필드는 slug를 저장(기존 `section9` 값과 호환). CLI/조회는 id·slug 모두 허용.

### 프로젝트 문서 frontmatter (1단계)
id, type=project, slug, title, summary, status(active|archived),
customer(고객 조직), contact_name/contact_email/contact_phone/contact_org(현업 담당자),
members: [{"user","role","since","until"}], created, updated.

### 멤버십 · 역할
- 프로젝트 역할(시스템 role과 별개): owner|maintainer|contributor|viewer.
- 한 사용자가 여러 프로젝트에 동시 참여 가능(멤버십은 각 프로젝트 문서에 분산 기록).
- 만료(until): 빈 값=무기한, 날짜면 그날까지 유효. member_active = until 없음 or until>=오늘.
- 추가/수정/삭제: s9 project member add/rm, 역할·만료 변경은 add 재실행(upsert).

### 인가(authorization) — 단계적
1단계: 기록·조회만. project_role(slug,user) / user_projects(user) 조회 primitive 제공, 강제 없음.
차기: 미참여·만료 사용자의 해당 프로젝트 요청 생성/전이 차단(하네스 훅에서).

### 요청 → 프로젝트 매핑 (1단계)
s9 new request: --project 명시하면 그대로(id→slug 정규화). 없으면 요청 주체의 활성 멤버십이
정확히 1개면 자동 기입, 2개+면 비움(모호), 0개면 비움. 감사 훅도 동일 규칙.

### 대시보드 (1단계)
프로젝트 셀렉터(전체/특정) → 보드·그래프가 그 프로젝트로 필터. 프로젝트 정보 패널(고객/담당자/멤버·역할·만료). 기존 by-project 필터 재사용.

### 로드맵
- 1단계(현재): 데이터모델 + CLI + 요청매핑 + 대시보드 뷰 (인가 기록·조회).
- 2단계(예정): 인가 강제, 프로젝트별 에이전트 커스터마이즈, 멤버 만료 알림.
- 3단계(예정): 고객 포털/외부 공유, 프로젝트 템플릿, 감사 리포트.

### 프로젝트 = 지식 허브 (2단계 구상, REQ-20260823-062)

프로젝트는 단순 태그가 아니라 그 프로젝트의 모든 것을 **수집·기억·대응·생산**하는 허브다.
흩어진 요구를 4계층으로 정리한다.

### 계층 1 — 메타데이터 (프로젝트 문서 자체)
현재(1단계) 보유: 고객사(customer), 이름(title), 별칭(slug), 개요(summary), 멤버·역할·만료.
추가 필요: 내용/상세 설명, 계약 정보(계약일·기간·규모), 프로젝트 코드/번호.

### 계층 2 — 산출물 문서 (deliverables) · "만든다"
제안서, 계약서, 요구사항정의서(SRS), WBS, 설계서, 테스트계획, 보고서 등.
- 각 문서: 유형(doc_kind) + 버전 + 상태(초안/검토/승인) + 프로젝트 링크 + 담당자.
- section9 문서로 편입(frontmatter + 그래프). 원본이 바이너리(docx/xlsx/pdf)면 → **메타+요약+링크는 vault(md), 원본 파일은 attachments/ 참조**(md 기반 유지).

### 계층 3 — 커뮤니케이션·컨텍스트 (ingested) · "수집·기억"
이메일, 채팅 로그 등. 산출물이 아니라 근거/맥락.
- 고volume·반구조화. 전부 1급 문서화하면 vault 비대·보드 오염.
- 방향: 출처 메타(발신/수신/일시/스레드) + 원문 보존 + 프로젝트/REQ 링크. 대량은 요약·인덱싱 중심, 원문은 참조.

### 계층 4 — 생산 활동 (produce/respond) · "대응·생산"
요청(REQ) → 에이전트가 **프로젝트 컨텍스트(계층1~3) 안에서** 작업 → 산출물 생성.
기존 요청·에이전트·감사 시스템이 프로젝트 스코프로 동작(1단계 매핑이 시작점).

### 역할 2축 분리 (핵심 설계 결정)
현재 PROJECT_ROLES(owner/maintainer/contributor/viewer)는 **접근권한(access)** 축.
사용자가 말한 PM·PMO·개발자·엔지니어·시니어/주니어는 **직무(title/position)** 축.
→ 두 축은 직교(PM이 viewer일 수도, 주니어가 contributor일 수도). 멤버에 role(권한)+title(직무) 분리 저장.

### 아키텍처 긴장점 (2단계 착수 전 결정 필요)
1. 바이너리 산출물(docx/pdf/xlsx): section9는 md 기반. → 원본은 attachments/에 두고 vault엔 메타+텍스트추출/요약+링크만? (검색·그래프는 md, 원본은 참조)
2. 고volume 이메일/채팅: 전부 문서화 vs 스레드 단위 요약+원문 아카이브. 보드/그래프 오염 방지 위해 별도 type·별도 뷰 필요.
3. 산출물 유형: 새 문서 type(deliverable) + doc_kind 서브분류 vs knowledge 재사용 + category. (제안서/계약서는 생명주기·승인흐름이 knowledge와 달라 별도 type이 유력)

### 로드맵 갱신
- 1단계(완료): 프로젝트 1급 문서 + 멤버·역할·만료 + 요청매핑 + 대시보드 뷰 (인가 기록·조회).
- 2단계(구상): (a) 역할 2축(권한+직무), (b) 산출물 문서 type·첨부 모델, (c) 인가 강제.
- 3단계(구상): 이메일/채팅 수집·아카이브·요약 파이프라인, 프로젝트 컨텍스트 기반 생산.
- 4단계(구상): 프로젝트별 에이전트 커스터마이즈, 산출물 자동 생성(제안서 초안 등), 고객 리포트.
