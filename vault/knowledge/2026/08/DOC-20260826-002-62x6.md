## Original

DOC-20260824-002(깃 동기화·실시간 협업 설계)를 대체한다. 그 문서의 전제(dual-repo,
디바운스 워처, serve 폴링 pull)는 구현이 다른 길을 갔거나 아예 구현되지 않았다.
아래는 **as-built + 확정 설계**다.

## 1. 지금 실제로 돌아가는 것 (as-built, 2026-08-26 코드 실측)

문서 쓰기 이벤트 6곳(new·status 전이·note·set·link·rm)에서 **동기 순차**
`add → commit → pull --rebase → push`. 디바운스도 워처 스레드도 없다.
활성 조건은 `.s9-sync` 마커 + `.git` + `S9_SYNC!=off`. 실패는 전 단계 fail-soft로
`state/sync.log`에 남고 60초 네트워크 backoff. 대상 경로는 vault·users·projects·
streams·state/sessions.

설계 6축 대조: 일치 2(충돌 자동해결 금지, chat 로컬) · 대체 1(dual-repo →
업스트림/인스턴스, REQ-053) · **미구현 3(pull 주기, 실패 표면화, config 옵트인)**.

## 2. 결론 — 방향 5개

### 결론 A. push는 "이벤트마다 즉시"가 맞다. 디바운스는 폐기한다.
문서 이벤트는 초당이 아니라 분당 단위다. 디바운스 30초는 협업 지연을 줄이지
못하면서 커밋 1개=변경 1개라는 감사 가치를 깎고, 배치 스레드를 serve 수명에
묶어 CLI만 쓰는 사용자를 놓친다. **DOC-002 §2의 push 설계를 폐기하고 현행을 확정한다.**

### 결론 B. streams를 이벤트 동기화에서 뺀다. (지금 최대 리스크)
실측: 동기화 대상 106MB 중 **streams가 102MB(96%)**, 최대 파일 33MB. 미러는
append가 아니라 **매 Stop 훅마다 전체 파일 복사**(bin/s9-audit-response:36-47)라,
문서 이벤트마다 33MB 새 blob이 히스토리에 쌓인다. 하루 이벤트 50회면 GB 단위다.
- SYNC_DATA_PATHS에서 streams 제외 → 이벤트 커밋은 vault·users·projects·state/sessions만.
- streams는 **세션 종료 1회 또는 `s9 sync --streams` 배치**로 따로 싣는다.
- 90일 경과 스트림 아카이브 정책은 "후속"이 아니라 **streams 동기화의 선행 조건**이다.
- 트레이드오프: 다른 머신에서 진행 중 세션의 transcript를 실시간으로 못 본다.
  받아들인다 — transcript는 사후 감사용이고, 진행 상황은 문서·state/sessions로 읽힌다.

### 결론 C. commit에 pathspec을 준다 — 결함 두 개가 한 수정으로 닫힌다.
현행 `sync_run`은 데이터 경로만 `add` 한 뒤 **pathspec 없이 commit** 한다(bin/s9:2447).
격리 재현으로 확인된 두 결과:
- **결함 A**: admin이 WIP 코드를 stage 해둔 상태에서 문서를 하나 만들면
  **미완성 코드가 origin에 푸시된다**(실측: bin/fake_code.py가 sync 커밋에 실려 나감).
- **결함 B**: non-admin이 보호경로를 stage 하면 pre-commit(s9-guard)이 커밋을 거부해
  **sync가 전면 정지**한다 — `s9 new`는 rc=0으로 성공을 보고하고 문서는 로컬에도
  커밋되지 않는다. **무증상 데이터 미동기화**다.
`git commit --only -- <데이터경로>` 로 바꾸면 커밋 내용이 데이터로 한정돼 A가 막히고,
guard가 볼 파일에 보호경로가 없어 B도 사라진다. **훅 우회(--no-verify)는 쓰지 않는다** —
guard는 인가 경계지 장애물이 아니다.

### 결론 D. pull은 세 지점에 둔다 — 쓰지 않는 사람도 최신을 본다.
현재 pull은 sync_run 안에만 있다. 즉 **문서를 쓰지 않으면 영원히 낡는다** —
대시보드로 읽기만 하는 팀원은 남의 변경을 전혀 못 본다. DOC-002가 약속한
"최악 90초"는 성립한 적이 없다. 세 지점을 둔다(새 데몬·새 스레드 없이):
1. **SessionStart 훅 1회** — 세션 시작 신선도. 비용 0(이미 있는 훅).
2. **serve의 기존 30초 루프(_rework_loop)에 pull 틱** — 활동 중 60초, 유휴 5분.
   새 스레드를 만들지 않는다.
3. **`s9 digest` TTL pull(120초)** — CLI만 쓰는 사용자의 갱신 경로.
목표 수치(고정): push 지연 = 이벤트 즉시(수 초) · pull 지연 ≤ 60초(활동 중) ·
**체감 최악 ~60초**. 초 단위 실시간은 하지 않는다 — 허브(SSE)는 로컬 파일 원칙을
깨고 단일 장애점을 만든다. 필요해지면 pull 주기를 10초로 좁히는 것이 먼저다.

### 결론 E. 실패를 사람에게 보이게 한다. 자동 해결은 계속 금지.
rebase 충돌은 지금 "60초 backoff → 다음 이벤트 재시도 → 같은 실패"를 **아무 신호 없이**
무한 반복한다. sync.log를 읽는 코드는 `s9 sync --status` 하나뿐이다.
- 연속 실패 카운터를 state에 두고, 1회 이상이면 **`s9 digest` 첫 줄**과 **대시보드
  배지**, SessionStart 컨텍스트에 ⚠ 한 줄로 올린다.
- 문구는 사유와 다음 행동(`s9 sync` 수동 실행 / 충돌 파일)을 함께 준다.

## 3. 확정된 것들 (재판정 불필요)

- **리모트**: 업스트림(코드) ↔ 인스턴스(사설, 데이터 track). dual-repo는 폐기(REQ-053).
- **옵트인**: `.s9-sync` 마커 방식 유지. 사용자 확정("클론만 한 사용자 환경에서 git
  쓰기 0")의 취지는 마커로 충족된다 — 마커는 인스턴스 리포에만 있다. 킬스위치
  `S9_SYNC=off` 유지. 단 **docs/08의 "이 시스템은 스스로 commit/push 하지 않는다"는
  문장은 인스턴스에서 거짓이 됐다 — 개정 필요.**
- **id 충돌 안전망 불필요**: uid fingerprint 접미(REQ-031)로 다머신 동시 발번이 파일명
  수준에서 겹치지 않는다. DOC-002 §4의 한계와 REQ-006 §3 안전망은 close.
- **state 범위**: state/sessions만 공유(파일명에 머신 포함), 나머지(terminal inbox·
  port·auto_resume·sync.log)는 머신 로컬. 현행 유지.
- **첨부**: vault 하위 assets/에 있어 동기화 대상에 포함. 단 대시보드 첨부 ingest가
  `s9 new` 서브프로세스 **뒤에** 실행돼 그 사이클을 놓친다(bin/s9:1849) — 순서 수정 필요.

## 4. 마이그레이션 (현재 → 목표)

- **0단계 (차단 수정, 선행)**: commit pathspec(결론 C) · 첨부 ingest 순서 · 회귀 테스트
  (WIP 코드 stage 상태에서 sync가 코드를 싣지 않는다 / non-admin sync가 정지하지 않는다).
- **1단계**: streams 분리 + 아카이브 정책(결론 B).
- **2단계**: pull 3지점(결론 D).
- **3단계**: 실패 표면화(결론 E) + docs/08 개정.
- **4단계**: 실환경 1회 실측 — 지금까지 sync는 **단위 테스트에서만** 돌았다.
  인스턴스 리포에 마커를 두고 실이벤트 1건이 origin에 반영되는 것을 확인해야
  "동작한다"고 말할 수 있다.

0단계 전에는 인스턴스에 sync를 켜지 않는다 — 켜는 순간 결함 A/B가 실데이터에서 터진다.
