## Original

## 사실 (2026-09-09, DESKTOP-TEHV1KR, REQ-20260909-067)
- `ip rule` 우선순위 1: from all ipproto tcp lookup 127 → table 127: 127.0.0.1 via 169.254.73.152 dev loopback0. 리눅스→리눅스 loopback 연결도 윈도우 중계(pid 는 netstat.exe 로 확인)를 지나 돌아온다. 그래서 loopback 리셋의 발신자가 리눅스 커널이 아닐 수 있다.
- 9911(오늘 16회 재기동, 매번 5초 뒤 = 유령 창 안)은 새 연결 30~50% 리셋. 같은 시각 갓 띄운 포트(stdlib·같은 코드 s9)는 0. Chrome 을 붙인 채 3회 재기동한 임시 포트는 0→2%.

## 판별법 (서버 코드인가 중계인가)
1. 리셋이 나는 동안 서버 프로세스 스레드 수(/proc/<pid>/status Threads)와 wchan — 핸들러 스레드가 안 늘면 서버는 그 연결을 받은 적이 없다.
2. `ss -tlnp` 리스너 Recv-Q(accept 큐) — 0 이면 큐 넘침이 아니다.
3. `ss -tanp` 에서 :포트 행 — users:(...) 가 있으면 accept 된 것, 없고 ESTAB 이면 accept 큐, 아예 없으면 중계가 서버에 연결하지 않았다.
4. `nstat -n; …; nstat` 의 TcpOutRsts 가 관측 리셋 수보다 작으면 RST 는 리눅스 밖에서 왔다.

## 대응
- 복구: 포트를 62초 넘게 완전히 비운 뒤 다시 듣는다(윈도우 netstat.exe 에서 LISTENING 이 사라진 것을 확인).
- 예방: 재기동 때 리스닝 소켓을 닫지 않거나(감시자가 쥐고 fd 상속) 자동 재기동 빈도를 줄인다. 환경 쪽은 networkingMode=mirrored 실측이 필요하다.
