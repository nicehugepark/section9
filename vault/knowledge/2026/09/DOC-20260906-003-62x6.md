## Original

## 실측 (2026-09-06, DESKTOP-TEHV1KR, WSL2)

- 리눅스에서 127.0.0.1:P 에 listen 하면 윈도우 쪽 netstat 에 P 가 LISTENING 으로 나타난다(조용할 때 50ms 안).
- 리스너를 닫아도 윈도우 쪽 LISTENING 은 **약 62초** 남는다. 그동안 P 로 connect 하면 **성공한 뒤 8ms 안에 reset** — 아무도 듣지 않는데 붙는다.
- 0.0.0.0 리스너의 공개는 대개 닫자마자 걷힌다(5주기 중 4주기).
- 조용할 때는 공개가 남은 채 같은 포트에 서버를 다시 올려도 40/40 도달한다. 붉음은 **낡은 공개 + 새 리스너 + 부하**가 겹칠 때다: 4샤드로 잇단 실행 3회 안에 2회 — 「server did not start — 40초 27회 시도」·code_read_gate 5건 FAIL, 전부 직전 실행이 7초 전 닫은 포트.
- bind+listen 한 번이 이 판에서 약 12ms 다(26,000회 = 304초). 중계가 listen 마다 일한다 — 시험에서 포트를 수천 번 뽑지 마라.

## 고침 (tests/portpool.py)

- 풀은 대역 전체 18800~23999(5200)이고 칸(slot)은 그것을 샤드 수로 나눈 몫이다(8샤드 → 650). 예전 칸당 32포트는 한 실행 안에서도 감겼다.
- 칸의 커서를 칸 잠금 파일(/tmp/s9-portpool/slotN.lock)에 남겨 다음 프로세스가 **이어서** 돈다. 같은 포트는 칸 한 바퀴 뒤에나 돌아온다.
- 잠금·커서는 러너의 실행 전용 루트(s9run-*) **밖**에 둔다 — 샤드 자식이 TMPDIR 을 물려받아 잠금을 루트 안에 만들면 실행마다 지워져 매번 칸 첫머리를 다시 잡는다(실측으로 그렇게 붉었다).
- 윈도우 쪽 LISTEN 을 읽어 그 포트를 뒤로 미루는 층(foreign_listens)은 그대로 2층으로 남는다.

## 판별

연결은 되는데 서버 스레드가 select 에서 놀고 backlog 0 이면 연결이 서버에 도착하지 않은 것이다. 그 포트가 60초 안에 닫힌 적 있는지 먼저 보라(cd /mnt/c && netstat.exe -an -p tcp | grep :P).
