# Jira 동기화 — 설계 결정 (REQ-20260908-070)

주인 지시 2026-09-08 21:13: 개인별·프로젝트별 Jira 연동 — 요청이 생기면 이슈가 생기고, 카드·문서에 이슈가 보이고, 상태를 맞춘다. 방향은 논의. product-owner·architect·security-engineer·backend-developer·designer 다섯의 판정(REQ-070 subagent 노트)을 리드가 합쳐 정한 것이다. Notion 은 이 어댑터가 닫힌 뒤 같은 틀로 재판정한다.

## 결정 열

1. **문서가 진실이다 — Jira 는 거울이지 검사가 아니다.** 우리 전이는 do_transition 한 경로의 검사(TDD N/N · goal · 확인 포인트)를 지난다. Jira 에서 바뀐 상태를 검사 없이 받으면 규약 19조가 우회된다. 그래서 Jira→우리 전이는 같은 검사를 지나고, 걸리면 전이하지 않고 `jira.status` 만 갱신해 카드에 「Jira 와 다름(≠)」으로 보인다.
2. **기본 방향은 push(우리→Jira).** `direction: push | pull | both`, 프로젝트별 설정, 기본 push. 근거: 주인 원문의 첫 요구가 「요청이 생기면 이슈가 생긴다」이고, 밖→안 변경은 문서-진실 제품에서 옵트인이어야 한다. designer 는 pull 기본을 권했다(남의 보드에 잘못 보낸 전이는 되돌릴 수 없다) — 그 위험은 「연결 자체가 옵트인 · 내보내기 범위 설정 · 실패 시 노트」로 받는다.
3. **연결은 두 층.** 개인 자격은 `s9 secret` 키 `jira:<site>` = `email:api_token`(Atlassian API token, Basic; Data Center 는 PAT Bearer — `auth: basic|bearer` 분기 하나). OAuth 3LO 는 후순위(앱 등록·refresh 회전이 비밀을 둘로 늘린다). 프로젝트 연결은 프로젝트 문서 frontmatter `jira: {site, project_key, issue_type, direction, create_on, export, status_map}` — track 되어 팀이 공유한다. **projects/·vault/ 에 비밀 금지**는 검사 한 곳(SECRET_LOCATION_KEYS 자리).
4. **이슈 생성은 요청 생성 직후**(`create_on: open` 기본, `in-progress` 옵션), 요청 `user:` 의 자격으로(reporter = 그 사람). 대상은 「Jira 연결된 프로젝트 ∧ 그 사람 토큰 있음 ∧ `export: all(기본) | size:M+ | manual`」. 자격이 없으면 `jira.pending: create` 만 남긴다. 실패(오프라인·401·timeout)는 요청 생성을 막지 않는다.
5. **멱등은 라벨.** 이슈에 `labels: ["s9-<REQ-id>"]`, 생성 전 문서의 `jira.key` 가 있으면 호출하지 않고, 없으면 JQL `labels = "s9-…"` 로 선검색. 이슈 property 에 REQ id·머신·세션.
6. **문서 필드 하나가 표시의 전부.** `jira: {site, key, url, status(Jira 원문), synced_at, synced_by: s9|jira, pending: ""|create|push, last_error, actor, via}`. 서버가 카드 페이로드에 그대로 싣고 브라우저는 Jira 를 부르지 않는다(토큰이 브라우저로 흐르지 않는다).
7. **상태 매핑은 statusCategory 기본 + 프로젝트 표.** Jira 는 상태를 직접 쓰지 못하고 transition 을 골라야 하며 id 가 워크플로마다 다르다. 기본은 카테고리로 고른다: open→new(To Do) / in-progress·blocked·review→indeterminate(In Progress) / done·cancelled→done(Done). 프로젝트 `status_map` 이 상태 이름 단위로 덮어쓴다(owner 가 정한다). 필수 필드(resolution)가 걸리면 400 → 노트·카드 표시, 우회하지 않는다.
8. **Jira→우리는 폴링, webhook 은 후순위.** 워처 스텝 60초, site+project 당 JQL 1회(`labels in (s9-*) AND updated >= -2m`), `state/jira-poll.json` 에 마지막 시각. webhook 은 공개 URL·인바운드 경로가 필요해 로컬 대시보드에 맞지 않는다. 루프 방지: pull 이 일으킨 전이는 `synced_by: jira`·노트 표식 → push 훅이 건너뛴다. both 충돌: 문서의 마지막 전이 시각 > synced_at 이면 우리 것을 다시 push 하고 Jira 변경은 노트로만.
9. **실패는 outbox 로.** `state/jira-outbox.jsonl` 에 적재, 워처가 backoff(30초×2^n, 최대 1시간) 재전송. 429 는 Retry-After 를 지킨다. **401 은 재시도하지 않는다**(반복 401 은 계정 잠금) — blocked 전이 + 재설정 가이드. 3회 실패면 `jira.last_error` 를 문서에 적고 카드에 보인다. 호출 timeout 5~10초, 표준 라이브러리(urllib)만.
10. **백그라운드 작업자는 기본 거부.** `auto_resume_jira` 옵트인(auto_resume_gh 와 같은 갈래, 만료일 있음)이 있어야 작업자가 사람의 토큰으로 Jira 를 바꾼다 — Jira 감사 로그에는 그 사람이 한 것으로 남는다는 사실을 스위치 문장에 적는다. 이슈로 내보내는 본문은 허용 목록(title·summary·goal·링크)뿐 — 문서 body 는 나가지 않는다.

## 화면 (designer)

- 카드: id 줄에 이슈 키만(mono·muted·점선 밑줄, 새 창). 저쪽 상태는 카드에 쓰지 않는다 — 어긋나면 키 뒤 `≠` 한 글자(툴팁에 양쪽 상태).
- 문서: `.metatbl` 한 행 — `PAY-123  In Progress · 3분 전 동기화`(Jira 표기 그대로).
- 자리: 개인 토큰 = Settings 「내 계정」, site·key·direction = Projects 정보 패널(select 값은 push/pull/both 글자 그대로, 이름은 「여기 → Jira」「Jira → 여기」「양쪽」).

## 사람만 답할 것

- Jira **Cloud 인가 Data Center 인가**(인증이 다르다) — 첫 구현 단위가 실호출로 확인한다.
- 이 저장소(section9)도 내보낼 것인가 — 하루 요청 70건이라 `export: size:M+` 를 권한다.
- 우리 프로젝트 1 ↔ Jira 프로젝트 1 대응으로 시작해도 되는가(기본 가정).

## 한계

실 Jira 없이 판정했다. endpoint·필드 이름은 REST v3 지식 기준이고 첫 단위(`s9 jira ping`)에서 실호출로 확인한다. 같은 OS 계정 아래 여러 s9 user 면 `s9 user switch` 만으로 남의 토큰을 쓸 수 있다 — 사용자 간 격리가 없다는 사실은 그대로 둔다(기존 secret 모델의 한계).
