## Original

상황(2026-09-13, 에이전트 9명 병렬): git diff --cached 에 다른 요청(REQ-006)의 파일과 bin/s9.py hunk 가 이미 담겨 있었다. 이때 git commit 은 index 전체를 실으므로 남의 미완성이 내 commit 이 되고, 반대로 남이 먼저 commit 하면 내 hunk 가 남의 메시지로 실린다. git reset/restore 로 남의 스테이지를 풀면 그 사람의 상태를 흔든다.

절차(공유 index 를 건드리지 않는다):
1. 내 hunk 만 고른다: git diff <파일> 을 hunk 단위로 갈라 내 표식(함수·라우트 이름)이 든 것만 패치로 저장. 패치 머리의 old mode/new mode 줄은 지운다(mode 변경을 실수로 싣지 않게).
2. export GIT_INDEX_FILE=$(mktemp) ; git read-tree HEAD ; git apply --cached <패치> ; git add <새 파일…>
3. git diff --cached --stat 로 내 파일만 있는지 읽는다.
4. tok=$(bin/s9-guard --concurrent | grep -o "S9_ALLOW_CONCURRENT=[0-9a-f]*" | cut -d= -f2) — 표는 이 index 의 담긴 내용으로 난다.
5. S9_ALLOW_CONCURRENT=$tok git commit -F <메시지> — 훅(guard·commit-msg·post-commit)은 그대로 돈다(GIT_INDEX_FILE 을 물려받는다).
6. HEAD 가 그 사이 옮겨졌으면(sync commit) guard 가 목록 변화로 거부한다 — 옳은 거부다(옛 HEAD 로 읽은 index 는 그 뒤 commit 을 되돌린다). 2 부터 다시.

주의: 임시 파일을 os.replace 로 덮어쓰면 실행 비트가 사라진다(bin/s9.py 0755 → 0644 실제 발생). chmod 755 와 git update-index --chmod=+x 로 되돌린다. pre-commit 시험은 working tree 를 보므로 남의 미완성 파일(예: 금지어)이 내 commit 을 막을 수 있다 — 그때는 노트에 적고 기다린다.
