## Original

## 문제
에이전트 8명이 한 작업 트리에서 일하면 (1) `git add <파일>` 은 그 파일의 지금 상태를 담아 남의 hunk 가 딸려오고, (2) 공유 index 에 남의 add 가 남아 있으면 각자의 `git diff --cached` 가 남의 파일을 보여 guard 의 동시 작업 표가 서로 죽는다, (3) `git commit` 은 시작할 때 HEAD 를 읽어 두므로 훅(검사 40초)이 도는 사이 sync commit 이 HEAD 를 옮기면 `cannot lock ref HEAD: is at X but expected Y` 로 실패한다.

## 절차 (실측으로 들어간 것: REQ-20260913-006-62x6 commit 8f80ebabd)
1. 자기 hunk 만 고른다: `git diff HEAD -- <파일>` 을 `@@` 단위로 나눠 자기 표식(REQ id·함수 이름)이 든 hunk 만 patch 로 만든다.
2. 임시 index 를 쓴다: `export GIT_INDEX_FILE=<scratch>/idx; git read-tree HEAD; git apply --cached <patch>; git add <자기 파일들>`. 공유 index 는 건드리지 않는다(reset·restore 없이 남의 항목이 그대로 남는다). 훅은 GIT_INDEX_FILE 을 물려받아 그 index 를 읽으므로 guard·시험은 담긴 것만 본다 — 우회가 아니다.
3. 담긴 것을 기계로 확인한다: `git diff --cached --name-only` 가 정확히 내 파일 목록인지, 공유 파일의 hunk 수가 기대와 같은지.
4. 조용한 창에서 시작한다: `state/commit-in-progress`(5분)·`.git/index.lock`·`state/.sync.lock`(30초) 이 셋이 모두 없거나 낡았을 때만 commit 을 건다. sync 는 guard 가 pre-commit 시작에 만드는 표식을 보고 회차를 건너뛰지만, 표식 전에 이미 시작된 회차(원격 pull·push 포함)는 막지 못한다 — 그래서 시작 전에 기다린다.
5. guard 표: `bin/s9-guard --concurrent` 가 준 `S9_ALLOW_CONCURRENT=<표>` 를 같은 명령 안에서 바로 쓴다(표는 담긴 내용과 작업자 목록의 지문이라 몇 초면 죽는다).
6. 겹쳐서 두 번 실패하면 세 번째를 걸기 전에 요청으로 세운다(규약 18조) — 이 건은 REQ-20260913-022-62x6.

## 주의
- 임시 index 로 commit 하면 `.git/index.lock` 이 안 잡히므로 sync 의 두 보호 중 하나가 없다 — 4 의 대기가 그 자리를 메운다.
- `git commit -- <경로>` 는 index 가 아니라 작업 트리의 내용을 담는다: 남이 고치는 중인 파일에는 쓰지 못한다.
- 첫 commit 뒤 HEAD 에 있어야 시험이 통과하는 파일(VERSION 처럼 `git archive HEAD` 를 재는 시험)은 먼저 따로 commit 한다.
