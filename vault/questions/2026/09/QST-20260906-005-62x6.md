**왜 `sjpark` 이 저절로 사용자가 됐나** — 사용자 해석 순서는 `--user` → 세션 바인딩 → `$S9_USER` → **운영체제 계정**이고, 마지막 단계는 `os_accounts` 별칭에 없으면 계정 이름을 그대로 사용자로 씁니다(REQ-20260827-060-62x6 의 폴백). jade 의 리눅스 계정 `sjpark` 이 nicehugepark 의 별칭에 없었고, 제가 돌린 `s9 sync` 가 그 이름으로 머신 등록부(`users/sjpark/machines.json`)를 쓰면서 `users/sjpark/` 이 생겼습니다 — 그것이 동기화로 이 기계까지 건너왔고, 화면에 `sjpark @ eek-p620 [member]` 로 보였습니다. 제품이 계정을 지어낸 것이고, 사람이 등록한 것이 아닙니다.

**한 것**
- jade: `s9 user attach nicehugepark` 으로 계정 `sjpark@eek-p620` 을 nicehugepark 에 이었고, `users/sjpark` 은 지워 동기화했습니다. 지금 jade 의 `s9 user current` = nicehugepark, 터널의 `/api/whoami` = `nicehugepark · admin · eek-p620`. 브라우저(`http://127.0.0.1:9919`)를 새로고침하면 오른쪽 위가 바뀌어 있습니다.
- 뿌리(`e0eb4f7`, REQ-20260906-008-62x6): 폴백 앞에 **git 신원 대조**를 넣었습니다 — git 의 `user.name`(jade 는 이미 `nicehugepark` 이었습니다)·`github`·`user.email` 이 등록 사용자와 맞으면 그 사용자로 해석하고, 어느 것도 안 맞으면 계정 이름은 쓰되 `users/<계정>/` 등록부는 **만들지 않습니다**. 회귀 시험 U1~U3.
- 동기화 켜기(001)도 닫았습니다: 켜는 중 드러난 sync 결함 둘 — s9 가 스스로 쓴 파일이 rebase 를 막고, `rebase --abort` 마저 실패해 잔재가 남던 것 — 을 `876e257` 로 고쳤고(C10/C11), jade 의 메모가 이 기계에 60초 안에 도착하는 왕복을 실측했습니다. 88a73d7 나무의 원격 전체 시험은 초록(97초)이고, 방금 커밋의 전체 실행은 jade 에서 도는 중입니다 — 끝나면 결과만 한 줄 보고하겠습니다.
