## Original

이 하네스를 만들고 고치고 개선하는게 section9 프로젝트이고, 그 외의 프로젝트는 이 section9을 건드리면 안되지않나? 어떤게 맞는건가?

## Notes

### 2026-09-04T16:13:28+09:00 answer (agent: lead:claude-opus-5, by nicehugepark)

`[2026-09-04 16:13:27 KST - lead]`

**말씀하신 게 맞습니다. 그리고 그건 이미 이 저장소의 규칙이자, 기계로 막혀 있습니다.**

구조가 둘로 갈립니다(docs/08, DOC-20260824-003).

- **section9 저장소 = 업스트림(하네스 자체).** 하네스를 만들고 고치는 일만 여기서 합니다. 지금 `projects/` 에 section9 하나만 있는 건 우연이 아니라 **이 저장소가 곧 그 프로젝트**이기 때문입니다.
- **인스턴스 저장소 = 실제 일하는 자리.** 다른 프로젝트는 여기가 아니라 자기 인스턴스에서 돕니다. 코드(`bin/`·`web/`·`harness/`)는 이미 그 안에 복사돼 들어가 있고, 업그레이드는 `git merge upstream/main` 으로 받습니다.

**「건드리면 안 된다」가 말뿐이 아닙니다.** 커밋 문(`bin/s9-guard`)이 보호 경로를 들고 있습니다:

```
bin/ · web/ · harness/ · .github/ · .gitignore · .gitattributes
projects/<이름>/agents/ · users/<사람>/skills|agents/
```

여기에 걸리는 파일이 커밋에 하나라도 있으면 **admin 이 아닌 사용자는 거부**되고, 「하네스 변경은 PR 로 제안하고 admin 승인을 받는 것이 원칙」이라고 화면에 그대로 말합니다. 뒤의 두 줄이 특히 중요한데 — 에이전트 정의는 데이터 자리에 살지만 **워커 프롬프트에 그대로 주입되는 실행 권위**라, 데이터라는 이유로 열어 두면 push 권한자가 남의 세션 행동을 바꿔 쓸 수 있습니다. 그래서 코드와 같은 취급입니다.

**그러니 정리하면:**

- 하네스를 고치는 일 = section9 프로젝트 = 이 저장소 = 그래서 `tests/` 가 여기 있는 것이 맞습니다.
- 다른 프로젝트 = 인스턴스 저장소 = 하네스 코드는 **읽기 전용으로 받아 쓰는 것**이고, 고칠 것이 있으면 여기로 올려서 고칩니다.
- 인스턴스에서 하네스 결함을 발견하면 그 자리에서 고치지 말고 여기서 고쳐 배포합니다(DOC-20260824-003).

하나 덧붙이면 — 지금 문은 **역할(admin이냐)**로 가릅니다. 「어느 저장소냐」로 가르지는 않습니다. 혼자 쓰는 지금은 같은 말이지만, 팀이 붙어 인스턴스가 여럿 생기면 「admin 인데 인스턴스에서 하네스를 고쳐 버리는」 경로가 열려 있습니다. 그때는 서버쪽 보호(CODEOWNERS·branch protection)가 받치는데, 그건 사람이 GitHub 에서 설정해야 하는 것이라 자동이 아닙니다. 지금 당장 문제는 아니고, 팀이 생길 때 다시 볼 자리입니다.
