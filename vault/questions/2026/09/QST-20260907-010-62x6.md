**전체 테스트가 왜 거짓말을 했는지 밝혀졌습니다. 원격 머신이 옛 커밋을 돌고 있었습니다.**

원인이 둘입니다.

**하나, `set -e` 가 못 막는 자리가 있었습니다.** 원격에서 도는 준비 명령이 `cd $D && git fetch … && … && git clean;` 한 줄이었는데, `set -e` 는 AND-OR 로 이어진 명령 중 **마지막이 아닌 것**의 실패를 무시합니다. 그래서 `git fetch` 가 실패하자(로그 머리의 그 두 줄이 바로 그 흔적이었습니다) 새 코드를 펴는 단계가 통째로 건너뛰어지고, **clone 때 펴져 있던 옛 커밋으로 시험을 돌았습니다.** 종료 코드는 0 → 「전체 통과」.

**둘, 무엇이 실제로 돌았는지 아무도 세지 않았습니다.** 「356파일」은 실행 수가 아니라 **이 머신의 목록 길이**였습니다. 원격에 없는 파일 이름은 조용히 빠지는데, 그걸 잡는 검사는 순차 갈래에만 있었고 원격은 언제나 병렬 갈래였습니다.

고친 방향이 옳습니다 — 「그 파일도 목록에 넣는다」가 아니라 **「돌지 않은 파일이 있으면 통과라고 하지 않는다」** 입니다. 준비 단계를 하나씩 막고, 편 뒤 `git rev-parse HEAD` 로 **요청한 커밋인지 되묻고**, 원격이 실제로 센 파일 수를 걷어 와 요청 수보다 적으면 통과가 아닙니다. 회귀 시험 8건은 가짜 `git` 을 PATH 에 두고 실제 셸로 그 한 줄을 돌려 cd166cc 를 재현합니다.

**제가 판정한 것 하나**: 남아 있던 전체 통과 기록을 지웠습니다. 그 하나만 거짓인 게 아니라 **그 뒤 기록도 같은 길로 만들어졌기** 때문입니다. 하나만 지우고 나머지를 남기면 「어떤 통과는 믿을 수 있다」는 거짓을 더 오래 끄는 셈이죠. 다음 실행이 고쳐진 셈으로 다시 세웁니다.
